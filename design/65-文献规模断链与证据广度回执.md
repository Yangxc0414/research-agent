# 65 · 文献规模断链与证据广度回执

> 触发问题：「咱们目前的来源是否少了，应该搜很多篇进行形成 idea 才对吧」。
> 本文件只记录**实测数字、可定位证据与本轮改动**，不再堆反思长文（见 `61-` 关于「反思产能 >> 改进产能」的判断）。
> 全部命令用 `D:\Program Files\Python38\python.exe` 执行。

## 1. 结论

**是的，来源少了；但根因不是「参数没调大」，而是四层断点让「搜很多篇 → 形成 idea」这条链在默认运行里根本不成立。**

最硬的一条实测：把 `max_sources` 从 3 调到 50，默认 fixture 的来源数、span 数、覆盖度、饱和状态、Q0 判定**完全不变**。调预算无效，因为语料物理上限就是 3 条。

## 2. 实测对照

| 场景 | 命令 | 独立来源 | span | coverage_score | saturation | Q0 | review_grade |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 默认 fixture，3 → 50 预算 | `literature run --question "钙钛矿 界面 钝化 湿热稳定性" --max-sources {3,6,12,50}` | 3 | 5 | 0.454 | partial | `pass` | **no** |
| 7 篇本地 CC-BY 全文，预算 12 | `literature run --question "self-improving agent" --source local --corpus-dir runtime_data/probe-corpus-20261106 --max-sources 12` | 7 | 56 | 1.0 | saturated | `pass` | **yes** |
| 同一本地语料，预算 3 | 同上 `--max-sources 3` | 3 | 24 | 0.675 | partial | `pass` | no |

Q0 在第一行与第二行给出**同一个 `pass` 理由格式**（只报全文数 / span 数 / saturation）。也就是说：**门禁输出无法区分 3 篇演练语料与综述级语料**。

**完整 pipeline 链路的额外实测**：`pipeline run --topic "self-improving agent" --corpus-dir runtime_data/probe-corpus-20261106 --max-sources 12 --flow-mode strict`（`--run-dir` 指系统临时目录）在无模型 key 时**不会跑完**：进程停在 `awaiting host model: awaiting host agent model output; respond to turn ... (module=idea purpose=S2 idea candidates)`，退出码 3，未产出任何 run 产物。这是宿主模型交接机制，不是故障，但它意味着「完整链路」那条命令不是无条件可照抄的 —— 要么用 `research_model_turns` + `research_model_respond` 回答后重跑（replay 复用已答 turn），要么只跑纯离线的 `literature run` 取 S1 结果。接入面文档需按此修正。

**S1→S2 衔接实测**（`LiteratureAgent.run` 的 spans 直接喂 `IdeaAgent.run`，`max_candidates=3`）：

| S1 输入 | S2 状态 | 候选数 | 跨候选去重 `evidence_refs`（span 引用，非独立论文数） | `source_mode` |
| --- | --- | --- | --- | --- |
| fixture 3 篇 / 5 span | `candidates_need_human` | 3 | 4 | `fixture` |
| 本地 7 篇 / 56 span | `candidates_need_human` | 3 | 12 | `real` |

证据引用确实随来源变宽（4 → 12），但 **S2 的候选数与状态完全不随来源规模变化**，也没有 `review_grade` 概念 —— 这进一步说明「形成 idea」这一步目前对证据规模不敏感，只有 S1 侧的新回执能区分两者。

## 3. 四层断点（可定位）

1. **语料天花板**：`modules/literature/fixtures/corpus.json` 只有 3 条（2 全文 + 1 摘要）；四套语料合计 14 条 / 9 全文，且主题分散。`research_agent/adapters/fixture_retriever.py:48` 按 `ranked[:limit]` 取，limit 再大也不超过 3。`research_agent/modules/literature.py:190` 的 `cap = max(1, min(max_sources, 50))` 只是上限。
2. **契约没有下限**：`modules/literature/SPEC.md` 与 `modules/idea/SPEC.md` 都未规定最小来源数 / 最小 span 数 / 覆盖阈值。S1 的 `TARGET_SOURCES=6 / TARGET_FULL_TEXT=3 / TARGET_SPANS=12`（`literature.py:23-25`）只是 `coverage_score` 的**评分分母**，不是阻断条件；唯一校验是 `max_sources >= 1`（`:404-405`）。设计文档里的 100+50 篇（`02-需求书…:751`）、200 篇语料（`:781`）从未进入契约。
3. **Q0 不判来源数**：`research_agent/flow.py:63-92` 只检查「有 span / 有 ≥1 全文 / `saturation != insufficient`」。而 `saturation` 在 `literature.py:322-327` 只要有任意 span 就是 `partial`，`insufficient` 只在 spans 为空时出现 —— 因此 `saturation=insufficient` 与 `no locatable span` 实际上是同一个条件。`coverage_score` 与 missing facets 从未被 Q0 读取。这就是 `coverage_score=0.454`、缺 4 个 facet 仍 `pass` 的原因（`64-:23-24` 已记录）。
4. **S2 无来源下限**：`research_agent/modules/idea.py` 的 `IdeaRequest` 不接收来源数；`run()` 只有空 spans 才 `needs_evidence`，来源不足只写 advisory gap（`single_source` / `no_multi_source_candidate`）。`pipeline.py:437-446` 传给 S2 的只有 `spans`，候选数固定 3。

**真实检索通道的边界**：`--source openalex` 的 `full_text()` 恒为 `None`（`adapters/openalex_retriever.py:163-166`），S1 会记 `full_text_unavailable` gap、0 span、Q0 blocked，**不能当证据来源**；`research_literature_fetch`（`mcp_server.py:1289`，`max_results` 上限 10）与 `conference_fetch` 只负责下载 PDF，下载后仍须 `--source local --corpus-dir` 解析成 span。因此「能取回几十条元数据」≠「能形成可引用证据链」。真正可用的大规模路径是 `LocalDocumentRetriever`（本地 PDF/TXT/MD），本轮实测已验证。
