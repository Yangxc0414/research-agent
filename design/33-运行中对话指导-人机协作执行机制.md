# 运行中对话指导：把“插话”变成受治理的 Guidance 对象

> 目标：用户不只在下指令前后聊天，而是在 Agent 运行过程中随时插话、纠正方向、补充约束、要求暂停/继续。系统需要把自然语言变成**可追踪的 Guidance 对象**，在检查点应用；不能把插话直接当成对 claim/gate 的修改。
> 本轮仍是静态实现：指导只改本地执行策略与下一阶段旁注，不调用 API、不改变真实证据。

---

## 0. 结论

1. **对话是运行控制面的一部分。** 用户在自动运行中输入“优先看 archive 复用”，系统应确认收到、排队、在下一个检查点应用，并在阶段输出里显示“已按指导……”。
2. **插话必须被类型化。** 至少区分：`pause / resume / step / status / sign / guidance(constraint|note)`。不是所有自然语言都直接改状态。
3. **指导只改执行策略，不改证据规则。** 可以改检索关注点、阅读顺序、预算、下一个阶段的提示；不能改 claim/EA/gate/rubric/export/signature。
4. **检查点应用。** 运行中指导默认排队，到下一阶段开始前应用；用户可“立即应用”或“丢弃”。人工门处不能跳过，不能在 gate 未签时继续。
5. **所有指导有账。** `GUIDE-…` 包含文本、类型、状态（queued/applied/dismissed）、应用时间、scope；RUN 上下文可见，线程里有确认卡。
6. **状态必须一致。** 阶段卡、RUN 上下文、header chip、侧栏 guidance 计数都来自同一状态；不出现“已应用但页面还显示 queued”的旧状态。
7. **未来接 runtime 时，指导是 API 资源，不是 prompt 注入。** `POST /api/runs/{id}/guidance` + SSE ack；服务端校验 scope/权限/幂等，不允许指导修改 claim/gate。

## 1. 交互模型

### 1.1 运行中能做什么

| 用户输入 | 系统行为 |
|---|---|
| “暂停 / 停一下” | 立即暂停；保留当前阶段与对象 |
| “继续 / resume” | 从暂停处继续；人工门未签时拒绝 |
| “单步 / step” | 推进一个阶段；人工门处拒绝 |
| “现在到哪了 / 为什么卡住” | 返回当前 stage/gates/guidance 状态；不排队 |
| “签核 / approve” | 仅在 claim 人工门时可签（SIM） |
| “优先看 archive 复用，少取 2020 年前文献” | 入队 guidance；下一阶段输出显示已按指导 |
| 其他自然语言 | 入队 note；不直接改状态 |

### 1.2 指导队列

```text
GUIDE-xxxx
  text      用户原话
  kind      note | constraint
  scope     next_checkpoint
  status    queued | applied | dismissed
  at/appliedAt
```

- 默认 `next_checkpoint`：下一个阶段开始前应用一条；剩余保持 queued。
- `立即应用`：用户显式点击，设置 `guidanceNote`，下一阶段读取；不改变当前阶段已完成的对象。
- `丢弃`：状态 dismissed，不进入下一阶段。
- 人工门：指导可排队，但不能替代签核；`pause/step` 在 gate 处拒绝继续。

### 1.3 反馈

- 收到指导：Agent 在线程里回复“收到指导（GUIDE-…），会在下一个检查点应用；只改执行策略，不改 claim/EA/gate”，并附一张 `USER GUIDANCE` 卡。
- 应用指导：系统事件 `GUIDANCE APPLIED · GUIDE-…`；阶段输出追加 `· 已按指导：…`；阶段卡 note 标 `guided`。
- 丢弃：系统事件 `GUIDANCE DISMISSED`；不写阶段输出。
- Header：`GUIDANCE n`；RUN 面板：`GUIDANCE n QUEUED`；侧栏：guidance 队列计数。

## 2. 状态机

```text
IDLE / RUNNING / PAUSED / HUMAN_GATE
  ├─ user message
  │    ├─ command (pause/resume/step/status/sign) → apply immediately or reject
  │    └─ guidance → append queued
  ├─ next stage
  │    ├─ queued guidance → status=applied; add note to stage output
  │    └─ no guidance → normal
  ├─ human gate
  │    ├─ user sign → SIM claim; continue
  │    ├─ user guidance → queue only; do not bypass
  │    └─ pause/step → paused; no auto-skip
  └─ finish
       └─ remaining queued → visible; user can apply/dismiss
```

**关键不变量**

- 人工门未签时，任何“继续/单步”都不能越过。
- 指导不能改变 claim/EA/gate；它只能改变执行策略。
- 一行指导只应用一次；重复点击不重复生效（idempotent）。
- 阶段状态和 guidance 状态从同一个 project 对象渲染。

## 3. UI 落地

### 3.1 会话

- 输入框在运行中显示：“全自动运行中 · 输入指导会在下一阶段应用”。
- 建议 chips 变为：`插入指导 / 暂停 / 单步 / 停止`；暂停后变 `继续`。
- 用户消息保留在会话中；Agent 确认卡显示 `USER GUIDANCE` 与 scope。
- 阶段卡显示 `guided` 与“已按指导：…”。

### 3.2 RUN 上下文

新增 `GUIDANCE` 面板：

```text
GUIDANCE                        1 QUEUED
GUIDE-xxxx · constraint
优先看 archive 复用，少取 2020 年前文献
queued
[立即应用] [丢弃]
```

- 已应用项显示 `applied · 时间`；丢弃项灰显。
- 空态说明“运行中直接在输入框说话；不会改 claim/EA/gate”。

### 3.3 Header / 侧栏

- Header chip：`GUIDANCE 1`，与 RUN 面板同源。
- 侧栏 RUN CONTEXT：`guidance 1 queued`。
- 自动状态同时显示 `AUTO RUNNING / AUTO PAUSED / HUMAN GATE`。

## 4. 静态实现（本轮）

- 状态：`project.guidance[]`；新增项目/种子项目初始化为空。
- 入口：`sendMessage` → `respondTo`；运行中/人工门处进入 `queueGuidance`。
- 应用：`autoStep` 在阶段开始时调用 `applyPendingGuidance`；阶段输出追加指导文本。
- 立即应用：`applyGuidanceById` 设置 `guidanceNote`，下一阶段消费。
- 丢弃：`dismissGuidanceById` 改 dismissed。
- 签核：自然语言“签核/approve”只在 claim gate 生效。
- 所有操作只改 localStorage 与本地 UI；不调用 API、不真实签核。

### 4.1 边界

- 指导不是 prompt：它是一个有 id/status/scope 的对象；静态版不把它拼进模型请求。
- 指导不是 claim：它不创建/修改 Claim；阶段输出只是旁注。
- 指导不是 gate：它不能清除 `HUMAN GATE`，签核仍是单独动作。
- 静态版没有真实 token 预算消耗；指导应用只是 UI 状态。

## 5. 接 runtime 的 API 设计

> 本轮不实现，只定义边界。

```http
POST /api/runs/{run_id}/guidance
{
  "text": "优先看 archive 复用",
  "kind": "constraint",
  "apply_at": "next_checkpoint"
}
→ 202 {guidance_id, status: "queued"}

GET /api/runs/{run_id}/guidance
→ {items: [...]}

POST /api/runs/{run_id}/guidance/{guidance_id}/apply
POST /api/runs/{run_id}/guidance/{guidance_id}/dismiss
```

- 服务端校验 run 状态、scope、权限、幂等键。
- 只在 checkpoint 应用；应用记录进审计/事件流。
- 指导文本不直接拼进系统 prompt 的“最高优先级”区域；按阶段模板注入，并记录注入位置。
- 不允许通过指导修改 claim/EA/gate/export/signature；服务端拒绝越界字段。
- SSE 事件：`guidance_received`、`guidance_applied`、`guidance_dismissed`、`guidance_rejected`。

### 5.1 未来必须补

- 指导的优先级/冲突合并（例如两个用户同时给约束）；
- 指导的预算/长度限制；
- 指导与 artifact 的绑定（“先看这个来源”）；
- 运行完成后 queued 指导的清理/归档；
- 安全：指导文本是用户输入，不得执行代码/工具；不得覆盖系统安全指令。

## 6. 设计依据

- `14-` 的证据运营：人保留判断、签署与责任；指导是把人的判断注入执行，不是替代签署。
- `21-` 的可落地系统：SSE、job 状态、人工门；指导应作为 run 的事件/资源，而不是聊天旁路。
- `31-` 的静态工作台：对话是控制面，artifact 是状态；本页把“插话”做成 artifact。
- `32-` 的模型设置：指导只改执行策略/预算，不改变模型能力与 claim 规则。
