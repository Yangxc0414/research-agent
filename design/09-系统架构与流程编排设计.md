## 0. 结论先行

### 0.1 六条架构结论

1. **一个内核，两条轨道，五类流程。** 内核只做四件事：产物契约、状态与事件、门禁与签名、claim/run 账本。论文轨道（5–6 人）只建内核 + RWJT 闭环；产品轨道（9+1）再加载完整工作台、Idea 收敛、评审模拟与多用户。两条轨道共用同一套 schema 与 runner，不维护两份代码。
2. **顶层编排是确定性的，Agent 只是被调用的工人。** S0–S16 的转移、门禁、预算、重试由代码状态机执行；LLM 不能决定"下一步进入哪一阶段"，也不能自行放行。Agent 只在单个步骤内有界地规划与执行。
3. **证据账本是唯一事实源。** 稿件事实来自 claim 账本，结果 claim 来自 verdict + `EA(source=rerun)`；数字不直接来自模型上下文，图不直接来自草稿。导出硬门是账本上的纯规则检查，fail-closed。
4. **三权分离写进运行时，而不是写在 prompt 里。** Work 不可见测试与 rubric；Judge 不读 Work 可写状态；Writer 不能创建结果 claim；Export Gate 的判定不可被生成角色覆盖。权限由服务边界与文件系统保证。
5. **v1 采用模块化单体 + 后台 worker + 隔离 runner。** 不引入微服务、Kafka、Neo4j、Kubernetes；一台机器能跑完整闭环。等并发、租户或数据隔离成为真实瓶颈再拆，不提前为假想负载设计。
6. **论文轨道 headless-first。** 先做 CLI/API + 三页最小工作台（门禁签署、槽位查看、审计报告），把预算花在 RWVH、证据账本、槽位与评测上；完整编辑器、图谱交互、多人协作属于产品轨道。

### 0.3 明确不做什么（v1）

| 不做 | 原因 | 重新评估的触发条件 |
| --- | --- | --- |
| 微服务、Kafka、服务网格 | 5–9 人团队运维不起；事务跨服务会让 claim/verdict 一致性变难 | 单机 runner 排队 > 30 分钟成为常态，或出现独立部署的第三方消费者 |
| Neo4j 等图数据库 | v1 的传播闭包用 PostgreSQL 递归 CTE 足够；图规模是万级节点，不是亿级 | 闭包查询 p95 > 2 秒，或需要多跳实时交互 |
| Kubernetes / 多集群 | Docker + 单机 runner 可覆盖 CPU/单卡 v1 任务 | 并发任务 > 8，或需要跨机构调度 |
| 多租户 SaaS、SSO、计费 | 首个周期是论文与内部产品验证，不是商业上线 | 有外部机构试用并签署数据处理协议 |
| 实时协同编辑器 | 单人/小组串行写作足够；协作不是研究贡献 | 产品轨道出现 ≥5 人同时编辑同一稿件 |
| 通用 Agent 聊天界面 | 自由对话不可审计；一切以产物和门禁为中心 | 不重新评估；聊天只作为命令入口 |
| 微调 / 自训练模型 | 数据量不足，效果不可归因；先用网关路由与提示版本 | 有 ≥1 万条经审核的领域轨迹与独立评测 |
| 湿实验、仪器控制 | 安全、伦理与责任边界；A3 不含实验安全决策 | 有实验室合作协议与安全审查 |
| 原生科学环境、GPU 集群（FR-24） | 成本高，v1 用 CPU/单卡冻结任务即可验证 RWJT | H7/H8 进入 10+1 配置且 W1/W3 已达标 |
| AIGC 检测规避 | 合规红线；系统只做披露与留痕 | 永不实现 |
| 自动投稿、冒充真实同行评审 | 合规红线；评审模拟只作自检，不得写成真实审稿意见 | 永不实现 |

### 0.4 规模适配：同一架构，不同能力档

| 轨道 | 人数 / 人周 | 必须有的组件 | 可以没有的组件 | 架构含义 |
| --- | --- | --- | --- | --- |
| 论文轨道（W1+W2+W3） | 5–6 人 / 100–112 `[估算]` | K0 内核、K1 证据、K2 判定、K3 写作、K4 完整传播、最小工作台 | S2/S3 完整收敛、S14 评审模拟、多用户、原生环境 | 单机 + 2 并发；CLI 为主；只做三门禁三页面 |

## 1. 目标、边界与质量属性

### 1.1 产品边界仍是 A3

机器可以做：检索、阅读、抽取、收敛、设计草案、执行、图表、起草、核验、修订、打包。
人必须做：研究问题、确证协议批准、科学新颖性与伦理判断、终审、署名与责任。
架构必须让"人不在场时系统停下来"，而不是让系统"假装完成"。

### 1.2 五个架构目标

| 目标 | 具体含义 | 验收方式 |
| --- | --- | --- |
| **可追溯** | 任何稿件事实句可追到 claim，再到 run、EA、快照与协议版本 | 随机抽 50 句，追溯完整率 100% |
| **可隔离** | Work/Judge、探索/确证、项目/项目、私有/公开数据四类隔离 | 越权测试 0 通过；Judge 读到 Work 私有状态 = 0 |
| **可恢复** | worker 崩溃、容器被杀、长任务超时后可从最近检查点恢复 | 杀进程测试后状态一致；不重复计费、不重复提交 |
| **可控制** | 每个阶段有预算、并发、超时、重试上限与人工停止开关 | 超预算 100% 可定位到阶段/调用；无静默降级 |
| **可演进** | 换模型、换提示、换体裁模板不改核心契约 | 同一任务在新模型版本上可重放并产出可比 manifest |

### 1.3 非目标

- 不做"通用 AI Scientist"或"RSI"；系统是证据闭合的工作台。
- 不把外部系统的效果数字当作我们的结果；不复刻 OpenRSI 的 8×H100 / 13 小时负载。
- 不追求"一次生成整篇论文"的演示；追求"每个进入稿件的结论都有证据"。
- 不让 Agent 自主决定研究方向、伦理边界、署名或投稿。
- 不在 v1 解决跨机构协作、商业化计费与大规模多租户。

### 1.4 质量属性与设计目标

| 属性 | `[设计目标]` | 来源 / 备注 |
| --- | --- | --- |
| 审计完整率 | 100% 的 `R/X/N/F` 槽可解析；导出包字段齐全 | `07-` §10.5、`04-` §2.14 |
| 伪造准入 | 伪造数字/引用通过数 = 0 | C2 成功阈值 |
| 基础设施误记 | `infrastructure_error` 记 0 分的次数 = 0 | `07-` §5.3 I5 |
| 单篇 2 万字 LLM 成本 | ≤ 30 元 | `02-` §11/§13 |
| 单任务复现成本 | ≤ 50 元；Judge ≤ 30 分钟 | `07-` §6.5 |
| 并发 | v1 同时 2 个确证运行；Judge 独占 | `07-` §6.5 |
| 事件可见时延 | 门禁/阶段状态变更 ≤ 2 秒可见 | 本文新增 |
| 导出硬门耗时 | 2 万字稿件 p95 ≤ 60 秒 | 本文新增 |
| 崩溃恢复 | 已提交产物不丢；状态恢复 ≤ 5 分钟 | 本文新增 |
| 备份 | v1 RPO 24 小时、RTO 4 小时 | 本文新增，非研究指标 |

## 2. 总体架构

### 2.1 五层职责与禁止事项

| 层 | 负责 | 明确禁止 |
| --- | --- | --- |
| L1 体验层 | 项目视图、门禁签署、槽位查看、运行/判定查看、审计包下载、CLI | 不直接写数据库；不绕过 API 改状态 |
| L2 编排层 | 状态机、调度、门禁、预算、失败路由、人工收件箱、事件 outbox | 不执行用户代码；不生成稿件内容；不修改 verdict |
| L3 认知层 | 模型网关、上下文包、Agent 运行时、工具、检索/解析、记忆 | 不判定门禁；不直接写 claim 账本；不跨项目读数据 |
| L4 证据与判定层 | claim/evidence 图、槽位注册、传播、RWVH、rubric、导出硬门 | 不生成散文；不替人签署；不接受 Work 自报证据 |
| L5 基础设施 | Postgres、对象存储、Redis、Sandbox、密钥、遥测 | 不承载业务规则；不把队列当事实源 |

### 2.2 v1 运行拓扑

```
浏览器 / CLI
    │ HTTPS / SSE
    ▼
┌─────────────────────────────┐
│ API + Orchestrator（单体）   │  FastAPI；状态机在进程内，事务落 Postgres
│  ├─ Gate Service            │
│  ├─ Scheduler               │
│  ├─ Budget Ledger           │
│  └─ Failure Router          │
└──────┬──────────────┬───────┘
       │              │
       ▼              ▼
┌────────────┐  ┌──────────────────────────┐
│ Worker 池   │  │ Runner Service（独立容器）│
│ LLM / IO   │  │ Work 容器 / Judge 容器    │
│ 解析 / 检索 │  │ 只读快照 / 私有测试 / 无网 │
└─────┬──────┘  └────────────┬─────────────┘
      │                      │
      ▼                      ▼
┌──────────────────────────────────────────┐
│ PostgreSQL（事实）· MinIO/S3（产物）      │
│ Redis（队列/缓存，可丢）· OTel（观测）     │
└──────────────────────────────────────────┘
```

**部署原则**：

- 单体 API 与 worker 可同机，也可 API 一台、worker 一台；v1 不拆服务。
- Runner 必须与 API 进程隔离命名空间；Work 与 Judge 不共享可写卷。
- 基准环境与产品私有环境物理或逻辑分离；产品数据不出私有部署。
- 所有外部模型调用经模型网关，业务代码不持有供应商密钥。

### 2.3 为什么是模块化单体

| 选择 | 替代方案 | 理由 | 代价 |
| --- | --- | --- | --- |
| 模块化单体 | 微服务 | 5–9 人；claim/verdict/gate 需要同库事务；部署简单 | 后期拆服务要还债；用清晰模块边界降低 |
| Postgres + 对象存储 | 图数据库 + 文档库 | 一套事务、备份、权限；万级图足够 | 图查询需手写递归 SQL；有上限 |
| 确定性状态机 | LangGraph / 自由 Agent 编排 | 可审计、可恢复、可测试；阶段转移不应由 LLM 决定 | 灵活性较低；新流程需改代码与版本 |
| Docker Sandbox | 进程级隔离 | 文件系统/网络/资源边界清晰；Work/Judge 可复现 | 启动慢；需镜像治理 |
| 内容寻址对象存储 | 普通文件路径 | 快照/证据不可变；去重；校验简单 | 需清理策略与元数据索引 |

### 2.4 建议代码结构

```
apps/
  api/            # FastAPI 入口、鉴权、SSE
  worker/         # 队列消费者：LLM/IO/解析/传播
  runner/         # Work/Judge 容器编排与快照
  web/            # 最小工作台（React + TS）
packages/
  contracts/      # JSON Schema / Pydantic / TS 生成
  core/           # 状态机、门禁、账本、预算、失败路由
  agents/         # 角色 AgentSpec 与提示版本
  tools/          # 检索、解析、绘图、引用、导出
  rwvh/           # TaskSpec、Work、Judge、rubric、EA
tasks/            # RWJT 任务包（benchmark 与私有任务同格式）
eval/             # 基线、消融、盲评、统计脚本
migrations/       # 数据库迁移
deploy/           # docker compose、镜像、备份
```

**边界规则**：`apps/*` 只能通过 `packages/contracts` 交互；`packages/core` 不 import 任何模型 SDK；`packages/agents` 不直接访问数据库。

## 3. 领域模型与数据架构

### 3.1 聚合与对象

| 聚合 | 对象 | 作用 |
| --- | --- | --- |
| 项目 | `Project P-`、ProblemCard、GenreProfile、ProjectConfig、Member | 研究问题、体裁、预算、成员、政策 |
| 来源 | `SourceRecord SR-`、Document、Span、ReadingState | 文献元数据、版本、许可证、页—段—句锚点、阅读深度 |
| 证据 | `Claim CL-`、EvidenceLink、Conflict、Gap | 三类 claim、支持/反驳边、争议矩阵、gap 卡 |
| 实验 | `DesignCard D-`、`Protocol`、`TaskSpec T-`、`RunPlan RP-`、`Run RUN-`、`Submission SUB-`、`Verdict V-`、`EA-`、`FR-` | 设计、协议、任务、运行、提交、判定、证据产物、失败 |
| 稿件 | `Document DOC-`、Section、Block、Sentence、`Slot`、`Figure F-`、Issue、Revision | 论证与文本结构、六类槽、图包、问题与修订 |
| 治理 | `GateDecision`、Signature、`PropagationRun PROP-`、`ExportBundle EB-`、AIUsageRecord、AuditEvent | 门禁签署、传播事务、导出包、AI 使用留痕、审计事件 |

> 文档层新增 `DOC/SEC/BLK/SENT/SLOT` 细分 ID；`04-` 的 `S-` 继续表示大纲/章节业务产物，二者通过 `section_ref` 关联。状态与 ID 前缀以 `04-` §2.14 与 `07-` §5.1 为准，本文不另立主键体系。

### 3.2 ID、版本与状态

| 对象 | 版本策略 | 状态 |
| --- | --- | --- |
| 产物通用 | 冻结后只出新版本；内容寻址 `sha256` | `draft / frozen / superseded / invalid` |
| Claim | 条件、证据或文本变化即升版 | `draft / supported / refuted / inconclusive / stale / superseded / retracted` |
| Run | 绑定 RunPlan 与镜像 digest；不原地改 | `planned / running / paused / judging / completed / no_valid_submission / failed / cancelled / timed_out` |
| Submission | 快照不可变；重复提交是新 SUB | `created / snapshot_ok / judging / scored / candidate_invalid / incomplete / verifier_error / verifier_timeout / infrastructure_error / submission_error` |
| Slot | 绑定对象变化即重算 | `empty / bound / conflicted / stale / orphan / blocked` |
| Gate | 绑定冻结版本与签署人 | `requested / approved / rejected / expired / overridden` |

### 3.3 存储分工

| 存储 | 存什么 | 权威性 | 备注 |
| --- | --- | --- | --- |
| PostgreSQL | 实体、边、状态、门禁、账本元数据、成本、事件索引 | **唯一事实源** | JSONB 存契约快照；递归 CTE 做传播闭包 |
| 对象存储 | PDF、快照、日志、图、导出包、裁定原始输出 | 产物内容权威 | 内容寻址；不可变桶；生命周期策略 |
| pgvector | 论文/片段检索索引 | 派生，可重建 | 不存 claim 状态；索引重建不影响审计 |
| Redis | 队列、租约、缓存、限流 | **非权威** | 丢失只影响调度，不影响已提交状态 |
| 事件日志 | append-only 业务事件 + outbox | 审计权威 | 与业务表同事务写入 outbox，再投递 |
| OTel 后端 | trace/metrics/logs | 观测，非审计 | 敏感字段脱敏 |

### 3.4 唯一事实源与派生视图

- **事实**：claim 状态、run/verdict、EA 哈希、门禁签署、槽位绑定、传播结果。
- **派生**：稿件视图、图谱可视化、项目看板、成本汇总、检索索引、评审报告。
- 任何派生视图必须可由事实重建；不允许"图上改了但账本没改"。
- 图数据库、向量库、缓存删除后，系统仍能恢复全部审计结论。

### 3.5 产物信封

沿用 `04-` §2.14，并补三个字段：

```json
{
  "schema_version": "artifact-1.1",
  "artifact_id": "EA-021",
  "type": "evidence_artifact",
  "project_id": "P-001",
  "stage": "S5c",
  "version": 1,
  "status": "frozen",
  "inputs": ["RUN-0004", "V-0007"],
  "produced_by": {"role": "judge", "run_id": "RUN-0004"},
  "verified_by": [{"role": "verifier", "gate": "Q1", "decision_id": "GATE-0031"}],
  "created_at": "2026-10-19T10:00:00Z",
  "content_hash": "sha256:...",
  "permissions": {"visibility": "project", "exportable": true},
  "retention": {"class": "audit", "until": "2031-10-19"},
  "depends_on": ["T-RWJT-001", "RP-0002"]
}
```

规则：

1. 没有 `inputs` 的产物只能进"待证区"。
2. 冻结后修改 = 新版本；旧版本保留，标 `superseded`。
3. `content_hash` 覆盖内容与关键元数据；导出与 Judge 都以哈希为准。
4. `permissions` 决定能否进入导出包、能否跨项目复用。
5. schema 变更必须升 `schema_version`，并提供迁移与回放测试。

### 3.6 Claim 与边

| 边 | 方向 | 语义 | 传播 |
| --- | --- | --- | --- |
| `supports` | 证据 → claim | 支持 | 证据失效 → claim 复核 |
| `contradicts` | 证据 → claim | 反驳/冲突 | 冲突升级人工 |
| `derived_from` | claim → claim/图 | 派生 | 上游失效 → 下游 stale |
| `reproduced_by` | result claim → run | 由该确证运行产生 | run 失效 → claim stale |
| `measured_by` | result claim → EA | 数值来自该证据产物 | EA 失效 → claim stale |
| `derived_from_run` | 图/表 → run | 图表由该运行生成 | run 失效 → 图 stale |
| `invalidates` | 新证据/运行 → 旧 claim | 推翻或削弱 | 旧 claim stale |
| `supersedes` | 新版本 → 旧版本 | 版本替代 | 旧版本保留但不可导出 |

**三类 claim 的生命周期**（谁创建、谁准入、谁冻结）：

| claim 类型 | 创建阶段 | 创建者 | 准入条件 | 冻结/失效 |
| --- | --- | --- | --- | --- |
| `literature_claim` | S1 | Reader/Extractor | 身份核验 + 可定位 span + Q0 独立复核 | Q0 冻结；撤稿/更正 → `stale` |
| `result_claim` | S5c | 系统从 `scored` verdict 派生 | `V-` 为 `scored` 且带 `EA(source=rerun)` | 结果包冻结；run 失效 → `stale` |
| `manuscript_claim` | S9 | Claim Composer（Curator + 规则） | 至少一条已准入上游 claim；句有 span；槽位可解析 | Q1 冻结；上游失效 → `stale` |

**claim 通用字段**：`claim_id`、`claim_type`、`text`、`sentence_span`（稿件 claim 必填）、`upstream_claim_ids`、`evidence_ids`、`evidence_level`（`confirmed / exploratory / literature / inferred`）、`strength`（`strong / moderate / weak / unclear`）、`conditions`、`status`（`draft / admitted / frozen / stale / rejected`）、`created_by / admitted_by`、`content_hash`。

**硬规则**：

1. `literature_claim` 不能 `reproduced_by` 运行；`result_claim` 必须同时有 `reproduced_by` 与 `measured_by`；`manuscript_claim` 必须至少有一条上游 claim。
2. 每个事实句最多一条 `manuscript_claim`；S10 只绑定槽位与改写措辞，不得新建 claim。
3. `manuscript_claim` 的 `evidence_level` 不得高于其上游 claim 的最弱等级；把 `literature` 写成 `confirmed` 属于越级，Q1 阻断。`strength` 单独表示支持强度，不得用来替代证据等级。
4. 孤儿 claim、环、跨项目边、重复 `sentence_span` 在 Q0/Q1 报错。

### 3.7 六类槽

| 槽 | 绑定 | 未满足时 |
| --- | --- | --- |
| `E` | 文献 claim + 可定位 span | `blocked`，不得写成事实 |
| `R` | result claim（`confirmed`） | `blocked` |
| `N` | 数字 + `EA(source=rerun)` | `blocked`；禁止模型补数 |
| `F` | 图包 + 数据/代码哈希 | `blocked` |
| `X` | run（`scored`） | `blocked` |
| `C` | 交叉引用目标 | `orphan` |

> 命名冲突提醒：`E` 槽表示"文献证据"，`E 车道`表示"探索运行"；代码中必须分别用 `slot_kind=E` 与 `lane=explore`，禁止混用。

### 3.8 数据生命周期

| 数据 | 保留 | 删除/脱敏 |
| --- | --- | --- |
| 项目事实与门禁 | 项目生命周期 + 5 年 | 用户可申请删除；审计签署记录按机构要求保留 |
| 稿件与证据包 | 同项目 | 导出后仍保留源版本 |
| 运行日志 | 90 天热存，之后归档 | 密钥、token、个人信息脱敏 |
| 模型调用原文 | 默认 90 天 | 可配置不落原文，只留哈希与用量 |
| 私有数据快照 | 运行结束 + 30 天 | 按任务策略销毁；Judge 容器用完即删 |
| 基准任务与 canary | 长期 | 封闭集不公开；canary 只做污染控制 |

## 4. 模型与 Agent 架构

### 4.1 原则：工作流编排，Agent 执行

- 全局状态在账本，不在 Agent 的对话历史里。
- 每个 Agent 只接收一个"上下文包"，产出一个符合 schema 的产物；不能跨阶段自行行动。
- Agent 不能调用门禁、不能改 verdict、不能直接写数据库；只能通过工具与产物服务。
- 同一角色可以用不同模型，但必须记录模型与提示版本；高风险角色必须独立上下文。
- 多 Agent 不做自由聊天；只在 S3 辩论与 S11 批判中做有界多轮，且以结构化产物结束。

### 4.2 AgentSpec 契约

```json
{
  "role": "reader",
  "version": "reader-1.3",
  "model_policy": {"tier": "T3", "fallback": ["T3-alt"], "temperature": 0.1},
  "tools": ["read_artifact", "search_sources", "parse_pdf", "write_artifact"],
  "input_schema": "context-pack-1.0",
  "output_schema": "claim_batch-1.0",
  "max_steps": 12,
  "max_repairs": 2,
  "budget": {"tokens": 60000, "cost_cny": 2.0},
  "permissions": {"read": ["project"], "write": ["claim_draft"], "network": "none"},
  "isolation": {"fresh_context": true, "forbid_roles": ["writer", "judge"]}
}
```

### 4.3 角色清单

| 角色 | 阶段 | 输入 | 输出 | 工具 | 模型档 | 上下文隔离 | 可写范围 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| Planner | S0 | 用户材料、约束 | 问题卡、预算建议 | 读项目、请求人工 | T4 | 是 | 问题卡 |
| Librarian | S1/S7/S9 | 查询、来源配额 | 来源候选、检索回执 | 检索、去重、元数据核验 | T2 | 是 | 来源候选 |
| Reader/Extractor | S1 | PDF、章节、阅读深度 | span、claim 草稿、条件 | 解析、锚点、抽取 | T3 | 是 | claim 草稿 |
| Claim Curator | S1/S9/Q0/Q1 | claim 草稿、span | 准入/驳回、争议矩阵 | 规则 + 独立复核 | T3 + T0 | **独立** | claim 状态（审计范围） |
| Claim Composer | S9 | 已准入 claim、大纲、证据卡 | `manuscript_claim`、槽位绑定草案 | 读 claim/EA、写 claim 草稿 | T2 + T3 | 是 | `manuscript_claim` |
| Ideator | S2/S3 | gap 卡、证据卡 | 20–50 候选 | 检索、生成、聚类 | T4 | 是 | 候选卡 |
| Critic/Debater | S3/S11 | 候选/草稿 | 结构化批评、Elo 理由 | 读证据、对比 | T4 | **独立模型族** | 问题清单 |
| Experiment Architect | S4 | 短名单、资源 | 设计卡、protocol、消融矩阵 | 预算估算、协议模板 | T4 | 是 | 设计卡/protocol |
| Work Agent | S5e/S5c | TaskSpec、工作区 | 代码/数据变更、提交 | shell、编辑器、测试（本地） | T4 编码 | 沙箱内 | 仅工作区 |
| Judge/Verifier | S5c/Q0/Q1/S13 | 快照、私有 rubric | verdict、EA、问题清单 | 重跑、规则、独立检索 | T0 + T4 | **独立** | verdict/审计 |
| Writer/Editor | S8/S10/S12 | 大纲、证据卡 | 段落、槽位草稿、diff | 读 claim、写文档 | T2/T4 | 是 | 稿件草稿 |
| Figure Builder | S6 | EA、图 brief | 图包、caption | 确定性绘图、QA | T2 + T0 | 是 | 图包 |
| Reviewer/Red Team | S14（P1） | 稿件、证据 | 审稿式问题 | 只读证据 | T4 | 独立 | 问题清单 |
| Export Auditor | S16 | 终稿、账本 | 导出检查报告 | 规则、清单 | T0 + T2 | 是 | 审计报告 |

**可兼任规则**：Librarian/Reader/Figure Builder 等低风险角色可由同一模型不同会话兼任；Writer 与 Judge、Work 与 Judge、Critic 与 Writer 不得共享上下文；Judge 不得与被判定对象使用同一会话或同一可写工作区。

### 4.4 三权分离矩阵

| 动作 | 提议 | 执行 | 判定 | 人的位置 |
| --- | --- | --- | --- | --- |
| 文献 claim | Librarian/Reader | Reader 抽取 | Claim Curator + Q0 规则 | 抽样复核 |
| Idea 短名单 | Ideator | Critic 辩论/查新 | 规则 + G1 | G1 签署 |
| 实验设计 | Architect | Work | Judge + G2′ | G2 签署 |
| 结果 claim | 系统从 verdict 派生 | Judge 重跑 | Curator 准入 | 例外裁决 |
| 稿件 claim | Claim Composer | Writer 绑定槽位 | Claim Curator + Q1 | G4 签署 |
| 稿件句子 | Writer | Writer/Editor | Q1 + 独立 Verifier | G4 签署 |
| 导出 | Export Auditor | 导出服务 | G5 硬门 | G5 签核 |

**硬规则**：

1. 生成者不能成为同一产物的最终判定者。
2. 规则能判的，不交给 LLM；LLM 只处理规则无法覆盖的语义支持与体裁判断。
3. Judge 不能读 Work 的对话、草稿、rubric、测试或参考解。
4. 人的"拒绝"必须写理由；"通过"必须绑定产物版本与哈希。
5. 任何门禁都不能被 Agent 以"任务紧急"为由绕过；只能由有权限的人记录 override 并承担理由。

### 4.5 模型网关与路由

| 档 | 用途 | 典型角色 | 要求 |
| --- | --- | --- | --- |
| T0 规则 | 哈希、schema、引用存在性、数字比对、槽位解析 | Q0/Q1/Export | 确定性、可单测 |
| T1 小模型 | 分类、去重、格式修复、初筛 | Librarian | 低成本、可批量 |
| T2 通用 | 段落起草、摘要、图注、常规整理 | Writer、Figure | 稳定、可缓存 |
| T3 长上下文 | 论文阅读、span 抽取、跨节一致性 | Reader、Curator | 长输入、结构化输出 |
| T4 强推理 | 规划、设计、辩论、判定、复杂修订 | Planner、Architect、Judge | 独立上下文、预算上限 |

**网关规则**：

- 每次调用记录：`model_id`、`provider`、`prompt_version`、`temperature`、`seed`（如支持）、输入/输出 token、成本、缓存命中、trace_id。
- 模型与提示版本在项目启动时冻结进 manifest；运行中不静默升级。
- 升级模型/提示前必须跑离线回放集，比较质量、成本、失败分布；升级后旧项目仍可重放旧版本。
- 高风险阶段（Judge、Q1、导出）不允许"因成本自动降级"；降级必须显式记录并重新判定。
- v1 不做微调；缓存键 = 内容哈希 + prompt 版本 + 模型 ID + 关键参数。

### 4.6 上下文构建

**上下文包**（ContextPack）只包含：

```json
{
  "objective": "本节要完成的论证义务",
  "stage": "S10",
  "constraints": ["体裁", "字数", "禁用未确认 claim", "引用格式"],
  "allowed_artifacts": ["OUTLINE-003", "CL-0107", "EA-021", "F-003"],
  "evidence_cards": ["..."],
  "untrusted_sources": ["..."],
  "output_schema": "section_draft-1.0",
  "budget": {"tokens": 30000, "cost_cny": 1.5}
}
```

规则：

- 不放完整对话历史；需要历史时，从账本取结构化摘要。
- 不跨项目检索；不把其他项目的 claim 放入上下文。
- 外部文献内容标记为 `untrusted_sources`，只作为数据，不作为指令。
- 长文用分层摘要（章节摘要、论证图、claim 卡），不把 2 万字全文反复塞入。
- 超出预算时先裁"背景材料"，不裁"证据卡与约束"。

### 4.7 工具与权限

| 工具 | 能力 | 允许角色 | 边界 |
| --- | --- | --- | --- |
| `search_sources` | 多源检索、去重、元数据 | Librarian、Reader | 只读；来源配额；不抓未授权库 |
| `parse_pdf` | 版面、章节、引用、图表标题、span | Reader | 只读；解析结果落对象存储 |
| `read_artifact` | 读冻结产物 | 全部 | 只读；按项目权限过滤 |
| `write_artifact` | 写本角色允许的产物 | 按 AgentSpec | schema 校验；不能写 verdict/claim 状态 |
| `execute_code` | 沙箱内运行代码 | Work | 仅工作区；无宿主挂载；资源/网络策略 |
| `run_tests` | 私有测试 | Judge | 只读测试；输出只回聚合结果 |
| `plot` | 从 EA 数据生成图 | Figure Builder | 只能用绑定数据；输出哈希 |
| `verify_citation` | 存在性/字段/撤稿/上下文 | Curator、Q1 | 三态；不可伪造"已核验" |
| `compile_export` | 模板渲染、GB/T 7714、打包 | Export Auditor | 只读终稿与账本；fail-closed |
| `request_human` | 进入人工收件箱 | 全部 | 必须带问题、证据、建议与截止时间 |

### 4.8 记忆：四个结构化存储，不做"记忆汤"

| 记忆 | 内容 | 写入条件 | 读取者 |
| --- | --- | --- | --- |
| 项目记忆 | 决策、门禁、协议、预算、体裁 | 人签署或系统状态变更 | 全项目 |
| 证据记忆 | claim、span、冲突、gap、失效状态 | 通过准入/Q0 | 全项目 |
| 运行记忆 | run、verdict、EA、失败记录 | 运行结束/判定完成 | 判定、写作、传播 |
| 经验记忆 | 已准入的提示、模板、技能、反例 | 小样本测试通过 + 人工批准 | 后续项目（按域） |

**禁止**：把 Agent 的自由文本"反思"直接写入长期记忆；把未验证的结论写入证据记忆；把失败教训写成不可检索的散文。失败记忆必须是结构化记录（阶段、类别、可归因对象、重试结果）。

### 4.9 Agent 循环与预算

- 默认循环：`plan → act → observe → validate schema → produce artifact`；最多 `max_steps`，超过即停止并报告未完成。
- 结构化输出失败最多修复 2 次；仍失败则升级人工，不无限重试。
- 缺证据时停止并产出 `evidence_gap`，不得"先写后补"。
- Work Agent 例外：持久工作区、最长 2 小时、最多 5 次提交；每次提交都生成新 SUB 与快照。
- 所有 Agent 都有硬预算；预算耗尽输出"未完成清单"，不得静默降低质量。

### 4.10 为什么不用"多 Agent 自治社会"

| 问题 | 后果 | 本文选择 |
| --- | --- | --- |
| 角色自由对话 | 上下文膨胀、成本不可控、不可复现 | 产物中介的固定交接 |
| Agent 自行决定下一步 | 越权、跳过门禁、无法审计 | 顶层状态机决定阶段 |
| 辩论无界 | 趋同或循环、成本爆炸 | 只在 S3/S11 做有界轮次 |
| 记忆自由生长 | 错误扩散、跨项目污染 | 四类结构化记忆 + 准入 |
| 判定与生成同源 | 自己批自己 | 独立模型族 + 独立上下文 + 规则优先 |

### 4.11 模型/提示变更治理

1. 任何提示或模型变更都产生新版本，不覆盖旧版本。
2. 变更必须跑回放集：至少 20 个历史产物，比较 schema 合法率、claim 支持率、成本、失败分类。
3. Judge/导出相关变更需要双人复核；变更记录进入项目 manifest。
4. 已冻结项目重放时，默认锁定原版本；需要升级时创建新 Run，不修改旧 verdict。
5. 供应商弃用模型时，保留旧调用记录与替换评估，不伪造"同一模型"。

## 5. 编排设计

### 5.1 运行时对象

| 对象 | 含义 | 关键字段 |
| --- | --- | --- |
| `WorkflowRun` | 一个项目的一次完整流程 | `workflow_version`、`current_stage`、`status`、`budget`、`manifest` |
| `StageRun` | 一个业务阶段的一次执行 | `stage`、`attempt`、`inputs`、`outputs`、`gate_id` |
| `StepRun` | 阶段内的一个可重试步骤 | `step_key`、`status`、`attempt`、`lease`、`error` |
| `Attempt` | 一次具体调用/执行 | `model_run_id` / `run_id`、耗时、成本、错误 |
| `GateDecision` | 一次门禁判定 | `gate`、`artifact_versions`、`decision`、`signer`、`reason` |
| `OutboxEvent` | 与业务事务同提交的事件 | `type`、`payload`、`published_at` |

### 5.2 执行语义

- **状态机是代码，不是提示**：阶段转移表版本化；新增转移需代码评审与测试。
- **每步提交**：StepRun 完成后写产物、状态、事件（同一事务）；事件通过 outbox 异步投递。
- **至少一次投递、恰好一次效果**：消费者按 `event_id` 幂等；外部副作用用内容哈希去重。
- **租约与恢复**：worker 领取 StepRun 后持有租约；崩溃后租约过期，其他 worker 可重领；已提交产物不重算。
- **长任务**：X0–X7 以 `RUN-` 为中心轮询，不把一个 2 小时容器塞进一个 HTTP 请求。
- **取消**：用户取消 = 停止新步骤 + 终止沙箱 + 保留已提交证据；不删除审计记录。

### 5.3 门禁

| 门 | 时点 | 类型 | 检查 | 冻结 | 不通过 |
| --- | --- | --- | --- | --- | --- |
| G0 | S0 后 | 人 | 问题、材料、体裁、伦理与资源边界 | 问题卡 | 回 S0 |
| Q0 | S1 后 | 自动 + 抽样人审 | 来源覆盖、身份核验、span、争议矩阵、gap 可检验 | 文献快照 | 回检索/抽取 |
| G1 | S3 后 | 人 | 候选数量、机制簇、证据边、查新、可证伪条件 | 短名单 | 回 S2/S3 |
| G2 | S4 后 | 人 | 变量、对照、消融、样本量、指标、停止规则、预算 | 设计卡/protocol | 改设计，禁止执行 |
| G2′ | X0 后 | 自动；高风险转人 | TaskSpec 字段、路径、网络、超时、测试引用、rubric digest、oracle 可用 | RunPlan | 任务不可运行 |
| G3 | S8 后 | 人 | 章节义务、论证链、证据需求、图计划、篇幅 | 大纲 + 图计划 | 重规划 |
| Q1 | S13 | 自动 + 独立复核 | 引用、数字、图、跨节一致、槽位、`manuscript_claim` 覆盖率与越级、stale/orphan、结构 | 核验报告 | 回 S12 |
| G4 | S15 | 人 | 科学价值、结论边界、责任、署名、AI 使用声明 | 终稿 | 退回 |
| G5 | S16 前 | 自动 + 人签核 | 导出硬门 8 条、模板、GB/T 7714、证据包 | 导出包 | 阻止导出 |

**说明**：G2′ 不是新的人工门，而是 G2 冻结后的运行准入检查；只有高风险任务（GPU、外部数据、敏感领域）升级为人工确认。所有门禁的判定记录不可被 Agent 修改。

**人工工作量 `[估算]`**：G0 30 分钟、G1 60 分钟、G2 60 分钟、G3 45 分钟、G4 90 分钟、G5 15 分钟；加上例外处理，一篇稿件的固定人工约 5 小时。系统的目标不是"无人"，而是把人的时间集中在科学判断上。

### 5.4 人工收件箱

- 触发：门禁、预算耗尽、政策违规、连续失败、证据冲突、传播需要裁决。
- 每条任务必须带：问题、影响范围、证据、建议动作、截止时间、负责人。
- 人的动作：批准、拒绝、要求补证据、改设计、终止、升级。
- 超时：提醒 + 升级；**不自动批准**。默认暂停，不用"默认通过"换取吞吐。
- 所有动作写 `Signature`；支持委托，但受托人必须有权且记录原因。

### 5.5 调度与并发

| 队列 | 内容 | 并发策略 | 优先级 |
| --- | --- | --- | --- |
| `interactive` | 门禁、用户查询、取消 | 立即 | 最高 |
| `judge` | 确证判定 | **独占**，不与 Work 争 GPU | 高 |
| `llm` | Agent 调用 | 按项目配额与全局 token 限流 | 中高 |
| `io` | 检索、解析、下载 | 8–16 并发 | 中 |
| `sandbox_cpu` | Work CPU 任务 | 2 个运行 | 中 |
| `sandbox_gpu` | Work GPU（P1） | 1 卡；release-all | 中 |
| `maintenance` | 传播、重建索引、归档 | 低峰；可抢占 | 低 |

- 项目内阶段默认串行；同阶段内可 fan-out（检索 8、解析 4、候选生成 20–50、章节最多 3 个并行）。
- 全局最多 2 个确证运行（`07-` §6.5）；Judge 队列独占，保证判定不受 Work 资源干扰。
- 队列积压超过阈值时拒绝新项目启动并给出预计等待；不静默降低 Judge 预算。
- 公平性：按项目轮转，避免一个大项目饿死其他项目；单项目设每日预算。

### 5.6 预算与成本账本

- 三层预算：项目 → 阶段 → 单次运行/单次 Agent 调用。
- 调用前**预留**，结束后**结算**；并发调用不能超卖同一预算。
- 超预算：停止新调用，输出未完成清单与已产生证据；不得"先跑完再解释"。
- 成本按项目、阶段、角色、模型、run 归集；缓存节省单独记账。
- 成本异常（单阶段超过预算 2 倍）触发告警与人工检查，常见原因是循环、重复检索、上下文膨胀。
- 论文轨道的演示成本目标：单篇 2 万字 ≤ 30 元；RWJT 单任务 ≤ 50 元。两者都是 `[设计目标]`。

### 5.7 失败模型与路由

| 类别 | 例子 | 重试 | 上限 | 路由 | 计分影响 |
| --- | --- | --- | --- | --- | --- |
| `input_incomplete` | 缺材料、缺体裁、缺预算 | 否 | — | 回门禁/人工 | 不计分 |
| `schema_invalid` | 输出不符合 schema | 修复提示 | 2 次 | 再失败转人工 | 不计分 |
| `evidence_missing` | 无 span、无 claim 支持 | 否 | — | 回 S1/S9，或降级为限制 | 不生成 claim |
| `tool_error` | 检索超时、解析失败 | 指数退避 | 3 次 | 换工具/降级/人工 | 不计分 |
| `model_error` | 供应商 5xx、限流 | 退避 + 备用模型 | 2 次 | 人工 | 不计分 |
| `model_refusal` | 合规拒绝、输出为空 | 换模型一次 | 1 次 | 人工 | 不计分 |
| `citation_unverifiable` | 找不到原文、字段不符 | 否 | — | 删除/降级 claim | 不得进入稿件 |
| `candidate_invalid` | 候选代码错、缺交付物、发散 | Work 循环 | 5 次提交 | 回 S5c | **不记 0 分**，记候选失败 |
| `verifier_error` | 测试脚本错、rubric 解析错 | 重判一次 | 1 次 | 修 Judge 后重跑 | 不计分 |
| `verifier_timeout` | 判定超时 | 先归因 | 1 次 | 候选导致→candidate_invalid；否则 infra | 按归因 |
| `infrastructure_error` | 镜像、GPU、网络、调度 | 退避重跑 | 3 次 | 告警 + 人工 | **不计分** |
| `gate_rejected` | 人拒绝 | 否 | — | 按门禁回退 | 不计分 |
| `budget_exhausted` | 超预算 | 否 | — | 停止 + 未完成清单 | 不计分 |
| `policy_violation` | 越权、外网、数据泄漏 | 否 | — | 硬停 + 安全审查 | 不计分，阻断导出 |
| `human_timeout` | 门禁超时 | 提醒 | — | 升级；保持暂停 | 不计分 |

**归因原则**：候选的错记候选，评测器的错记 verifier，环境的错记 infrastructure；三类不能混。只有 `scored` 进入 best-of-N 与 claim 准入。

### 5.8 循环护栏

| 循环 | 上限 | 超过后 |
| --- | --- | --- |
| S2 候选生成 | 50 条 | 停止生成，进入聚类 |
| S3 辩论/反思 | 3 轮 | 锁定 Elo，交 G1 |
| S11–S12 修订 | 2 轮 | 剩余 P0 问题交人工；不得声称完成 |

| 章节重生成 | 2 次 | 保留最佳版本 + 问题清单 |

### 5.9 幂等与恢复

- `step_key = hash(stage + input_hashes + config_version)`；重试不产生新逻辑步骤。
- 产物写入对象存储使用内容哈希；同一内容不重复存。
- 数据库事务 + outbox：状态变更与事件同生共死；事件重复投递由消费者去重。
- 长任务用 `RUN-` 轮询：worker 崩溃不会丢 run；重新接管后先读状态再决定是否继续。
- 恢复测试是 A0 的硬门：杀死 worker 后，流程能从最近提交点继续，且不重复计费、不重复提交。

### 5.10 事件与可观测性

**核心事件**：

```
project.created            stage.entered             artifact.created
artifact.frozen            artifact.superseded       gate.requested
gate.approved              gate.rejected             run.planned
run.started                run.submitted             run.judged
claim.created              claim.admitted            claim.staled
propagation.started        propagation.completed     export.checked
export.blocked             export.released           budget.exhausted
policy.violated            human.escalated
```

每个事件带 `event_id / type / project_id / workflow_run_id / stage / artifact_id / occurred_at / payload / trace_id / schema_version`。指标至少包括：阶段耗时、门禁等待、人工干预次数、失败分类、重试率、缓存命中、token/成本、stale 数、导出阻断原因、run 有效率、Judge 泄漏事件数。

### 5.11 版本轴与失效传播

| 版本轴 | 变化会触发什么 |
| --- | --- |
| 来源版本 | 新版本/撤稿/更正 → 文献 claim 复核 → 句子 blocked |
| 协议 | 主指标/停止规则变化 → 旧 run superseded → 结果 claim stale |
| 运行 | 重跑/判定变化 → 结果 claim、图、摘要句 |
| TaskSpec/rubric | 任务或评分变化 → 旧 verdict 不可比；新 run |
| 模型/提示 | 默认不使科学结论失效；影响文本与解析时需复核 |
| 体裁模板 | 结构变化 → 大纲与导出格式重检 |

**传播事务**：

1. 事件触发（新来源、run 失效、协议变更、claim 手工修改、图表数据变化）。
2. 计算闭包（递归 CTE）：受影响的 claim、句、图、表、导出包。
3. 在一个数据库事务中写 `PropagationRun` + 所有 `stale` 标记；不允许部分更新。
4. 为每个受影响对象生成处置：`rerun`（需新证据）、`rewrite`（结论仍成立，文字需改）、`review`（影响不确定，人工）。
5. 入队执行；阻塞相关句子的导出。
6. 修复后重跑 Q1；只有全部解除才允许导出。
7. 保留旧版本与传播记录；不删除、不原地覆盖。

## 6. 五类流程的编排

> 五类流程共用同一账本、门禁与 runner；区别在触发方式、角色与并发。基准模式可跳过 F1/F2，直接使用任务包提供的冻结材料；产品模式按 F1→F4 顺序执行，F5 异步运行。

### 6.1 F1 文献与证据流程（S1，Q0）

| 步 | 动作 | 角色 | 产物 | 失败 |
| --- | --- | --- | --- | --- |
| 1 | 明确范围、语言、时间窗、来源配额 | Planner/Librarian | 检索计划 | 范围过宽 → 回 G0 |
| 2 | 多源检索、去重、身份核验 | Librarian | 来源候选 | 来源不足 → 扩充查询/人工 |
| 3 | 解析版面、章节、引用、图表标题 | Reader | Document/Span | 解析失败 → OCR/排除并记录 |
| 4 | 阅读深度路由 D0–D4 | Librarian/Reader | 阅读状态 | 无权限 → 排除 |
| 5 | 抽取 claim、条件、span | Reader | claim 草稿 | 无 span → 不入库 |
| 6 | 跨源冲突与争议矩阵 | Curator | 冲突边 | 冲突未决 → 标 `unresolved` |
| 7 | gap 卡与可检验性 | Curator | gap 卡 | 不可检验 → 删除 |
| 8 | Q0 审计（规则 + 独立复核 + 抽样） | Curator/Verifier | Q0 报告 | 失败 → 回 2/5 |
| 9 | 冻结文献快照 | 系统 | 快照哈希 | — |

**并发**：检索 8、解析 4、抽取 4；单项目默认上限 200 篇语料，Q0 抽样不少于 20%。论文轨道的 RWJT 切片可用 50 篇 Q0 子集，不等待全量语料。**禁止**：未核验元数据入库、无 span 的 claim、把摘要当全文证据。

| 步 | 动作 | 角色 | 产物 |
| --- | --- | --- | --- |

| 4 | oracle/nop 校准（任务构建期） | 任务作者/Judge | 校准报告 | oracle < 0.90 或 nop 过高 → 修任务 |
| 5 | E 车道试跑（可选） | Work | 探索记录 | 不进 Judge；可反复 |
| 6 | C 车道 Work 启动 | Work | 工作区 | 启动失败 → infra |
| 7 | 研究循环、提交、快照 | Work | `SUB-` | 非法提交 → candidate_invalid |
| 8 | 干净 Judge 重跑、M/E/V 评分 | Judge | `V-`/`EA-`/`FR-` | 按 §5.7 |
| 9 | 结果 claim 准入 | L4 自动 + Curator | `CL-` | 非 scored → 拒绝 |
| 10 | best-of-N 选择与冻结 | 系统 | 最终 run + 证据包 | 无有效提交 → no_valid_submission |

**v1 边界**：C 车道只接受**人工冻结的 TaskSpec**——任务作者提供 environment、tests、rubric 与交付要求，经 oracle/nop 校准后冻结。设计卡 → TaskSpec 自动编译是 P1 研究项，不进入 v1；它需要额外验证环境可复现、rubric 不泄漏、测试不过拟合。

**S5e 回环**：探索结果若要求改变变量、对照、指标或停止规则，必须新建设计卡版本并重签 G2；旧 protocol、TaskSpec 与 run 标 `superseded`，不得在旧 G2 下继续 C 车道。

**预算与并发**：Work ≤ 2 小时、Judge ≤ 30 分钟、5 次提交、单任务 ≤ 50 元、同时 2 个确证运行；Judge 独占资源。**禁止**：探索 run 进入 claim；修改 rubric/测试；把 Work 自报日志当 `EA`；把 infra 失败记 0 分。

### 6.4 F4 写作与保证流程（S6–S16，G3/Q1/G4/G5）

| 步 | 动作 | 角色 | 产物 | 失败 |
| --- | --- | --- | --- | --- |
| 1 | 冻结证据快照（claims + EA + 图数据） | 系统 | 证据快照 | stale → 先传播 |
| 2 | S6a：按已有 claim 生成候选数据图（不绑定 claim） | Figure Builder | 候选图包 | 数据不一致 → 重绘/修数据 |
| 3 | 论证图（问题→gap→方法→证据→结论） | Architect | 论证图 | 孤立/环/范围膨胀 → 重规划 |
| 4 | 体裁大纲 + 图计划（哪些图支撑哪些 claim） | Architect/Writer | 大纲 + 图计划 | G3；不完整 → 重规划 |
| 5 | S6b：按图计划定稿图、caption，绑定 claim/run | Figure Builder | 图包 | 无 claim/run 绑定 → 不生成 |
| 6 | S9：Claim Composer 建 `manuscript_claim`，按节组装槽位 | Curator/Writer | `manuscript_claim` + 证据卡 + 槽位 | 缺证据 → 回 S1/S5c |
| 7 | 分节起草（最多 3 节并行；只绑定，不新建 claim） | Writer | 草稿 | 槽位违规 → 重写该节 |
| 8 | 合并与全局一致性（数字、术语、时态） | Writer/Editor | 合并稿 | 冲突 → 以账本为准 |
| 9 | 多角色批判（证据/方法/结构/语言） | Critic | 问题清单 | 意见不可定位 → 退回 |
| 10 | 定向修订 ≤2 轮，保留 diff 与回归检查 | Writer/Editor | 修订稿 | 新错误率 >5% → 回滚该轮 |
| 11 | Q1：引用、数字、图、槽位、`manuscript_claim` 覆盖率与越级、stale、结构 | Judge/Verifier + 规则 | 核验报告 | 失败 → 回 S12 |
| 12 | 评审模拟（P1，只用已有证据） | Reviewer | 审稿问题 | 不生成虚假意见 |
| 13 | G4 人工终审 | 人 | 终稿 | 退回 |
| 14 | G5 导出硬门 + 打包 | Export Auditor | `EB-` | 任一硬门失败 → 阻断 |

**写作阶段的硬约束**：Writer 只能使用已冻结的证据卡；不得生成新数字；不得把探索结果写成结果；不得引用未核验来源；章节并行时必须共享同一证据快照，合并时以账本数字为准。

**claim 创建边界**：S1 只建 `literature_claim`，S5c 只建 `result_claim`，S9 只建 `manuscript_claim`；S10 不新建 claim，只绑定槽位与改写措辞。Q1 要求事实句 claim 覆盖率 100%、越级 0、重复 `sentence_span` 0、孤儿 `manuscript_claim` 0。

### 6.5 F5 变更与传播流程（W2）

| 步 | 动作 | 角色 | 产物 |
| --- | --- | --- | --- |
| 1 | 监听/接收变更事件 | 系统 | 事件 |
| 2 | 计算受影响闭包（claim/句/图/表/导出） | 传播引擎 | `PROP-` |
| 3 | 分类处置：rerun / rewrite / review | 规则 + 人工 | 处置队列 |
| 4 | 执行重跑或重写；必要时回到 S4/S5c | Work/Writer | 新版本 |
| 5 | 重跑 Q1，解除 stale | Verifier | 新核验报告 |
| 6 | 更新导出包；保留旧版本与传播记录 | 系统 | 新 `EB-` |

**处置定义**：

- `rerun`：结论依赖新数据/新运行，必须走 C 车道；旧 run 标 `superseded`。
- `rewrite`：结论不变，但文字、数字或引用需要更新；只改受影响句。
- `review`：影响不确定（跨领域、弱依赖、样本边界），交人判断；不得自动放行。

**传播指标**：受影响 claim/句召回 ≥85%、误报 ≤20%、三类处置准确率 ≥80%（C3）；达不到就缩到"结果变更→摘要句"子场景，如实报告。

### 6.6 一次 RWJT 的端到端时序

| 步 | 谁 | 做什么 | 产物/边界 |
| --- | --- | --- | --- |
| 1 | 任务作者 | 提交 TaskSpec、代码/数据版本、冻结协议、交付要求、私有 rubric digest | Work 不可见 rubric/tests |
| 2 | 编排器 | 编译环境、资源、网络、超时；G2′ 准入 | `RP-`；不通过则拒绝启动 |
| 3 | Work Agent | 读 instruction，检查仓库/数据，复现实验，写中文小节 | 仅工作区可写 |
| 4 | Work Agent | 提交：暂停、快照、manifest | `SUB-`；缺交付物 → incomplete |
| 5 | Judge | 干净镜像、无网重跑、M/E/V + W 检查 | `V-` + `EA-`；只认重跑产物 |
| 6 | 系统 | 若 `scored`，创建结果 claim；否则写失败记录 | `CL-`/`FR-`；infra 不记 0 |
| 7 | Claim Composer + Writer | 先用已准入的 `literature_claim` 或 `confirmed` 的 `result_claim` 建 `manuscript_claim`，再组装中文段落与槽位 | 不得读 Work 日志编数；S10 只绑定，不新建 claim |
| 8 | Q1/导出 | 槽位、数字、引用、图、体裁、`manuscript_claim` 覆盖率与越级、stale | 任一失败 → 阻断 |
| 9 | 评分 | R、W、J 分开报告；记录有效/无效提交、成本、失败分布 | 不把 J 当论文质量 |
| 10 | 打包 | 稿件、claim 图、run 账本、verdict、EA、AI 使用记录、manifest | `EB-` |

**关键边界**：第 3 步 Work 可以内部试跑，但只有第 5 步 Judge 重跑产生的 EA 能进入第 6 步；第 7 步 Writer 看不到第 3 步的原始对话与日志，只能看第 6 步的 `result_claim` 与 EA，以及 S1 已准入的 `literature_claim`。这是 RWJT 与"复现 + 写作拼接"的结构差异。

### 6.7 跨流程规则

1. 只有冻结产物能跨阶段；工作区、对话、临时日志不能跨。
2. 任何流程都不能绕过 L4 直接写稿件数字。
3. F5 可异步触发任何流程，但不得静默修改已导出包；必须生成新版本。
4. 基准模式跳过 F1/F2，使用任务包材料；产品模式必须保留 F1 的证据快照，否则 Q1 无法审计。
5. 同一项目同一时刻只允许一个主流程；F5 维护流程可并行，但写操作串行化。

### 6.8 回退矩阵：写作级、证据级、研究级

| 层级 | 触发 | 回退 | 必须失效/重签 | 不得做 |
| --- | --- | --- | --- | --- |
| 写作级 | 结构、表达、局部引用不支持 | S11/S12 | 受影响句标 `stale`；Q1 重跑 | 为迁就文字而改 claim 等级 |
| 证据级 | 数字不一致、run 失效、槽位无法解析 | S5c/S6b/S9 | 旧 run/protocol/TaskSpec 标 `superseded`；受影响 `result_claim`/`manuscript_claim` 标 `stale`；改 protocol 则重过 G2，否则重过 G2′ | 在旧 G2 下重跑；手工改 EA |
| 研究级 | 贡献不成立、核心 claim 被推翻、S14 判定需补实验 | S2/S3 或 S4 | 受影响 claim/句/图触发 F5 传播；新设计卡重过 G1/G2 | 只改摘要或措辞；保留已失效 claim 继续导出 |

**规则**：

1. 回退必须保留旧版本、旧门禁签署与回退理由；不删除、不原地覆盖。
2. 写作级不得改 claim；证据级不得改结论方向；研究级不得复用旧短名单直接过关。
3. 同一项目最多 2 次研究级回退，超出转人工决策（终止、降级或换题），防止无限重规划。
4. S5e→S4、S14→S2/S4、F5 `rerun` 三类回退都按本矩阵执行，不能只改阶段指针。

### 7.2 错误信封

```json
{
  "code": "RUN_INFRASTRUCTURE_ERROR",
  "category": "infrastructure",
  "retryable": true,
  "user_message": "运行环境启动失败，已自动重试；本次不计分。",
  "detail_ref": "FR-0042",
  "trace_id": "..."
}
```

规则：面向用户的消息不暴露堆栈、密钥、rubric；详细原因写 `FailureRecord` 与日志；`retryable` 由类别决定，不由 Agent 决定。

### 7.3 契约治理

- `packages/contracts` 是唯一 schema 源；Pydantic/TS 客户端自动生成。
- 所有 schema 带版本；破坏性变更需迁移脚本 + 回放测试。
- 每个阶段有契约测试：合法输入通过、缺字段失败、越权写入失败、冻结后修改失败。
- 状态机转移表有单测：非法转移必须报错；门禁未签署不得进入下一阶段。
- 关键安全测试：Work 读 tests 失败、Judge 联网失败、infra 失败不记 0、篡改数字导致导出阻断。
- 不允许"运行时动态放宽 schema"来让流程通过。

## 8. 部署、安全与运维

### 8.1 环境

| 环境 | 数据 | 模型 | 网络 | 用途 |
| --- | --- | --- | --- | --- |
| `dev` | 合成/公开样例 | 可 mock | 可选 | 开发与单测 |
| `ci` | 固定 fixture | mock | 无 | 契约、状态机、导出硬门 |
| `benchmark` | 公开任务 + 封闭集 | 正式 | 受控；Judge 无网 | W3 评测与基线 |
| `product-private` | 用户私有 | 私有端点/受控 API | 最小出网 | 真实项目 |
| `archive` | 导出包与账本 | — | 无 | 审计与复现 |

### 8.2 隔离与网络

- Work：可写工作区、只读数据挂载、默认 `no-network`；需要模型时只允许 pinned 端点；禁止宿主目录、Docker socket、云元数据。
- Judge：一次性干净镜像、只读快照、私有 tests/rubric、默认无网、无 Work 凭据、用完销毁。
- 项目隔离：数据库行级权限 + 对象存储前缀；跨项目查询默认拒绝。
- 基准/产品隔离：不同数据库与对象存储桶；产品数据不进入 benchmark 日志。
- 密钥：只注入网关与 runner 的短期凭据；不写入工作区、不进入 prompt、不落日志。

### 8.3 供应链与许可证

- 任务镜像固定 digest；依赖锁定；生成轻量 SBOM。
- 复用开源组件逐项核对许可证；在交付物中注明来源与版本。
- 禁止在 Judge 中 `pip install` 未固定版本；任务自带依赖必须预构建。
- canary 只用于污染控制，不用于规避 AIGC 检测。

### 8.4 提示注入与来源信任

- 检索文本、PDF、代码注释、网页内容一律视为不可信数据，不作为指令。
- 上下文包把 `untrusted_sources` 与系统指令分区；工具白名单；禁止执行来源中的脚本。
- 输出必须过 schema；涉及工具调用的参数做白名单校验。
- 建立提示注入测试集：恶意文献、伪造引用、诱导越权、诱导泄密；每次发布回归。
- Writer/Judge 不直接浏览网页；检索经 Librarian 与引用核验。

### 8.5 日志、脱敏与披露

- 结构化日志；密钥、token、个人信息、私有数据路径自动脱敏。
- 模型调用记录保留版本、用量、成本与哈希；原文保留期限可配置。
- 导出包附 AI 使用记录：使用了哪些角色、模型、阶段、人工修改点；不披露内部 rubric 与私有数据。
- 任何对外材料不得把模拟评审写成真实同行评审。

### 8.6 备份与恢复

- 每日 Postgres 全量 + WAL 归档；对象存储版本化；导出包双份。
- v1 RPO 24 小时、RTO 4 小时；恢复演练每季度一次。
- 恢复后先跑一致性检查：产物哈希、claim 边、verdict 引用、未完成传播。
- 不删除已签署门禁与 verdict；只做 `superseded`。

### 8.7 运行手册（最小集）

| 事件 | 立即动作 | 后续 |
| --- | --- | --- |
| Judge 泄漏（Work 读到测试/rubric） | 停止 judge 队列；隔离相关 run；作废受影响 verdict | 修镜像/权限；重跑；记录事件 |
| 误记 0 分 | 将 verdict 标 `superseded`；不改历史 | 重判/重跑；通知用户 |
| 成本异常 | 暂停项目；检查循环与上下文 | 调预算/修提示；出报告 |
| 数据泄漏 | 撤销密钥；隔离环境；保留证据 | 通知与合规流程；修策略 |
| 导出包缺字段 | 阻断导出；定位产物版本 | 重生成；补测试 |
| 传播误报过多 | 暂停自动 rewrite；转人工 review | 调整规则；评估召回/误报 |

### 8.8 合规

- A3：人保留科学决策、实验安全、署名与最终责任。
- 不代写未披露、不伪造数据/引用、不规避 AIGC 检测、不自动投稿、不伪造评审。
- 生成内容是草稿；导出必须有人工终审与 AI 使用声明。
- 机构政策作为可配置模板，记录来源与生效日期，不硬编码单一机构规则。

## 9. 与轨道、工作包和构建顺序的对应

### 9.1 能力档

| 档 | 组件 | 支撑 | 说明 |
| --- | --- | --- | --- |
| **K0 内核** | 产物信封、ID/版本、事件、状态机、门禁、预算、模型网关、最小存储 | 全部轨道 | W1 的 M0 12 人周覆盖最小版；RBAC/多用户不在论文轨道 |
| **K1 证据** | 解析、检索、claim 卡、证据图、争议矩阵、Q0、阅读路由 | W1/W2/W3 | L1/L2/L3 的主体 |
| **K2 判定** | RWVH、TaskSpec、Work/Judge、rubric、EA、失败归因、导出硬门 | W1 | H1–H5；RWJT 的核心 |
| **K3 写作** | 体裁契约、论证骨架、大纲、槽位、逐节生成、Q1、最小传播标记 | W1 | D1/D4-lite；中文核刊单体裁 |
| **K4 传播** | 完整边语义、闭包、三类处置、50 个变更场景 | W2 | 与 K3 的最小标记分开 |
| **K5 产品** | S2/S3 完整收敛、S11/S14、完整工作台、多用户、图谱交互 | 产品轨道 | 论文轨道可不做 |
| **K6 扩展** | 原生科学环境、GPU 集群、技能准入（FR-11）、claim 条件化复现（P1 研究） | P1/P2 | 不进入首个论文闭环 |

### 9.2 论文轨道的最小架构

**保留**：K0 + K1（50 篇 Q0 子集）+ K2 + K3。
**跳过**：S2/S3 完整收敛（RWJT 的任务由任务包给定研究问题）、S14 评审模拟、完整工作台、多用户、原生环境。
**前端只做三页**：门禁签署、槽位与证据查看、运行/审计报告。
**验收**：一个 T4 任务从 TaskSpec 到导出包端到端跑通；篡改任一数字导致导出阻断；R/W/J 可复跑；Work 读不到 tests。

### 9.3 产品轨道的最小增量

在论文轨道之上增加：项目与团队管理、完整证据图谱交互、Idea 收敛、评审模拟、返修规划、模板市场、批量审计、权限与归档。仍不引入微服务；先把 K5 做成同一单体中的模块。

### 9.4 团队映射

| 角色 | 论文轨道（5–6 人） | 产品轨道（9+1） |
| --- | --- | --- |
| 架构/内核 | 1 人：K0、契约、状态机、门禁、预算 | 1 人 + 前端 1 人 |
| 执行/判定 | 1 人：K2、RWVH、沙箱、Judge、EA | 1 人 + 评测 1 人 |
| 证据/NLP | 1 人：K1、解析、claim、Q0 | 2 人（L1/L2） |
| 图谱/传播 | 0.5 人：K4 与 L3 | 1 人（R1） |
| 写作/体裁 | 1 人：K3、槽位、Q1 | 2 人（G3/G4） |
| 评测/benchmark | 1 人：W3、任务包、κ、盲评 | 1 人（E1/E2） |
| 集成/演示 | 0.5 人：CLI、三页工作台、导出 | 1 人（I1） |
| 顾问 | 0.5：科学判断、伦理、盲评 | 1：领域与机构规则 |

> 论文轨道的 5–6 人是 3.5–4.2 FTE（0.7–0.8 FTE/人 × 8 个月），对应 100–112 人周；产品轨道 9+1 对应 215 人周。不要把产品轨道的人头直接压到论文关键路径上。学生口径为 5–6 人：图谱 0.5 与集成 0.5 可由证据/架构角色兼任，顾问不计入学生数；产品轨道的九题分工见 `02-` §10.4。

### 9.5 构建顺序与硬门

| 架构里程碑 | 对应 02 里程碑 | 交付 | 硬门（不通过不进入下一步） |
| --- | --- | --- | --- |
| A0 契约与骨架 | M0 | 产物信封、ID/版本、事件、状态机、门禁 stub、模型网关、恢复机制 | 两人用同一 schema 互传产物；杀 worker 后可恢复；非法门禁转移被拒绝 |
| A1 判定纵切 | M1 | RWVH 最小版、T1/T3、快照、Judge、verdict、EA、oracle/nop | oracle ≥0.90、nop ≤0.10、Work 读 tests = 0、infra 记 0 = 0 |
| A2 RWJT 纵切 | M2–M3 | T4、中文小节、Claim Composer、六类槽、导出硬门、R/W/J | 端到端一份 EB；事实句 claim 覆盖率 100%；篡改数字/删除表导致导出阻断；J 可复跑 |
| A3 证据与写作纵切 | M3–M4 | 50 篇 Q0、claim 图、论证图、大纲、分节生成、Q1 | 伪造引用 = 0；计分数字 100% 绑 EA；无证据事实句相对下降（pilot） |
| A4 Benchmark 与传播 | M5 | ≥12 任务、双专家 κ、50 个变更场景、W2 三类处置 | C1/C3 阈值；达不到则缩范围并如实报告 |
| A5 产品增量 | 答辩后 | 工作台、S2/S3、S14、多用户 | 不影响 A0–A4 的验收 |

**注意**：A3 的 50 篇 Q0 子集不与 02 的 200 篇语料目标冲突；200 篇是全产品语料，论文轨道先用 50 篇跑通 Q0 与 RWJT，不因语料未齐阻塞判定链。

### 9.6 架构验收清单

1. 任一稿件事实句可追到 claim → run → EA → 快照。
2. 删除任一被引表格/图，导出被阻断并列出受影响句子。
3. Work 无法读取 tests/rubric；Judge 无法访问 Work 工作区。
4. 探索 run 无法创建 result claim。
5. infra/verifier 失败不记 0，且可重跑。
6. 门禁未签署不能进入下一阶段；Agent 不能签署。
7. 杀 worker 后可恢复，不重复提交/计费。
8. 模型/提示升级不改变旧项目 manifest，旧项目可重放。
9. 所有外部来源按不可信数据处理；注入测试通过。
10. 导出包含稿件、claim 图、run 账本、verdict、EA、AI 使用记录与 manifest。
11. 成本可归集到项目/阶段/角色/模型。
12. 传播一次给出"重跑/重写/复核"三类处置，且旧版本保留。

## 10. 架构决策、风险与开放问题

### 10.1 关键决策（ADR）

| # | 决策 | 替代方案 | 理由 | 后果 |
| --- | --- | --- | --- | --- |
| A1 | 模块化单体 + worker + runner | 微服务 | 团队小、事务一致性要求高 | 后期拆分成本；用模块边界控制 |
| A2 | 顶层确定性状态机 | 自由 Agent 编排 | 可审计、可恢复、门禁不可绕过 | 新流程需改代码 |
| A3 | Postgres 为唯一事实源 | 图数据库/文档库 | 事务、备份、权限简单 | 图查询手写 SQL；规模有上限 |
| A4 | 产物中介，不共享对话 | 多 Agent 聊天 | 可复现、上下文可控 | 角色间需要显式 schema |
| A5 | Work/Judge 容器隔离 | 同进程权限控制 | 防作弊与可复现 | 启动成本、镜像治理 |
| A6 | 规则优先，LLM 兜底 | LLM 判一切 | 数字/引用/槽位必须确定 | 规则覆盖不足时需人工 |
| A7 | 模型/提示版本冻结 | 总是用最新模型 | 可重放、可归因 | 升级需回放与迁移 |
| A8 | headless-first | UI 优先 | 研究预算有限 | 演示体验后补 |
| A9 | 任务包基准/产品同格式 | 两套格式 | 减少分叉、便于校准 | 私有数据需额外策略 |
| A10 | 导出 fail-closed | 先导出后补 | 合规与证据纪律 | 可能阻断交付；需清晰修复指引 |
| A11 | 论文轨道不依赖全量 L1 | 先建 200 篇语料 | 避免语料阻塞判定链 | 泛化主张需 W3 扩量 |
| A12 | 不微调、不做 AIGC 规避 | 自训练/规避 | 数据不足、合规红线 | 依赖提示与检索质量 |

### 10.2 架构风险

| 风险 | 信号 | 缓解 |
| --- | --- | --- |
| 过度编排 | 阶段/门禁/状态爆炸，开发跟不上 | 只保留 18 个业务阶段（S0–S16，S5 拆为 S5e/S5c）与 9 个门；新状态必须证明必要 |
| schema 频繁变更 | 前后端/任务包反复对不上 | 契约测试 + 版本 + 回放；变更评审 |
| 模型漂移 | 同输入输出差异大 | 固定版本、温度、缓存；回放集 |
| Judge 泄漏 | Work 看到测试或 rubric | 容器/挂载/网络隔离；泄漏测试；事件作废 |
| 成本失控 | 单阶段成本超 2 倍 | 预算预留、循环护栏、缓存、告警 |
| 工作台吞噬研究 | UI 需求挤占 W1/W3 | 论文轨道三页上限；产品增量后置 |
| 传播误报 | 大量句子被 stale | 三类处置 + 人工 review；先窄后宽 |
| 任务包不可复现 | oracle 失败、镜像漂移 | digest 固定、任务准入、oracle/nop |
| 单人依赖 | 只有一个人懂 runner/账本 | 结对、文档、A0 硬门、代码评审 |
| 数据许可 | 论文/代码不可再分发 | 来源许可证登记；导出不含受限全文 |

### 10.3 开放问题（A0 前拍板）

1. v1 是否只做 CPU？若做单卡，GPU 调度与 release-all 谁负责？
2. 模型供应商与私有化部署边界；哪些数据允许出私有环境？
3. 论文轨道的三页工作台由前端兼职还是后端兼职？
4. 任务包与 benchmark 的发布许可证；封闭集如何保管？
5. W2 传播是进入 Paper A 的机制章，还是独立 Paper B？架构上两者都支持，但评测预算不同。

### 10.4 一句话

**用一个可恢复的确定性内核，把"检索—构思—确证—写作—传播"变成同一条证据账本上的受控流程；论文轨道只建到 RWJT 闭合，产品轨道再加工作台与协作，绝不把平台规模当成研究贡献。**
