> 审计日期：2026-10-25  
> 审计对象：`research_agent/`、`modules/`、`apps/web/`、`tests/`、根目录 00–38 文档与 README  
> 证据等级：`[代码]` 已读实现；`[实测]` 本轮运行；`[文档]` 仅文档口径；`[市场]` 公开产品页/论文，未独立复现  
> 方法：先看代码与测试，再看文档宣称；市场部分只采用能力类别，不引用无法独立核实的定价或效果百分比。

## 0. 结论先说

**当前系统是一个“证据治理原型 + 高完成度演示工作台”，还不是一个可用的科研 Agent。**

它真正有价值的部分不是 9 阶段、16 阶段、Skills 面板或多智能体界面，而是四条已经开始落地的结构约束：

1. 摘要-only 不生成 span；
2. RunCapsule/EA 绑定真实运行与哈希；
3. Claim 通过 EA 绑定结果，稿件槽位不能抢先填数；
4. Closure 做结构检查并生成不自动投稿的导出清单。

但当前存在三层断裂，决定了它还不能辅助真实科研：

- **产品层断裂**：React 工作台的聊天、检索、实验、签署、导出全部是本地静态状态；真实 runtime 有 `/api/runs`，却没有被主对话和工作流使用。
- **完整性断裂**：claim 的“人签”只是普通 JSON 字段；closure 读取 demo 内嵌 capsule；protocol 在 run 之后才冻结；RSI 的 `claim_eligible` 可被默认值绕过。
- **叙事断裂**：文档 36/38 已经承认大量 SIM 与未实现，但 README 仍把 `EA(source=rerun)`、Verdict、lease-gated skills、评估隔离写成当前能力；`22/22` 创新点校验只是文件存在/字符串包含检查。

**差异化仍然成立，但必须换赛道。** 不能与 OpenAI/Anthropic/Google 比检索与综述，也不能与 Elicit/Undermind/Consensus/Scite 比文献覆盖，更不能与 Kosmos/AI Scientist/Co-Scientist 比实验能力。唯一值得押的是“**变更后哪一句还成立、哪一个导出必须被拦住**”的证据运营层；目前只完成了骨架，没有完成可用的维护闭环。

### 1.2 真实用户旅程判定

| 用户想做的事 | 今天发生什么 | 能否用于真实科研 |
| --- | --- | --- |
| 问一个研究问题 | 静态模板或关键词路由，不调用模型 | 否 |
| 检索一个领域的文献 | 4 篇冻结语料，或 OpenAlex 摘要线索（不生成 span） | 否 |
| 上传/读取自己的 PDF，追问其中证据 | 只读文件浏览器，预览文本；不解析 PDF、不做页码/字符定位 | 否 |
| 从文献中抽 claim、看支持/反驳 | 前端有证据卡，后端没有 claim 级语义支持检查 | 否 |
| 设计并运行一个真实实验 | 固定钙钛矿设计、iris/ChemLab toy run | 只适合协议演示 |
| 生成论文正文/综述 | 只有槽位，没有 prose | 否 |
| 人工签署 claim | 前端本地状态；CLI 只要求非空 `human_reason` | 不可审计 |
| 导出可投稿稿件 | 只能导出整个工作区 JSON，且不受 closure 拦截 | 否 |
| 数据/代码变更后知道哪些结论失效 | lineage 可做哈希图传播，但数据哈希来自 capsule 字段而非文件重算 | 部分，原型 |
| 展示“证据治理”给导师/评委 | ChemLab 真实 run → EA → 11/11 closure → export manifest | 是，但必须标注结构闭合 |
| 展示“自进化” | 候选/租约/rollback 面板，无真实 evaluator 与能力增益 | 只能作为控制面原型 |

**判定：**

- **作为毕业设计/答辩原型：可用。** 有真实可复算的 S5、真实产物、真实测试、完整叙事，以及罕见的自我审计文档。
- **作为日常科研工具：不可用。** 它不能回答用户的问题、不能读用户的 PDF、不能写作用户的稿件，也不能对真实文献做规模化检索。
- **作为“证据运营层”的最小验证：方向正确，但闭环未完成。** 目前更像“证据对象目录 + 结构检查器”，还不是“变更后可重新闭合的运行时”。

## 2. 后端问题：不是“代码写得丑”，而是信任边界不成立

### P0-1 “人签 claim”不是签名，任何人可手写

`ClaimRecord` 只有 `human_reason`，没有 signer、身份、公钥、签名或不可变日志（`research_agent/contracts.py:285-293`）。`run claim` 从 argv 接收 statement/reason/scope，检查 capsule/EA/hash/scope 后直接写 `status="supported"`（`research_agent/modules/run.py:301-349`）。`closure.sign` 生成的 `SignatureRecord` 也只是 JSON 字段（`contracts.py:315-322`；`closure.py:170-181`）。

后果：只要拿到目录写权限，就可以手写一份 claim + signature + closure report，让系统“看起来完成签署”。这不是密码学问题，而是**信任边界问题**：系统没有区分“作者本人批准”和“任何能写文件的人批准”。

最小修复：Ed25519 签名覆盖 canonical claim/EA/closure checks，`run claim --signer/--key`，closure 验签；append-only 审计日志；测试必须覆盖伪造 claim 失败。

### P0-2 Closure 读取 demo 内嵌 capsule，而不是 capsule 文件

`ClosureAgent.check` 从 `demo["modules"]["run"]["capsule"]` 读 `status`（`closure.py:39-58`），只对 capsule 文件做哈希比对，不解析文件内容。`tests/test_closure.py:31-61` 甚至写入一个空的 `{}` capsule 文件，同时在 demo 里写 `status: completed`，closure 仍然可以 ready。

后果：一个失败/空 run 可以在 demo 层被重新标成 completed，而哈希检查不会发现。这直接违背“RunCapsule 必须 completed”的检查语义。

最小修复：closure 从 `capsule_path` 读取并校验 `run_id/status/dataset_sha256`；EA 从 `ea_path` 读取并校验 `run_id/scope/source/immutable`；demo 只作为索引，不作为事实源。

### P0-3 “没有冻结 protocol 不执行”是 SPEC 不变量，但代码没执行

`modules/run/SPEC.md:21` 明确写“没有冻结 protocol 不执行”，但 `RunAgent.execute` 只检查 dataset/model/seed，不接收也不校验 protocol（`run.py:59-79`）；pipeline 的 `run_dataset` 分支也不要求 `protocol_file`（`pipeline.py:290-340`）。同时 `ExperimentDesignAgent.freeze` 要求 capsule 已完成（`experiment.py:95-108`），所以当前流程是“先跑后冻”，与预注册相反。

后果：anti-HARKing 的核心叙事没有代码支撑；protocol 更像“事后说明卡”，不是预注册。

最小修复：run 必须传入 protocol card，校验 design hash、dataset、metric、seeds、test_size；protocol 必须在 run 前冻结；或者诚实地把对象改名为 `PostHocProtocolCard`，并从 SPEC/论文中移除“预注册”表述。

### P0-4 RSI 的“安全不变量”可被默认值绕过

`EvalEvidence.claim_eligible` 默认 `True`（`rsi.py:78`），`admit()` 只检查 public/hidden 都 passed、dry-run 非空、human_reason/scope 非空，不强制 `claim_eligible=False`（`rsi.py:364-403`）。因此一个 harness-only 候选只要构造默认 evidence 并调用 `admit`，就可能写入 capability claim。当前 ChemLab ledger 安全，只是因为构造 evidence 时显式写了 `claim_eligible=False`，不是结构强制。

同时：

- S5 的 hidden/near-OOD/regression 只是同一 demo CSV 的不同 `test_size`（`s5_eval.py:14-21,83`）；
- 准入不使用 near-OOD/regression（`admit` 不要求）；
- lease 只覆盖 `literature.retrieval.budget` 与 `experiment.run.seeds`，没有代码/prompt/skill patch 执行器；
- immutable 检查是 target 子串检查，patch 是自由文本（`rsi.py:144-147`）；
- 已有 ledger 的 hidden mean Δ 为负，只是 seed 成本节省。

后果：“Lease-Gated RSI / 自进化”只能写成“两旋钮的候选/准入台账 + JSON 租约控制面”，不能写成能力提升或安全不变量已强制。

### P0-5 真实检索没有全文，span-only 只在小语料上成立

`OpenAlexRetriever.full_text()` 永远返回 `None`，hits 只有摘要（`openalex_retriever.py:14-18,152-163`）；`LiteratureAgent` 只对 `full_text` 解析 span，所以 OpenAlex 路径必然 `insufficient_evidence`。唯一真实全文路径是 4 篇冻结 CC-BY 语料或 3 篇 transfer 语料。

后果：S1 的核心卖点“span-only 证据”在一个真实研究主题上无法工作；用户拿不到足够多的论文，也读不到 PDF。

最小修复：PDF/HTML 抓取 + 解析（GROBID/PyMuPDF 或现成 OA API），保留页码/字符偏移；对摘要-only 明确 abstain；把“4 篇语料”标成 pilot，不写成 live search。

### P1-6 LLM 网关没有接进科研流程

`ModelRegistryService.WIRED` 中 literature/idea/experiment/paper 均为 `False`（`models/service.py:13-39`）；只有 `/api/models/probe` 与 `rsi propose-model` 调用模型。runtime 没有 chat/completions 路由（`runtime/app.py:242-700` 的路由表）；React 的 `sendMessage` 从未 fetch 模型（`workspaceStore.ts:1467-1638`）。

后果：模型选择、思考强度、上下文压缩、回复长度这些前端控件，对科研输出没有任何影响；“LLM research agent”目前不是事实。

### P1-7 lineage 不是内容寻址，变更传播不可信

`lineage.py:179-198` 的 dataset/code 节点哈希直接取 `capsule.dataset_sha256/code_sha256`，没有从当前文件重算；`closure.sign` 不调用 lineage；`export_allowed` 只要求存在未 stale 的 signature 节点（`lineage.py:455-461`）。文档 36 展示的“数据集变化 → 14/15 个下游 stale”是修改合成 capsule 字段，不是改真实 CSV。

后果：“数据/代码变化后 claim/图/签名失效”这一最强差异化，目前是哈希图的 CLI 原型，不是可验证的内容寻址。

### P1-8 runtime 是“本地无鉴权写 API”，不是可部署服务

- 无 auth（`runtime/app.py:236-239`；`__main__.py:23` 只限制非 loopback 需 `--allow-remote`）；
- CORS 允许 `null` 与公开 Pages origin；
- `JobManager` 内存态、单 worker、最多两个 pending、无 cancel/timeout/dedupe；
- 状态是 JSON 文件，read-modify-write 无跨请求锁；
- `requirements-runtime.txt` 只列 fastapi/uvicorn/pydantic，没有 numpy/pandas/scikit-learn，而 S5 需要它们；
- 没有 CI 跑后端测试（`.github/workflows` 只有 pages/refresh-digest）。

后果：本地演示可用；一旦通过代理暴露，任何页面都能 POST `/api/runs` 或 `/api/models/probe`（可能产生 API 费用）。

### P1-9 写作、书目、评估等“阶段”仍是没有语义的骨架

- `PaperAgent` 在 `claim_refs` 非空时就把 `result.primary` 设为 `bound_claim`，并自己警告“不重算 EA/scope”（`paper.py:84-91`）；
- 5 个槽位没有 prose、没有引用选择、没有 Word/LaTeX 导出；
- `BibliographyAgent` 只校验 `verification_source` 字符串与 64 位哈希形状（`bibliography.py:25-41`）；
- EVAL 面板是前端 store，真实 held-out 隔离不存在（文档 38 已承认，`38:106,140`）。

后果：S8–S16 的“论文产出”是对象接线，不是可交付稿件；“评估隔离”是控制面演示。

### 后端工程层面的其他问题

- 模块 SPEC 中 `run`、`closure`、`bibliography` 仍是 `status: draft`，但被用于“已实现”叙事；`AGENTS.md` 要求 draft 不能直接 active，这一点至少没有伪装成 active。
- JSON 存储没有 schema 迁移/锁；job 事件无限增长；`PipelineRunner._emit` 吞掉 sink 异常（`pipeline.py:102-106`）。
- EA 的 `path` 存的是传入的相对路径，换 cwd 后 closure 可能找不到（`run.py:165,290`；`closure.py:55-56`）。
- 测试覆盖的是“对象接线”，不是“真实科研失败模式”；`tests/test_closure.py` 的手写 claim 就是例子。

## 3. 前端问题：交互词汇领先于执行底座

React 工作台在视觉、信息架构、状态反馈上已经达到“可演示产品”的水平，但它目前是 **static adapter 的演示壳**，不是 Claude Code 类的工作台。

| 交互 | 看起来发生了什么 | 实际发生什么 | 影响 |
| --- | --- | --- | --- |
| 发送消息 | 有思考、回答、卡片 | 关键词路由或固定模板，不调用模型 | 不能回答研究问题 |
| 只读/询问/完全访问 | 有权限模式 | 只拦 5 个本地 reducer；freeze/sign/export 可绕过 | 权限承诺不成立 |
| 自动运行 | 9 阶段推进、暂停/单步 | 1.1s timer；刷新后 `running=false` | 关页即丢，结果与主题无关 |
| 检索 | 4 sources / 12 spans | 固定数字 | 不是真实检索 |
| 实验 | RUN-014、412 vs 286 | 固定值 | 不是真实 run |
| 签署 claim | 一键签名 | 本地 status 改为 signed | 无身份、无审计 |
| 导出 | “closure 未过，导出锁定” | 工作区 JSON 随时可下载 | 导出治理不成立 |
| Skills | 创建/导入/调用 | 目录同步；调用是模板 | 技能不能改变行为 |
| MCP | 注册/测试/审批 | 注册本地；审批插入固定 “SIM” 文本 | 无真实 transport |
| 自进化 | 候选/租约/rollback | 固定候选 + 本地状态 | 不改变任何行为 |
| 文件 | 文件夹选择/预览 | 只读索引；无编辑/树/全文搜索/undo | 不能作为研究工作区 |
| 持久化 | 自动保存 | 整包 localStorage；quota 错误被吞；无多标签协调 | 可能静默丢工作 |

最关键的三个问题：

1. **聊天没有模型。** 这是“research agent”的第一性能力，不接模型，后面的检索、写作、实验都无从谈起。
2. **签署/导出是本地剧场。** 即使后端完整性修好，前端也不能把“本地 signed”当作真签名；必须调用 runtime 的 claim/sign 端点，或者明确标注“演示”。
3. **文件管理只有读。** 研究者的核心资产是 PDF、笔记、稿件；不能读 PDF 内容、不能编辑、不能 diff/undo，工作台就无法承接真实工作。

与 Claude Code 类产品的差距不是“少一个按钮”，而是缺少 **tool execution + permission + file edit/diff + shell + checkpoint/rewind + MCP transport + hooks** 这一整套底座。对科研场景，最值得补的不是 shell，而是：

- PDF/Zotero 导入与 span 定位；
- 流式模型 + 工具调用（检索、读 PDF、跑实验）；
- 版本化笔记/稿件与 checkpoint；
- 证据卡与原文高亮联动；
- 导出 DOCX/LaTeX/BibTeX。

## 4. 市场对照：哪些是入场券，哪些才是差异化

> 以下只采用公开产品页/论文的能力类别，不引用无法独立核实的定价或效果数字；厂商自报的准确率不当作独立证据。

| 能力层 | 代表产品 | 2026 状态 | 对我们的含义 |
| --- | --- | --- | --- |
| 深网/多步研究报告 | OpenAI Deep Research、Gemini Deep Research、Claude Research | 入场券；分钟级、几十到上百来源、内联引用 | 不做正面竞争 |
| 文献检索/筛选/抽取 | Elicit、Undermind、Consensus、Semantic Scholar | 入场券；亿级元数据、全文/摘要、表格抽取、BibTeX | 不自建索引，接 API |
| PDF/资料库问答 | NotebookLM、PaperQA2、SciSpace | 入场券；span 引用、资料库对话 | 不自研通用 PDF chat |
| 引用语境/验证 | Scite、CitationAgent、各类 citation checker | 快速商品化；支持/反对/提及标签 | 不能把“引用 UI”当护城河 |
| 假设生成/实验执行 | Co-Scientist、AI Scientist、Kosmos | 高成本、强资源；有真实实验/湿实验合作 | 不押“自动发现” |
| Claim→artifact 溯源 | 主流产品普遍缺失；Kosmos 有 claim-to-code/text 链接但非通用审计层 | 稀缺 | 我们的潜在差异 |
| 变更后维护 | 几乎没有主流产品把“数据集/代码/论文变更 → 哪些 claim/图/句失效”做成产品 | 最稀缺 | 最值得押 |
| 可问责签署/审计 | 受监管行业有需求；消费级产品不卖 | 稀缺 | 我们的潜在差异 |
| 校准的“证据不足” | 多数产品会给一个看似完整的答案 | 稀缺 | 应做成一等对象 |

### 4.1 市场结论

- **表内前五层已经是红海。** OpenAI/Anthropic/Google 有模型、分发和价格；Elicit/Undermind/Consensus/Scite 有数据和文献工作流。毕业设计不可能在“检索更多、总结更好、写作更快”上赢。
- **真正稀缺的是“可审计的维护”。** 研究者真正的痛点是：论文写了 80 句，其中 12 句绑定到某次 run / 某篇论文 / 某张图；半年后数据变了、代码变了、论文被撤稿，哪些句子必须改？哪个导出必须拦？主流 deep research 报告是一次性的，不维护。
- **我们的方向与稀缺层重合，但实现还停在骨架。** 当前有 hash graph、closure、EA、slots，但没有把“变更 → 影响 → 处置 → 重新闭合 → 重新签署 → 导出”做成一个用户可走的闭环；lineage 也不是内容寻址。
- **不要做“全栈 AI Scientist”。** 市场已经证明这条路需要模型、算力、实验平台与领域数据；我们的优势是“轻、可审计、可本地部署、可接别人的检索/模型/实验”。

### 4.2 建议的市场定位

> **不是“又一个 Deep Research”，而是“论文/报告的证据运营与变更审计层”。**

首发楔子建议二选一：

1. **ML 论文复现档案**：给定一篇论文的仓库与数据，生成 claim 账本、复现 run、图表 provenance、数据/代码变更影响与可导出复现包。
2. **学位论文/综述的 claim 账本**：导入 PDF/Zotero，逐句绑定 span，标注支持/部分支持/反驳/无证据；变更（撤稿、新版、数据更新）后自动标 stale，导出带 citation 的章节草稿。

两者都比“16 阶段全自动科研”窄，但都能在 4–6 周内做出真实纵切，并且直接对应评审能听懂的价值。

### 5.3 文档自身的优点与风险

**优点：**

- 36/38 等文档已经主动写明“post-hoc protocol”“SIM”“未实现 held-out”“结构闭合非语义真值”，这是很多项目做不到的诚实。
- 22/23/27 对 RSI 的开源对照与“不可宣称”清单是真实的研究工作，不是包装。
- `modules/*/SPEC.md` + `AGENTS.md` 的规格驱动流程，确实让代码边界比一般毕设清楚。

**风险：**

- **概念增殖。** 39 份文档里出现了 RWMT、RWJT、StageLease、ProcessProtocol、Eval Isolation、Lease-Gated RSI、Evidence Debt、双轴审计等大量概念；真正 WIRED 的只有少数。每新增一个概念，答辩时就多一个被追问“实现了吗”的点。
- **顶层叙事与脚注不一致。** 文档深处承认 SIM，README 和演示页面却容易让读者以为已实现。答辩时评委通常只读 README/看 Demo，不会读到 38 的“边界”小节。
- **“文档先行”变成“文档替代实现”。** 27 的创新对账、22/22 校验、11/11 closure 都容易制造“已完成”的错觉；真正的验收应该是失败注入测试（空 capsule、伪造 claim、改 CSV、篡改图、越权导出）而不是指针存在。
- **自我审计的结论没有反馈到代码。** 28 已经列出 P0（S5 split、hidden sealed、single cycle、patch 语义、closure 身份），36 也列出缺口，但当前代码仍保留这些问题。审计文档如果只增加文档、不改变代码，就会变成“反思表演”。

### 5.4 是否“违背”了文档创新点？

更准确的说法是：**文档中的“设计主张”没有被实现到可宣称的程度，且顶层表述与代码存在直接矛盾。**

- 不是“文档说 A、代码做 B”这么简单；很多文档在脚注里已经承认 B。
- 真正违背的是：
  1. `modules/run/SPEC.md` 的不变量“没有冻结 protocol 不执行”被代码违反；
  2. README 的 `EA(source=rerun)/Verdict` 与代码 `source=run` 矛盾；
  3. README 的“lease-gated skills/workflows”与 skills `not_available` 矛盾；
  4. “human-signed”与“只有 human_reason 字段”矛盾；
  5. “22/22 校验”与“文件存在/字符串包含”矛盾。
- 这些是最应该在答辩前修掉的，不是再加功能。

## 6. 差异化：现在到底差在哪，应该押什么

### 6.1 不能作为差异化的东西

- 9/16 阶段流水线：Co-Scientist、AI Scientist、Kosmos 都有更完整的版本；
- 多智能体界面：Anthropic/OpenAI 的多 agent research 已经是产品能力；
- Skills 目录/导入：Claude Code、Codex、Kimi 等已有成熟生态；
- PDF chat / 引用卡片：NotebookLM、Elicit、SciSpace 已经商品化；
- “模型选择/思考强度”设置：是桌面 Agent 的标配，不是科研差异；
- “本地部署”：有价值，但不是学术创新。

### 6.2 可以作为差异化的东西

1. **Claim-level 证据绑定 + 结构闭合**：不是“引用存在”，而是 claim → EA → run → dataset/code hash → figure → slot → closure 的可阻断链。
2. **变更后的 stale 传播**：数据/代码/论文版本变化后，哪些 claim、图、句、导出失效；这是主流 deep research 不做的。
3. **可问责的人工门**：签名、角色、不可变日志、导出前重新闭合；面向导师/期刊/合规，而不是 consumer chat。
4. **受治理的 harness 改进**：候选只能改检索预算/seed 等 harness 旋钮，不能改 claim/gate；public/hidden/near-OOD/regression + 人签租约。注意：当前实现只到“两旋钮台账”，必须补真实 evaluator 才能称为 RSI。
5. **校准的“证据不足”**：摘要-only、无全文、无 span、无 EA 时明确 abstain；这比“生成一个完整答案”更适合科研。

### 6.3 一句话论文定位

> 我们不是构建一个更会检索和写作的科研 Agent，而是构建一个**让科研 claim 在数据、代码和论文版本变化后仍然可追责、可重新闭合**的证据运行时；检索、模型和实验执行是可替换的上游。

这个定位与当前代码的真实强项一致，也能把“没做全自动科研”从缺点变成边界。

## 7. 建议的改进顺序

### P0：先让“治理”是真的（1–2 周）

1. **签名与身份**：Ed25519 签名 claim/EA/closure；`--signer` + 公钥；append-only 日志；伪造 claim 测试。
2. **closure 事实源**：从 capsule/EA 文件读取并校验 `run_id/status/scope/source/immutable`；空 capsule 必须 fail。
3. **预注册**：run 前必须冻结 protocol；protocol 绑定 design/dataset/metric/seeds/test_size；否则把对象改名为 post-hoc 并删除相关宣称。
4. **内容寻址 lineage**：dataset/code 文件重算哈希；closure/export 查询 impact；改一个 CSV 必须让 claim/figure/signature stale。
5. **文档降级**：修 README 的 rerun/Verdict/lease-gated skills/22/22；在 README 顶部加“当前能力/非能力”两列表；把 27 的旧测试数与状态更新。
6. **失败注入测试**：空 capsule、伪造 claim、改 CSV、改图、越权导出、摘要-only 生成 span，全部必须 fail。

### P1：做一条真实纵切（4–6 周）

7. **PDF/Zotero 导入 + span 定位**：页码/字符偏移；全文搜索；原文高亮。
8. **真实对话 + 工具循环**：runtime `/api/chat` SSE；模型只能提议 SourceHit/Span/ClaimDraft，不能直接写 Claim；人类门保留。
9. **一个真实 ChangeSet/reclose 场景**：改数据或换论文版本 → 影响列表 → 处置（接受/重跑/降级）→ 重新 closure → 重新签署 → 导出。
10. **真实导出**：DOCX/LaTeX/BibTeX + 证据附录；导出必须查询 closure/lineage。
11. **React 接 runtime**：对话、run、claim/sign、closure、artifacts 全部走 API；删除静态假状态或加明显 DEMO 开关。
12. **runtime 硬化**：SQLite/Postgres + bearer token + idempotency key + cancel/timeout + durable event log + 依赖锁。

### P2：收敛产品面

13. **一个前端，一个真相源**：`site/live`、`site/agent`、`apps/web` 三套壳保留一套主入口，其余标 LEGACY 或删除；避免“三个演示，三种能力”。
14. **Skills/MCP 要么真执行，要么不要放在主路径**：目录可以保留，但“运行技能/审批工具”不能是假动作；先做只读工具 + 逐次审批，再谈执行。
15. **可观测性与成本**：每次 run 的 token/耗时/费用、失败原因、artifact 大小；成本 per verified claim 比“支持多少模型”更有说服力。
16. **停止扩张**：冻结阶段数、设置项、子智能体面板；在 P0/P1 完成前不再加概念。

### 验收标准（建议写进论文/答辩）

- 无 span → 不能创建 literature claim；
- 无 EA → 不能创建 result claim；
- 空/失败 capsule → closure 必须 blocked；
- 伪造 claim/签名 → 验签失败；
- 改 CSV/代码 → 下游 claim/figure/slot/signature 全部 stale，导出 blocked；
- 摘要-only → abstain，不生成 span；
- hidden 不参与候选排序；
- 导出文件能追溯到 closure report、EA、run capsule、dataset/code hash；
- 以上每条都有自动化失败注入测试，而不是文档说明。

## 9. 最终判断

- **项目有没有问题？** 有，而且不是小问题：核心信任边界（签名、closure 事实源、预注册、lineage）不成立；前端与后端断裂；文档顶层叙事超前。
- **后端有没有问题？** 有。工程结构比一般毕设好，但“治理”目前是 JSON 约定，不是强制不变量；真实检索、LLM、skills、MCP、写作、评估都未接。
- **有没有差异化？** 有，方向是“证据运营/变更审计”，不是“另一个 research agent”。但差异化目前是设计 + 骨架，不是已交付能力。
- **辅助科研是否真正可用？** 作为答辩原型可用；作为真实科研工具不可用。决定性的下一步不是再加 UI，而是做一条真实纵切：真实 PDF → 真实 span → 真实模型问答 → 真实 run → 真签名 → 真 closure → 真导出。
- **是否违背文档创新点？** 文档深处是诚实的，但 README/顶层叙事与代码有直接矛盾；`run/SPEC.md` 的预注册不变量被代码违反。答辩前必须修表述，最好同时修代码。

**一句话建议：**

> 先把“证据治理”做成真的，再把“科研工作台”接上去；不要再增加阶段、面板或概念。一个可失败注入验证的 claim→artifact→change→reclose 闭环，比 39 份文档和 59 个交互修复更能支撑这个课题。
