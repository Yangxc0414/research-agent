# 59 自改进度量设计（SLH / 拒绝账本 / 归属强制）

本文只解决一件事：**怎样让"系统在自我改进"这件事可被外人证伪**。不新增代码，实现按第 6 节顺序另起改动。
写作依据是本仓库实测库存，不是设想：431 个比较里 0 条已签确证结论；235/431 做过功效检查；
95 个宿主轮次里 0 个带 run 绑定（修复前）；检索探针在现有任务集上已饱和。

## 1. 为什么现在的自改进不可信（两条独立失效）

- **尺子饱和**：`rsi` 的检索型探针在既有任务集上打到顶。饱和指标上的差值不可分辨，
  于是"提案生效前后曲线"必然是一条平线，任何提升声明都无法被拒。
- **改进者给自己打分**：记忆 A/B 两臂目前为自答（`guideline-memory` 的提示由同一模型作答）。
  自答 A/B 只能证明模型配合了提示，不能证明系统变强。

这两条是**测量学**问题，不是接线问题。因此本节不给流程改进，给三把可替换的尺子。

## 2. 设计一：阶段局限命中度量（Stage-Limitation Hit, SLH）

**核心创新：参照物由被研究者自己写下，改进者无法生成它。**

- 参照物来源：公开语料（顶会语料 / Awesome-Journal-Skills 语料包）中**人类作者自陈的 limitation 段**。
  这是已经发表、已由他人署名、时间戳早于我们任何提案的文本，因此改进者不可能通过改写提示来制造参照物。
- 任务：给定某阶段的上游产物（S2 想法 / S4 设计 / S8 稿件），要求系统产出一条"这项工作最可能被追问的局限"。
- 判定：与该文自陈局限做对齐（先做**词法+命题级**两级：命题级由人抽检，不由模型判）。命中记 1，未命中记 0。
- 分母纪律（本仓库反复踩过的坑）：
  - 每条命中必须带两个分母：全局限段数与可判定段数（不可判定的单列，不进分子分母）；
  - 参照物截断状态必须显式输出（沿用 `skill coverage` 的 pack 截断披露）；
  - 命中率的粒度不足时报警（沿用 `ratio_granularity_points`，5 点以下不得当作差异）。
- **为什么它不饱和**：局限命中是稀疏事件，基线命中率天然远离 1；这与检索召回在 4 篇语料上打满是相反的分布形态。
  这是预期，不是结论——见 §6 的第 0 步，必须先测基线分布。
- **可证伪条件**：若在 40 篇语料上 SLH 基线 ≥ 0.85，或不同提案间的差异全部落在粒度阈值内，
  则该尺子与检索探针同病，本设计作废，不做第二轮修补。

## 3. 设计二：拒绝账本（Rejection Ledger）——把"没改成"当作主指标

自改进的可信证据不是"改好了很多次"，而是**改进者被自己的门禁大量拒收**。

- 记录 proposal 生命周期全部事件：`proposed → dry-run → public/hidden → 人签 → active / revoked`，
  以及每次被拒的确切原因码（缺 dry-run ref / 越界 / 指标未变好 / 撤销传播命中）。
- 对外报的三个数：拒绝率、拒绝原因分布、**生效后回退（revoked）比例**。
  只报生效数等于报一个自夸数字；这是本仓库一贯的边界（不给自己 clean bill）。
- 与既有实现的关系：`rsi` 已有 pending/active/revoked 状态与 lease 校验，
  缺的是把状态迁移序列投影成一张带原因码的账本，并让"拒绝率高"成为**合格信号**而非事故。
- **可证伪条件**：若某轮自改进的拒绝率为 0，判定为该轮的指标或门禁失效（而不是"提案都很优秀"），
  自动把该轮标记为不可信并停发结论。这条是硬规则：零拒绝=仪器坏了。

## 4. 设计三：产物归属由 harness 强制（收 #49）

现状是约定：idea/review 产物可被宿主直接改写，贡献归属只是文件里写着谁生成的。

- 写入时绑定 principal（host-agent / profile / 人），落进产物自身哈希闭包；
  归属与内容同签名，事后改写必然改变 `study_sha256` 类派生哈希 → `lineage verify` 报 stale。
- 直接收益：SLH 与拒绝账本的分子都可追溯到"谁产的"，自改进曲线才能按来源分解
  （否则宿主手改的那一条会被算成系统能力增益——这正是当前最容易被审稿人打的点）。
- **可证伪条件**：若改写产物后哈希链仍判 fresh，则该机制形同虚设，不得用于任何对外结论。

## 5. 设计四：探索性 / 确证性断言的门禁语义（收 #62）

建议方案（最小改动，且不放松任何门）：

- 断言必须显式标 tier。`confirmatory` 走现有 claim/closure 全链，且要求预注册在先 + 区间不跨零 + 强基线已声明；
  `exploratory` 不进 claim、不进正文允许集合，只进投递包的描述层（`power_tiers` 已把它作为描述层输出）。
- 门禁语义上二者不可互换：探索性断言**永不允许**被 `next_actions` 递成签核命令
  （这条已有实现方向：#29/#56 的"非结果不得给 claim 命令"，扩展到 tier 即可）。
- 为什么这是正确方向而不是拖延：128 种子那条包的实测是 4 条可签、0 条拒、`assertions: 0`；
  也就是说"能不能确证"已经不取决于功效，而取决于有没有人写下断言。tier 字段把这件事变成显式输入，
  而不是让系统偷偷把探索结果当结论用。

## 6. 实现顺序与验收（每步都必须带一条"能失败"的用例）

0. 先测 SLH 基线分布（40 篇语料 × 现有 S2/S4/S8 产物），只出数，不改代码。不达 §2 的可证伪线才继续。
1. 拒绝账本投影（读侧，纯新增）+ 零拒绝自动标不可信。
2. 归属绑定写入哈希闭包（涉及链，需一次人工授权重绑，走 #54/#74 的路径）。
3. tier 字段进断言 schema，`next_actions` 按 tier 收紧（只收紧不放宽）。
4. 全量套件交付前一次（今天实测 1446 秒），并跑 `workspace export` / `plugin export` / `build_release --prune`。

每一步的完成判据不是"实现了"，而是"该步的 §x 可证伪条件被真实跑过一次，并把数字记进 58 交付验收清单"。
