## 1. 目标与判断

### 1.1 我们要做什么

我们做的不是“再写一个自动论文生成器”，而是：

> **一个本地优先、证据可追溯、人工可治理的科研运行时。**  
> 它把“文献、假设、实验、证据、写作、导出”串成一条可检查的链，并允许系统在该停下时明确停下。

三个不可妥协的原则：

1. **证据可追溯**：每个结论都能回到来源、运行产物或人签 claim；
2. **结论可验证**：数字能从 metrics 重算，结构不一致必须失败；
3. **人工有最终决定权**：claim、closure、导出不能由模型自动完成。

### 1.2 为什么现在做这件事

最新研究给出的信号很明确：

- MLReplicate 发现，自动评审接收的论文中有 59% 含伪造或无支撑 claim；
- 验证缺口综述发现，24 个可运行科研系统中只有 38% 发布 seeds/执行轨迹，只有 38% 报告 novelty verification；
- 引用研究显示，“引用真实存在”容易查，“引用是否支持这句话”仍然很难。

因此，领域瓶颈已经从“能不能生成论文”转向“论文里的 claim 能不能被独立验证”。这正是我们的切入点。

## 2. 从底层到上层：已经实现了什么

| 层级 | 已实现能力 | 当前状态 |
| --- | --- | --- |
| L0 数据与契约 | 统一的来源、span、claim、EA、closure、论文契约；每个模块有 SPEC | 已落地 |
| L1 科研模块 | 文献、假设、实验设计、运行/EA、图表、论文、基金 | 已落地，S1–S5 较完整 |
| L2 编排与运行时 | 任务路由、Pipeline、本地 runtime、事件、产物、job 持久化 | 已落地 |
| L3 证据治理 | span-only、人工门、claim/EA/closure、静态审计、数值重算、RSI lease | 已落地核心链 |
| L4 证据工作台 | 真实任务运行、来源选择、证据/门禁回填、报告/论文预览、运行历史、真实模型调用、技能目录 | 已落地主路径 |
| L5 评测与自进化 | RSI public/hidden/confirm、lineage、bibliography | 部分落地，待正式评测 |

### 2.1 底层底座

- 每个科研模块都有明确输入/输出和边界，代码服从模块规格；
- 模块层提供 `module_overrides` / `module_factories` 接缝：替换一个模块不需要改主 pipeline，但仍受 SPEC 与证据边界约束；
- Skill 层提供“使用记录 → 确定性回归评测 → RSI pending 提案”：不自动改写、不自动启用；
- 同一套 CLI / runtime / 前端共享同一 pipeline，不再各跑一套；
- 失败、警告、fixture、证据边界都会进入产物，不静默通过；
- 任务状态、事件和结果摘要落盘，runtime 重启后仍可读取；
- 新增 bug 级静态检查，避免死代码和无效导入继续堆积。

### 2.2 科研主链

- **文献**：检索、全文读取、句级 span、覆盖回执与 gap；
- **假设**：从 span 聚成带否证条件的候选，不自动通过 G1；
- **设计**：假设、baseline、指标、对照、seeds、停止规则；
- **运行**：RunCapsule、EA、claim draft；数值 claim 可重算；
- **图表**：结构示意图与数据图分离，示意图不能冒充结果图；
- **写作**：可读工作稿与报告；结果段只写已签 claim 的验证数值；
- **闭合**：结构性 Closure、静态审计、人签后才允许导出。

### 2.3 运行时与工作台

- 任务层先识别任务类型，再选择最小必要阶段；文献综述不会误跑完整实验；
- 用户选择任务类型（自动 / 文献 / 假设 / 实验 / 完整），点一次“运行任务”即可看到阶段事件、产物和任务报告；
- 运行完成后，真实 coverage、gap、候选、门禁、RunCapsule 回填到证据链；
- 可在工作台直接预览报告、论文、JSON、SVG；
- 运行历史、真实模型调用、runtime 技能目录都已接入设置页；
- 模型设置页新增“模块模型绑定”：S1 检索、S2–S3 候选、S4 设计、S8–S12 写作分别绑定 runtime profile，任务与设置页共用同一个模型网关与会话密钥；
- 真实运行与静态演示有明确标识，不再把 fixture 当科学结论。

## 4. 创新点：对外可以怎么讲

### 4.1 真正的差异化

1. **证据运行时，而不是论文生成器**  
   我们不只产出一篇“看起来像论文”的文本，而是产出可审计的来源、span、claim、EA、RunCapsule 和 Closure。每个结论都有上游。

2. **数值 claim 可重算，错误会阻断**  
   人工签署 claim 前，系统会从 metrics 重算 metric/comparator/value；Closure 再重算一次。结果段只渲染已验证数值，避免“论文写了但没有证据”。

3. **人工门是系统门，不是提示词**  
   Claim、Closure、导出都必须人工完成；runtime 不提供签核端点。全自动可以在人工门前停下，而不是替作者做决定。

4. **受治理的自进化**  
   自进化只在策略层做候选，必须经过 public/hidden/held-out 与租约确认；不能修改 claim、gate、rubric 或导出层。

5. **测试与生产显式分离，生产强制模型驱动**  
   test 模式允许离线 fixture/规则回退，只用于回归与演示；production 模式要求 API key、模型绑定与模块接线齐备，缺一项直接 fail closed；已就绪后模型调用或输出解析失败同样让任务失败，不再静默退回模板。证据门禁与 claim/EA/closure 仍是确定性代码。

6. **流程门禁开始进入执行控制流**  
   `review` 继续生成完整待审包；`strict` 在 Q0 证据不足、G1 未选 idea、G2 未冻结协议时停止，并保留可续跑产物。S4 先 `freeze-design` 生成 ProtocolCard，S5 的 RunCapsule 记录 protocol design hash，run 完成后再写 ProtocolBinding；提供已签 `claim_file` 时自动执行 closure check 与 lineage build/verify，并回写证据包状态。

7. **Skill 不自动改写，改进必须走证据链**  
   Skill 使用会留下 usage 记录；内置 Skill 有 public/hidden 回归评测；改进只能生成 RSI pending 候选，必须经人签、租约后才可能生效，不自动改写或自动启用。

### 4.2 与现有方法的关系

| 方向 | 代表工作 | 我们的差异 |
| --- | --- | --- |
| 端到端论文生成 | AI Scientist、Agent Laboratory | 我们更强调证据治理与人工门，不追求全自动替代 |
| 文献综合 | OpenScholar、PaperQA2 | 我们承认文献能力较弱，但补上了运行/claim/closure 链 |
| 假设生成 | Co-Scientist | 我们的假设模块仍偏轻，差异化不在假设锦标赛 |
| 证据链审计 | ScientistOne / CoE | 方向最接近；我们的差异是本地优先、人工门、artifact runtime 与 RSI 租约 |
| 复现与证据审计（2026） | ReAgent / TruthInsightBench / PaperDoctor / Replica | 2026 的评测重点正从“能否生成论文”转向“结论能否被 artifact 复现、引用是否语义支持”；我们的 strict 预注册 + closure + 人签导出与这一方向一致，但还没有同任务基准与独立 Judge，不能宣称效果领先 |
| 端到端科研智能体 | Co-Scientist / ScientistTwo / AI-Scientist | 我们不争生成吞吐，补“资格判定（span/写作包绑定）、完成判定（人签 closure）、失效判定（SHA-256 链与 lineage）”三者的交集；证据链只证明存在性与身份，不证明正确性。完整对照与差距见 `49-` |

**边界要讲清楚：** 我们不是通用 AI Scientist，也不是已经达到 SOTA 论文质量；我们的优势是“可审计、可治理、可复现”的系统底座。

## 5. 当前不足

### P0：影响科学有效性

1. **本地全文入口已落地，但仍不完整**：支持 PDF/TXT/MD 与页码；仍缺浏览器上传、扫描件 OCR、中文版式与参考文献结构化解析。
2. **引用支持审计已落地，但不是语义保证**：现在有句子级 support-audit（模型 judge 或明确标注的 lexical heuristic），仍不能证明 entailment，也不能替代人工审稿。
3. **独立判定与评测仍不完整**：support judge 是模型 advisory，不是语义蕴含；judge 与 writer/idea 共用同一 profile 时只警告、不阻断；已有内部 oracle/nop 对照和结构化 FailureRecord，但外部 held-out、clean rerun 与人工盲评仍未实现。
4. **预注册已修正，但缺真正独立审计**：strict 模式在 G2 前停止，`freeze-design` 可先冻结 design，run 完成后再绑定 capsule；已增加 `design-audit.json` 机械清单（字段/seeds/统计计划关键词），但仍需独立统计/方法审阅，清单不等于 G2；
5. **正式评测缺失**：目前只有内部结构指标，没有同任务基准与人工盲评；
6. **不能保证“不错的中文期刊”**：现在能保证证据边界、引用映射与投稿条件审计；不能替代真实全文、真实实验、人工写作与同行评审。`manuscript-audit.json` 的 `submission_ready` 只是内部门槛，不是录用概率。
7. **production 仍默认被阻断**：idea/experiment 已接入模型路径，但默认没有绑定/密钥；必须在设置页为 literature/idea/experiment/paper/judge 选择 runtime profile 并配置 key，production readiness 才会通过。当前默认 readiness 为 false，这是刻意 fail closed，不是 bug。
8. **S5 运行契约仍不完整**：已补 run contract / artifact allowlist / evidence hash 核验与 strict seed 校验；仍缺 baseline min_delta 自动计算、run-state/stall ledger；外部 Skill 脚本也不做 OS 级 sandbox，依赖显式信任。

### P1：影响文章质量与使用体验

1. 写作已增加投稿工作稿与确定性审计，但仍缺全局大纲评审、section-level 模型修订、引用漂移控制与具体期刊模板；即使审计为 pass，也不等于期刊录用；
2. 失败恢复仍是单次反馈，缺少多假设 failure attribution；
3. EVAL / Review Pack / Lineage 还没有完全消费 runtime 真实产物；
4. 前端仍保留 SIM 自动状态机，但 runtime 任务已禁用 SIM 自动推进与“模拟签 claim”，避免把演示状态伪装成真实执行；纯演示任务仍是 SIM；
5. Closure / Export 已能在 UI 显示下一步命令与路径续跑，但签核/导出仍只能在 CLI；这条边界应继续保留，并补“线下签署、线上查看”的交接记录；
6. Skill 已有版本激活/回滚执行器、静态 manifest linter、canonical → Qoder/Claude/Zcode 同步脚本与一致性测试、外部 advisory/本地 trusted script 与 disabled 蒸馏候选；脚本执行是显式信任下的本机全权限，不是 OS sandbox；指令级质量评测仍需要模型或执行 harness。
7. S0 已有 RouteDecision（信号/置信度/needs_input）与 strict-routing 开关，但默认仍会 fallback 到 full_research；S2–S3 idea review 是词法预审，不是文献新颖性搜索或独立同行评审。

## 6. 下一步路线

### 阶段 1：真实证据入口（下一阶段，约 2–4 周）

- 支持 PDF / TXT / MD 导入，保留页码、段落和字符锚点；
- 接入本地语料检索，真实课题可以形成 span；
- 增加引用支持判定：支持 / 部分支持 / 不支持 / 无法判断；
- 选 10–20 个主题做内部评测，报告 citation support、coverage、unsupported claim。

**交付标准：** 任意给定主题，只要用户提供全文，就能形成可定位证据链。

### 阶段 2：独立判定与 RWJT（中期）

- 先冻结 ProtocolCard，再 run；design/dataset/metric/seeds 进入 capsule；
- run 与 Judge 分离，输出 support/refute/inconclusive；
- 4 个 RWJT 任务：复现一个结果，再写对应中文核刊段落；
- 数字、图、结论必须绑 EA；未解析槽位阻止导出。

**交付标准：** 每个计分数字可追溯；伪造数字/引用 0 通过；人工复核一致率 ≥ 90%。

### 阶段 3：高质量写作与治理闭环（后期）

- 全局大纲评审 + section-level 局部修订；
- 多假设失败归因、证据准入、负结果保留；
- 证据压缩、权限注册表、waitpoint、任务恢复；
- 正式 benchmark 与人工盲评。

**交付标准：** 形成可重复的评测报告，能够说明系统在哪些任务上真的更好。

## 9. 结论

当前项目已经完成了从“演示壳”到“可运行证据底座”的阶段跃迁：

- 有一条能跑通、能展示、能产出报告与工作稿的主链；
- 有 claim/EA/closure 和人工门，不把“写得像”当成“是真的”；
- 有 runtime、持久化、静态审计和功能接线测试，工程上开始可维护；
- 但距离“高质量文章/实验”还差真实全文、引用支持、独立判定与正式评测。

**下一阶段最重要的不是再加十个功能，而是把“证据入口、引用支持、独立评测”三件事做扎实。**
