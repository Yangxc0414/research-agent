# 52 独立评审：从"披露同一模型"到"可解除的单作者状态"

> 状态：已实现并在本机用宿主 Agent（Qoder）作为全部生成供给跑通一次真实评审。
> 代码：`research_agent/independence.py`、`research_agent/innovation_review.py`、
> `research_agent/model_catalog.py`、`research_agent/host_model.py`、
> `research_agent/runtime/app.py`、`apps/web/src/components/HostModelPanel.tsx`。
> 规格：`modules/idea/SPEC.md` v0.12.0、`modules/host-model/SPEC.md` v0.2.0、
> `modules/integration/SPEC.md` v0.17.0。
> 证据：`runtime_data/independence-demo/out/innovation-review.json`
> （sha256 前缀 `1120fa8e331cad36`，schema `innovation-review-0.2`）。

## 1. 问题：披露是诚实的，但它不可解除

`50-` 与 `51-` 记录的实测结果是：novelty / evidence / feasibility 三个"审稿人"在
Host-as-Model 下由**同一个宿主模型顺序回答**，而且只把阈值从 8 挪动就能让结论从
`needs_more_work` 变成 `reviewed`。当时的修复是**披露**——给产物加 `independence` 区块，
写死 `admission_eligible=false`，并在写作提示词里禁止把三角色说成三位独立审稿人。

披露解决了"不撒谎"，但留下三个结构性问题：

1. **不可解除**：系统里没有任何一条路径能让 `admission_eligible` 变真，所以它实际上是一个
   常量；诚实的常量没有信息量。
2. **归因缺失**：产物只记录了 `distinct_model_ids=[一个]`，没有记录**每一条分数是谁给的**，
   事后无法审计。
3. **配置即可骗**：如果要解除，最自然的做法是"绑三个 profile"——但三个 profile 可以指向
   同一个模型，于是"解除"会变成一次配置编辑。

## 2. 设计：供给指纹 + 两条独立的判定层

**供给（supply）= (provider_id, model_name)**，不是 profile_id。

| 层 | 判据 | 能拒绝什么 | 不能证明什么 |
| --- | --- | --- | --- |
| 配置层 | 每个角色绑定可解析的 provider+model 指纹；三者互不相同；提案模型不在审稿席 | 一个模型戴三顶帽子；提案者给自己打分；profile 数量造假（同 model 只算一个供给） | 输出是否真的不同；训练语料是否重叠 |
| 使用层 | 宿主交接的 `host_label` 由**账本**回读，不是绑定时自报 | 配置上三个 profile，实际上同一个宿主 Agent 回答了全部批评角色 | 不同宿主的答案是否独立 |

关键取舍：**使用层能否决配置层，配置层不能免除使用层**。面板只有在两层都不反对时才写
`admission_eligible=true`；而且 `kind` 会把"provider 也分散"和"只有 model 名不同"分开报，
避免共享供应商的三模型被读成三家审稿。

`reasons` 是给人看的拒绝理由，`boundary` 说明这套判定自身的限度：

```
supply fingerprints are caller-declared gateway configuration plus ledger host labels where a
host agent answered: distinct provider and model ids make a panel structurally independent but
do not prove independent outputs, disagreeing error modes or a different training corpus, and an
admission-eligible panel still validates nothing about novelty, correctness or G1/G2.
```

**拒绝路径**（这是本项目一贯的做法：每个字段都必须有能让它失败的条件）：

- 角色指纹不可解析 → `kind=unverifiable`，拒绝承认；
- 两角色共享供给 → `reasons` 指出"N 个角色共享"；
- 提案模型兼任审稿 → `proposer_is_critic=true` + "author bias is uncontrolled"；
- 全部批评由同一宿主回答 → `admission_eligible=false`，即使配置完全合规；
- 面板不可成席时 `--independent` **直接失败并说明缺几个供给**，不静默回落成单作者评审。

## 3. 顺带修掉的三个真实缺陷

做"归因"时撞到三个既有 bug，都不是为评审特设的：

1. **重放范围错**：`find_by_hash(sha)` 在全账本查找。同一提示词发给两个批评供给时，第二个
   会**复用第一个的答案**，于是"两个独立审稿人"实际是同一份文字。现在按
   `find_by_hash(sha, profile_id)` 限定，同一 profile 才重放。
2. **catalog 不遵守配置**：`profile_catalog(None)` 走 `GatewayStore()`（内建默认），
   而 CLI/MCP 走 `RESEARCH_AGENT_MODEL_STORE`。同一台机器上两处看到不同的模型清单——
   面板会基于错误的清单建议审稿席。现在统一走 `default_store_path()`。
3. **宿主交接在 CLI 里是 traceback**：`ModelTurnPending` 没被 CLI 捕获，`innovation review`
   在无 key 模式下直接抛栈。现在 `main()` 统一处理为**交接提示 + exit 3**（与
   `scripts/host_model_loop_test.py` 的"需要宿主回答"信号一致），语义是"去回答，再重跑同一条命令"。

## 4. 实测：配置合规，仍被拒绝承认独立

绑定四个 host profile（提案 `host_proposer` + 三个 `model` 互不相同的批评 profile），
用 Qoder 作为唯一的宿主 Agent 回答全部交接：

```
kind=model_only  eligible=False  single_author=False
distinct_supplies=3  providers=['host-agent']  models=[qoder-critic-a, qoder-critic-b, qoder-critic-c]
reasons=['the ledger attributes every critic turn to one host agent (Qoder Desktop),
         so distinct profile configs did not produce distinct reviewers']
answered_by={'novelty': ['Qoder Desktop'], 'evidence': ['Qoder Desktop'], 'feasibility': ['Qoder Desktop']}
review supplies=[(novelty, host_crit_a, qoder-critic-a), (evidence, host_crit_b, qoder-critic-b),
                 (feasibility, host_crit_c, qoder-critic-c)]
status=needs_more_work  ranking=[IDEA-01 7.667, IDEA-03 7.667, IDEA-02 6.0]  validation_warnings=0
```

这一条结果值得单独说清楚：

- **`single_author_review` 被解除了**，`distinct_supplies=3`，`proposer_is_critic=false`；
- **但 `admission_eligible` 仍然是 false**，因为账本说这三次批评都由 `Qoder Desktop` 回答；
- 也就是说，把这条路径写成"绑三个 profile 就独立了"是错的，而系统自己拒绝了这种写法。
  这是本项目里少见的"实现完成后被自己的验证层判负"的例子，所以我把它原样留下，不去改成绿灯。

要真正解除需要两个条件同时成立：三个互不相同的 provider+model 供给，且它们不是同一个宿主 Agent。
`--independent` 会在供给不足时失败并报告缺几个，`GET /api/host-model/panel` 会把可成席情况
（含 `suggested` 角色→profile、`distinct_supplies`、`missing_supplies`、`proposer_excluded`）
直接暴露给页面与宿主 Agent。

顺带可复用的效果：本轮 4 个缺口 + 5 个想法全部通过确定性校验（`validation_warnings=0`），
说明 `51-` 引入的可执行面约束在真实内容上是可满足的，而不是只让模板产物通过。

### 同一次评审走 CLI 与走 MCP 是同一份字节

宿主 Agent 侧的入口同样验证过：通过真实 stdio MCP 调 `research_innovation_review`
（带 `critic_profiles`，指向同一 store 与同一 ledger），三个角色的 `supply` 与
`independence` 判定完全一致，写出的 `innovation-review.json` 与 CLI 产物
**逐字节相同**（sha256 前缀同为 `1120fa8e331cad36`，副本存于
`runtime_data/independence-demo/mcp-innovation-review.json`）。这不是巧合：交接按请求哈希重放，
所以两个入口消费的是同一批已回答的 turn，而不是重新问一遍模型。

同一轮检查还顺手修正了两处过时描述：`research_innovation_review` 原来写着
"Requires a configured DeepSeek key"、`research_manuscript_draft` 写着"Requires a model key"——
在 Host-as-Model 之后这两句都会把无 key 用户挡在门外，现在都改成"需要生成供给（网关 profile、
env key，或由本 Agent 作答的 keyless host_agent profile）"。

## 5. 页面上的呈现

`HostModelPanel` 增加 **评审面板 INDEPENDENCE** 区块：当前可区分供给数、三个角色各自落到哪个
profile（未成席显示"回落提案模型"）、提案模型是否在审稿席、每个供给的 provider/model/kind
（keyless 显示"宿主供给"），并把"排不了席就失败"的命令行原样写在卡上。它只读，不提供任何
签核/执行入口，符合 `runtime` 侧既有边界。

## 6. 与调研到的现有工作的差别

`49-` 的对照表里，假设锦标赛族与端到端论文族的多评审通常是**同一模型的多个 prompt**，
少数用多模型但不记录"谁给了哪一分"，也几乎不把评审独立性作为**产物字段**参与下游措辞。
本项目的差别是三条同时存在：

1. 供给指纹去重（同 model 的多个 profile 不算多个审稿人）；
2. 使用层归因（宿主回答者由账本回读，能否决配置层的结论）；
3. 判定结果直接约束写作（`admission_eligible` 决定稿件能不能说"独立评审"，
   不可解除时必须写出解除条件）。

## 7. 边界（不得越过这条线解读）

- `admission_eligible=true` 只说明**供给层与使用层都不反对**，不说明意见独立、不说明
  novelty 成立、不通过 G1/G2、不是同行评审；
- `host_label` 仍是自报的，本项目只把它用于**否决**（同一宿主），不用于**证明**（不同宿主
  就一定独立）；
- 面板建议来自本地配置，不含任何网络探测；`has_key` 不代表该模型可达或有质量；
- 本文的实测由**一个宿主 Agent** 完成，因此它的价值在于"系统正确地拒绝了"，
  而不是"我们做出了独立评审"。

## 8. 复现

```bash
export RESEARCH_AGENT_MODEL_STORE=runtime_data/independence-demo/store.json
export RESEARCH_AGENT_HOST_MODEL_LEDGER=runtime_data/independence-demo/ledger.json
python -m research_agent host-model bind --profile host_proposer --model qoder-proposer --modules idea
for p in a b c; do
  python -m research_agent host-model bind --profile host_crit_$p --model qoder-critic-$p --modules ""
done
python -m research_agent innovation review --project runtime_data/topconf-research-2026 \
  --run-id RUN-20261026T122616Z-a13294 --rounds 1 --output-dir runtime_data/independence-demo/out \
  --critic novelty=host_crit_a --critic evidence=host_crit_b --critic feasibility=host_crit_c
# exit 3：按提示回答 MT-* 交接（host-model turns / respond）后重跑同一条命令
python -m research_agent innovation review --project <项目> --run-id <RUN> --independent   # 面板排席
python -m pytest tests/test_review_independence.py tests/test_host_model.py tests/test_model_catalog.py
```

宿主 Agent 侧（真实 stdio MCP，同一条判定）：

```json
{"name": "research_innovation_review",
 "arguments": {"project_dir": "...", "run_id": "RUN-...", "rounds": 1,
   "critic_profiles": {"novelty": "host_crit_a", "evidence": "host_crit_b",
                       "feasibility": "host_crit_c"}}}
```

`independent=true` 会由 `critic_panel()` 排席：它只会挑网关里**已配置**的供给，因此如果面板里
有带 key 的 provider，被选中的角色会产生真实外部调用。只想留在零 key 路径上时，用
`--critic role=profile` 显式指定 host profile，或把带 key 的 profile 从 store 里移除。
