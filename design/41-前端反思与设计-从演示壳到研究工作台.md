# 41 · 前端反思与设计：从“卡片式演示壳”到“证据工作台”

> 审计日期：2026-10-25  
> 依据：当前 `apps/web` 的 `App / WelcomeHome / Conversation / ContextPanel / Composer / SettingsPage`、`tokens.css`/`layout.css`/`components.css`，以及截图 `101`、`103`、`106–112`。  
> 边界：本文是设计判断与规格，不是“已实现”；前端仍受静态 adapter 与后端 runtime 边界约束。

## 0. 判断先说

当前前端已经具备三件难得的东西：

1. **识别度**：淡蓝纸面、细线网格、Wellsring 字标、宋体标题与等宽标签，和通用 SaaS 模板拉开了距离；
2. **真实骨架**：欢迎页 → 任务 → 对话 → 右栏运行/证据 → 设置，信息架构完整；
3. **诚实标注**：SIM/STATIC、人工门、权限模式、证据边界都能在界面上被看见。

但进入任务后，界面开始“像仪表盘，而不像研究工作台”：

- 三栏都在争抢注意力：顶部任务头、右侧上下文、底部 Composer 都在重复状态与动作；
- 大量 5.8–9.5px 的功能性小字，尤其集中在标签、阶段、卡片的 metadata；
- 消息里堆了 plan/sources/idea/protocol/run/skill 等大卡片，对话被切成一块块面板；
- 证据链藏在右栏 tab 中，真正的研究对象（claim、span、EA、closure）没有成为主视图；
- 很多控件看起来像真的，但静态模式下只是本地状态；界面需要用更明确的“SIM/LIVE + 当前任务状态”来表达。

**设计方向建议：从“功能卡片陈列”转为“证据工作台（Evidence Desk）”。**

一句话：

> 对话是桌面，右栏是案卷，claim/EA/closure 是案卷里的证据页；不是把每个阶段做成一张大卡片。

## 1. 当前界面的具体问题

### 1.1 信息架构：三个控制面互相重复

以任务视图为例：

- 顶部任务头：工作区、阶段、`0/9 stages`、`active`、`ASK`、`GPT-5 · medium`、`EVIDENCE 0 spans · 0 gaps`；
- 右栏：`GOVERNED AUTO`、`IDLE`、`0/9 stages`、`BUDGET`、`HARNESS`、`STAGE TRACE`、`GATES`、`GUIDANCE QUEUE`；
- Composer：模式、权限、Skills、模型、建议动作。

同一组状态（阶段、运行、权限、模型、证据数）至少出现两次；用户需要先决定“看哪一栏”，而不是继续研究问题。  
**原则**：一个状态只在一个主位置出现，其他位置只做引用。

### 1.2 字号：功能性文字仍然过小

当前 CSS 中仍有大量小字号：

- 63 处 `7px`、44 处 `8px`、41 处 `6.5px`、34 处 `7.5px`、30 处 `6.8px`；
- 证据 ID、阶段名、工具名、门禁说明、右栏 metadata 大量落在 6–9px；
- 大卡片配 6–8px 小字，正是之前已经指出的“框大字小”问题。

这不是单纯的审美问题：在 1440 屏幕上，6–8px 的功能性文字很难读；在 390 手机上更接近不可读。  
**目标**：功能性文字下限 10px；正文 13px；关键标题 20–28px。不是把所有字号一起放大，而是**减少字号层级 + 减少标签数量**。

### 1.3 卡片：对话被切成“面板墙”

消息里同时存在 plan、sources、idea、protocol、run、gate、evolution、skill、skill-use、writing、tool 等卡片；每种卡片都有自己的 header、metadata、actions。  
结果是：

- 一条回答的视觉重量超过对话本身；
- 技能检查、阶段输出、证据对象看起来都像“同等重要的卡片”，没有主次；
- 卡片越多，越需要小字来塞信息，形成恶性循环。

**原则**：对话里只保留两类“大对象”：

1. **Decision artifact**：protocol、run、claim、closure——需要人做决定的对象；
2. **Receipt**：skill/tool/source 的调用凭证——一行或两行，可展开，不抢主叙事。

其他中间态（coverage、idea、plan）改成对话内的轻量行或右栏的当前对象。

### 1.4 颜色：蓝色承担了太多语义

当前蓝色同时用于品牌、主按钮、链接、选中 tab、阶段点、进度、焦点；teal/amber/coral 虽有定义，但语义没有统一。  
建议明确：

- 蓝色 = 主操作 / 当前焦点；
- teal = 已验证 / 已封存 / 可定位证据；
- amber = 人工门 / 待签署 / 待补；
- coral = blocked / stale / 失败；
- gray = SIM / 静态 / 未连接。

同一屏上主蓝色不超过 3 处；其他状态用色块/细线/文字，不再全部用蓝色按钮。

### 1.5 移动端：欢迎页很好，任务视图仍像压缩桌面

390 欢迎页的留白、品牌字标、单输入框是成立的；但任务视图仍是三栏压缩：顶部任务头、右栏抽屉、底部 Composer、Slash 菜单会覆盖大量内容。  
移动端应该是**单列研究工作台**：

- 标题 + 一行状态；
- 对话 + inline receipts；
- 底部固定 Composer；
- 右栏/命令/技能作为 bottom sheet，不并排。

### 1.6 动效：状态动效可以保留，装饰动效应减少

当前有品牌水印、线稿、阶段脉冲、卡片入场等。  
建议保留：

- 运行中的蓝色 live dot / 阶段脉冲；
- claim 人工门的 amber 呼吸；
- 新证据到达时的轻量高亮。

减少：

- 每张卡片的重复入场；
- 与状态无关的 hover 位移/渐变；
- 多处同时闪动。

## 2. 设计方向：Evidence Desk（证据工作台）

### 2.1 隐喻

不是“聊天 + 仪表盘”，而是**研究案卷**：

- 左侧：案卷柜（工作区/任务）；
- 中间：工作桌面（对话、当前问题、receipts）；
- 右侧：打开中的案卷（当前对象：source/span/claim/run/closure）；
- 顶部：案卷标签（任务、模式、SIM/LIVE、权限）；
- 底部：记录工具（composer、命令、模型）。

### 2.2 三个主面

| 面 | 职责 | 不做什么 |
| --- | --- | --- |
| 左栏 | 工作区/任务导航、最近任务、文件夹 | 不再放第二个功能宫格 |
| 中间 | 对话、inline receipts、decision artifacts | 不再为每个中间态放大卡片 |
| 右栏 | 当前对象的证据页、stage/gate 摘要 | 不再做第二个全量仪表盘 |
| Composer | 输入、命令、Skill、模型、权限 | 不再重复任务状态 |

## 3. 信息架构与线框

### 3.1 桌面（≥1280）

```text
┌──────────────────────────────────────────────────────────────┐
│ workspace / task        SIM · LIVE    access · model         │
├──────────┬──────────────────────────────────┬────────────────┤
│ 案卷柜    │ 任务头（标题 + 一行状态）          │ 案卷 / 当前对象  │
│ 248px    │                                  │ 320–360px      │
│          │ 对话                             │ ┌────────────┐ │
│ 工作区    │  · 用户问题                       │ │ Claim      │ │
│ 任务      │  · Agent 回答                     │ │ span → EA  │ │
│ 最近      │  · inline receipt（skill/tool）   │ │ gate       │ │
│          │  · decision artifact（claim/run） │ └────────────┘ │
│          │                                  │ Stage / Gate   │
│          │ Composer                         │                │
└──────────┴──────────────────────────────────┴────────────────┘
```

关键变化：

- 任务头只保留：标题、模式、阶段、SIM/LIVE、一个主状态；证据数/模型/权限移入右栏或 composer 的次级层。
- 右栏改为“当前对象”而不是四个并列 tab；默认展示与当前阶段最相关的对象。
- 右栏顶部可以保留 `RUN / EVIDENCE / EVAL` 三个入口，但 `EVOLUTION` 作为独立案卷/二级入口，不与证据争夺主位。
- 对话宽度增加：左栏 248、右栏 320–360，比当前 280 + 352 给中间更多空间。

### 3.2 移动（≤900）

```text
┌──────────────────────────┐
│ workspace / task · SIM   │
│ 标题 + 一行状态            │
├──────────────────────────┤
│ 对话 + inline receipts    │
│                          │
│ [当前对象 bottom sheet]   │
├──────────────────────────┤
│ Composer（固定）          │
└──────────────────────────┘
```

- 右栏 → bottom sheet：`当前对象 / 运行 / 证据` 三个入口；
- Slash/命令/技能菜单占满宽度，限制最大高度，避免遮住整屏；
- 任务头只保留标题 + 阶段 + SIM/LIVE；
- 建议动作在输入框上方单行，不换成两行。

## 4. 设计系统规格

### 4.1 字号（功能文字下限 10px）

| Token | 用途 | 大小 |
| --- | --- | --- |
| `--text-display` | 欢迎问候 / 大标题 | 28–32px |
| `--text-title` | 任务标题 | 20–22px |
| `--text-section` | 卡片/面板标题 | 15–16px |
| `--text-body` | 对话正文 | 13px / 1.65 |
| `--text-ui` | 按钮、输入、导航 | 12px |
| `--text-meta` | 标签、时间、ID、说明 | 10–11px |
| `--text-micro` | 仅限装饰性标记 | 9px（不得承载关键信息） |

规则：

- 任何“可操作/可理解”的文字不得低于 10px；
- 同一屏最多 4 个字号层级；
- 等宽字体只用于 ID、命令、指标、状态码，不用于整段说明；
- 全大写标签减少 60%，用 sentence case 代替；ID/状态码保留大写。

### 4.2 颜色（语义角色）

| Token | 值 | 语义 |
| --- | --- | --- |
| `--ink` | `#0E1B2E` | 正文/标题 |
| `--muted` | `#53657D` | 次级说明 |
| `--faint` | `#7E8FA6` | 元数据（不要用过浅的 #8B9BB0 承载说明） |
| `--paper` | `#F7FAFE` | 页面底色 |
| `--surface` | `#FFFFFF` | 内容面 |
| `--accent` | `#2563EB` | 主操作/焦点 |
| `--evidence` | `#0F8A9E` | span/EA/已验证 |
| `--human` | `#9A6B1E` | 人工门/待签署 |
| `--blocked` | `#D92D55` | blocked/stale/失败 |
| `--sim` | `#64748B` | SIM/静态/未连接 |

规则：

- 一个屏幕主蓝色不超过 3 处；
- 证据状态使用 teal，人工门使用 amber，失败使用 coral；
- 不再用蓝色渐变装饰所有卡片；渐变只保留品牌/欢迎页。

### 4.3 间距、圆角与阴影

- 间距：4 / 8 / 12 / 16 / 24 / 32；
- 圆角：`6 / 10 / 14`，同一层级只用一种；
- 边框：一条 `--line`；重要分隔用 `--line-strong`；
- 阴影：只用于浮层/抽屉（`--shadow-pop`），内联卡片不用阴影；
- 卡片 padding 与文字大小成比例：大卡片不能配 6–8px 小字。

### 4.4 动效

- 只保留状态动效：运行/暂停、阶段推进、人工门、证据到达；
- 时长 120–220ms，避免每张卡片重复入场；
- `prefers-reduced-motion` 下全部关闭非必要动效；
- 不做与状态无关的装饰性 hover 位移。

## 5. 组件重设计

### 5.1 Task Header

现在：kicker + 标题 + goal + 5 chips + evidence 行。  
改为：

```text
材料实验室 / RESEARCH · S1
钙钛矿界面钝化
调研 · 0/9 stages · ASK · GPT-5 medium        [SIM]
```

- 标题一行，状态一行；
- 证据数、模型、权限不再全部渲染成 chip；
- 右侧只有一个主操作（继续/签署/查看证据），其余进右栏；
- 阶段用细进度线，不用多个重复的 stage 数字。

### 5.2 Conversation 与 Receipt

- Agent 回答正文优先，卡片只保留 decision artifact；
- skill/tool/source 调用改成 inline receipt：

```text
↳ 文献速览 · 4 sources / 3 full text / 12 spans    [展开]
```

- receipt 展开后显示检查项和原因；
- 同一轮最多 1 个 receipt，避免堆叠；
- plan/sources/idea 不再各自成大卡，改为回答中的结构化行或右栏当前对象。

### 5.3 Case File（右栏）

- 顶部：当前对象名 + 类型 + 状态（claim/run/source/span）；
- 中部：证据链 `span → EA → claim → gate → closure`，用细线时间轴；
- 底部：与该对象相关的 1–2 个动作；
- 阶段列表和 gate 保留，但默认折叠，避免与当前对象争夺空间；
- `EVAL` 作为一个入口，不和证据对象混排；`EVOLUTION` 移入二级案卷。

### 5.4 Composer

- 第一行输入，第二行工具（模式/权限/模型/命令/Skills）；
- 建议动作只在空输入时出现；
- Slash 菜单分 `COMMANDS`/`SKILLS`（已实现），继续按状态过滤；
- 未来 `@agent` / `@file` 也在这里，作为“引用”而不是“新面板”；
- 发送按钮是唯一主操作，其他按钮降为 quiet。

### 5.5 Evidence Ledger（新增主视图）

在右栏或独立“证据”页提供：

| Claim | Scope | Span | EA | Gate | Closure |
| --- | --- | --- | --- | --- | --- |
| CLM-… | S5/… | 2 | EA-… | signed | blocked |

- 这是“证据运营”最该被看见的对象；
- 每一行可打开当前对象详情；
- 没有证据的 claim 不能伪装成“支持”。

### 5.6 Welcome

保留现有品牌水印、宋体问候、单输入框；只做减法：

- 减少重复的 `Skills` 计数与标签；
- 4 个 prompt chips 保留；
- 不增加新的卡片区；
- 移动端保持单输入框 + 底部工具栏。

## 6. 实施顺序

### Phase 0：设计落地审计（0.5–1 天）

- 做一次字号/颜色/圆角/阴影的 token 扫描；
- 列出所有 <10px 的功能文字；
- 选定 1440/1024/768/390 四个断点截图基线。

### Phase 1：排版与任务头（2–3 天，低风险）

- 建立字号/颜色 token，先替换任务头、Composer、右栏 metadata；
- 任务头减到“标题 + 一行状态 + 一个主操作”；
- 移除重复的 chips/标签；
- 所有功能性文字 ≥10px。

### Phase 2：对话与案卷（1 周）

- 对话卡片分层：decision artifact vs receipt；
- 右栏改为当前对象 + 证据链；
- 增加 Evidence Ledger；
- 移动端 bottom sheet。

### Phase 3：真实能力（持续）

- 接 runtime chat/tool loop；
- `@agent` / `@file`；
- 文件 diff/checkpoint；
- 会话 resume/clear。

## 7. 验收标准

- 1440/1024/768/390 无页面级横向溢出；
- 功能性文字 100% ≥10px，正文 13px；
- 一屏主蓝色 ≤3 处；证据/人工门/失败颜色语义一致；
- 任务头高度 ≤96px（1440），移动端 ≤120px；
- 同一轮对话最多 1 个 receipt + 1 个 decision artifact；
- 右栏默认只展示一个当前对象，不并列四个完整面板；
- 键盘焦点可见， drawers 有 focus trap，reduced-motion 生效；
- 所有 SIM/LIVE 状态在任务头/操作处可见，不把静态结果伪装成真实。

## 8. 不要做

- 不再增加新的全局面板/功能格/设置分节；
- 不把每个阶段都做成大卡片；
- 不用 6–8px 小字承载说明；
- 不把所有标签都做成全大写等宽字体；
- 不为了“像 Claude Code”而复刻终端 TUI、插件市场或完整 hooks；
- 不在静态 adapter 上伪装真实模型/工具执行。

## 9. 与 Claude Code 的关系

Claude Code 给我们的设计启示不是“终端外观”，而是：

- Command / Skill / Agent / Hook / Permission 分层；
- 渐进披露：metadata 常驻，正文按需；
- 工具调用是 inline trace，不是大卡片；
- 权限与人工门是界面的一等公民；
- 变更前后要有 diff/checkpoint 的对照。

对应到我们的工作台：

- Command/Skill 已分层；
- 权限已补只读门；
- 下一步应把 tool/skill receipt 做成 inline，把 claim/evidence 做成 Case File，而不是继续加卡片。

## 10. 结论

当前前端的美学方向是对的：淡蓝纸面、宋体标题、等宽证据标签，已经形成识别度。  
真正需要调整的是**信息密度与叙事重心**：

> 少一点仪表盘，多一点案卷；少一点 6–8px 标签，多一点可读的正文；少一点卡片，多一点证据链。

如果只能做一件事：先把任务视图从“三栏状态面板”收敛成“对话 + 当前案卷 + Composer”，并把功能性字号下限提到 10px。这会比再加十个功能更能让它像一个真正的科研工作台。

## 11. 第二轮反思：控制室与研究案卷的冲突

### 11.1 两套气质在同一次会话里断裂

- 欢迎页和设置页是**编辑部式**的：宋体标题、大留白、品牌字标、克制的线条（截图 97 / 100）；
- 任务页却变成**控制室**：顶部五个 chip、右侧四个 tab、九阶段 trace、gate 列表、空 guidance queue、密集 6–9px 标签（截图 106 / 110）。

用户从“开始一个研究问题”进入任务后，视觉语言从“案卷封面”突然切换成“机器面板”。这不是功能问题，是**产品人格断裂**。

建议：把编辑部气质带进任务页，但不把正文做成宋体：

- 任务标题、案卷标题、设置页大标题用宋体/衬线；
- 对话正文、按钮、表单用无衬线；
- 证据 ID、命令、状态码用等宽；
- 右侧案卷像“页边批注”，不是第二块仪表盘。

### 11.2 状态词汇过载

当前同一屏会同时出现：

`SIM / STATIC / LOCAL / SNAPSHOT / LOCAL DRAFT / LIVE RUNTIME / READY / ACTIVE / RUNNING / PAUSED / HUMAN GATE / NOT STARTED / NEEDS HUMAN / PENDING / BLOCKED / OK / PASS / WARN / PARTIAL / INSUFFICIENT / DEFERRED / STALE`

用户无法判断哪些是数据来源、哪些是任务状态、哪些是门禁、哪些是证据质量。建议固定四层词汇：

| 层 | 只用这些词 | 放在哪里 |
| --- | --- | --- |
| 数据来源 | `SIM / STATIC`、`LIVE / RUNTIME` | 任务头或顶部角标，只出现一次 |
| 任务状态 | `就绪 / 运行中 / 已暂停 / 待签 / 已完成` | 任务头一行 |
| 证据状态 | `空 / 部分 / 饱和 / 已过期` | 案卷当前对象 |
| 门禁状态 | `通过 / 待人工 / 阻塞 / 未开始` | 案卷 gate 行 |

原则：**同一状态只在一个层出现**；不要把 `0/9 stages` 同时放进任务头、右栏和对话卡片。英文只保留 `SIM`、`LIVE`、`GATE`、ID、命令等不可替代的代码。

### 11.3 右栏不是第二个仪表盘

截图 106/110 的右栏同时承担：

- RUN / EVIDENCE / EVOLUTION / EVAL 四个 tab；
- GOVERNED AUTO、BUDGET、HARNESS；
- 9 行 STAGE TRACE、NEXT S1；
- 5 个 GATES；
- 空 GUIDANCE QUEUE。

这使右栏在 352px 宽度里塞进了 6–9px 的功能文字，也让对话区变窄。建议：

1. **默认只显示“当前对象”**：claim / run / source / span 的证据链（span → EA → claim → gate → closure）；
2. **stage/gate 折叠成时间线**，默认只展开当前阶段与下一阶段；
3. **空 guidance queue 直接隐藏**，有 pending 才出现；
4. **EVOLUTION 降级为“实验室/改进”二级入口**，不与证据对象并列四个 tab；
5. **没有当前对象时显示“下一步”**，而不是四个空 tab。

### 11.4 Chrome 太多：三个品牌标记、重复动作

欢迎页同时有：

- 左上角产品 logo；
- 中央 `WA` 字标；
- 右侧竖排 `WELLSRING` 水印（截图 97）。

这是三个品牌标记。建议保留“左上 logo + 中央 WA”，删掉右侧竖排水印，或只在超宽屏/空状态显示。Chanel 的减法原则同样适用于品牌。

另外存在重复入口：

- 设置出现在顶栏和侧栏底部；
- 新会话出现在顶栏、侧栏“新建任务”和欢迎页；
- 文件预览出现在顶栏和侧栏工具条。

建议：每个动作只保留一个主入口，其他入口只在对应上下文出现。侧栏的“自动化 / 技能 / 插件”三格也建议收成一行“工具”，让任务列表成为侧栏主体。

### 11.5 英文大写标签过多

`RESEARCH / S1–S3`、`TASK`、`EVIDENCE`、`GOVERNED AUTO`、`STAGE TRACE`、`GATES`、`GUIDANCE QUEUE`、`BUDGET`、`HARNESS`、`NEXT S1` 全部以等宽大写出现，像技术演示而不是研究工作台。

建议：

- 标题、导航、按钮用中文；
- 等宽大写只保留给 ID、命令、状态码与阶段编号（`S1`、`G5`、`EA-…`、`SIM`）；
- 其他标签改为 sentence case 中文，例如“当前案卷”“下一步”“运行轨迹”“门禁”；
- 同一屏的全大写标签减少 60%。

### 11.6 多对象配置应沿用“模板 → 草稿 → 应用”

子智能体的批量新建（截图 113–115）已经证明了一个好的模式：

```text
模板组 → 待创建清单（可校对/改名/移除）→ 批量创建 → 可编辑
```

它比“重复点单条表单”更符合“组队”心智，也避免了把多个职责塞进一个 agent。这个模式可以复用到未来的：

- 检索覆盖方案（核心/综述/方法/评测/局限/近期六面向的 scout 组）；
- 插件/MCP 组合；
- 写作技能包；
- 评估任务组。

但注意：**创建不等于执行**。模板只展开白名单能力，不能变成任意 prompt/工具编排。

### 11.7 五个具体改动

如果继续做前端设计，建议按这个顺序：

1. **任务头只留一行状态**：标题 + 模式 + 阶段 + SIM/LIVE + 一个主操作；删除重复 evidence/chips。
2. **右栏改“当前案卷”**：默认当前对象 + 折叠时间线 + 空状态隐藏；四个 tab 降为三个，EVOLUTION 二级化。
3. **标题字体分层**：任务标题/案卷标题用宋体，正文/按钮用无衬线，ID/命令用等宽；只保留两个品牌标记。
4. **全站字号下限 10px**：先处理任务头、右栏、Composer、设置；同屏最多 4 个字号层级。
5. **收侧栏 chrome**：工具三格合成一行，任务列表上移；设置/新会话/文件预览各保留一个主入口。

### 11.8 不要做

- 不要为了“信息完整”继续把状态塞进右栏；右栏是案卷，不是数据库。
- 不要把所有标题都做成宋体；只在标题/案卷名用，正文仍要清晰。
- 不要把欢迎页的品牌水印全部删掉；保留一个记忆点即可。
- 不要为了“像 Claude Code”复刻终端 TUI；我们要的是案卷结构，不是终端外观。
- 不要只优化 1440；390 的移动端应该继续是单列 + bottom sheet，而不是压缩三栏。

### 11.9 第二轮结论

第一轮解决的是“卡片太多、证据埋在右栏”；第二轮要解决的是**产品人格断裂**：

> 欢迎页是案卷封面，任务页也应该是打开的案卷；不是从封面走进控制室。

最值得先做的一件事不是再加功能，而是：

> 任务头减到一行状态；右栏默认只展示当前案卷；空状态全部隐藏；中文标签取代大部分等宽大写。

这四步不会改变业务逻辑，却会让“科研工作台”这件事第一次在任务页成立。

## 12. 流程反思：一条研究主线的状态机

### 12.1 真实用户路径与当前断点

按当前前端实际走一遍：

| 步骤 | 用户动作 | 当前结果 | 真正该出现的下一步 | 现状 |
| --- | --- | --- | --- | --- |
| 1 | 提问/检索 | coverage 4/12/2，G1 needs_human | 收敛候选 | 有，但建议里混入“扩展检索” |
| 2 | 送入实验设计 | protocol 草案，G2 needs_human | 冻结协议 | 有 |
| 3 | 冻结协议 | G2 pass | 运行 3 seeds | 有 |
| 4 | 运行实验 | S5 pass，claim unsigned，G5 blocked | 签署 claim | 有 |
| 5 | 签署 claim | claim signed，G5 仍 blocked | **闭包检查** | **没有入口** |
| 6 | 生成写作槽位 | S12.related / limitations 仍 pending | **补齐引用/作者声明 → 闭包** | **没有入口** |
| 7 | 导出 | 只能下载工作区 JSON | **closure 通过后的证据包导出** | **没有治理导出** |

最关键的两个死点：

1. **签署之后没有 closure 入口**：`signClaim` 只把 G5 写成“claim 已签；closure 未运行”（`workspaceStore.ts:1939`），`ContextPanel` 的 S13 详情只显示原因，没有“运行闭包检查”按钮（`ContextPanel.tsx:305`）。
2. **闭包永远 9/11**：`writingCard` 的 `S12.related` 和 `S12.limitations` 永远是 pending（`seed.ts:213,218`）；全自动在 S13 也写死 “closure 9/11；citation.related 仍待补”（`workspaceStore.ts:715`），然后继续到 META，形成一个“必然失败但继续跑”的假流程。

另外两个逻辑不一致：

- `suggestionsFor` 是按 mode 而不是按状态生成：签署完成后如果仍在 experiment mode，会建议“运行 3 seeds”；如果切到 writing mode，会建议“生成写作槽位”；都不会建议 closure（`Composer.tsx:27-48`）。
- 顶部“导出当前状态”永远可用（`workspaceStore.ts:2557`），而界面同时说“导出锁定”；用户无法区分“工作区 JSON 快照”和“受治理的证据包导出”。

### 12.2 设计原则：一条主线，一个下一动作

把流程收敛成一条状态机：

```text
提问/接入 → 检索 → 收敛假设 → 设计协议 → 冻结 → 运行 → 签署 → 闭包 → 导出
                                                                    ↘ 写作/评估/自进化（支线）
```

每个状态必须有且只有：

```ts
interface FlowState {
  id: "intake" | "retrieve" | "converge" | "design" | "freeze"
    | "run" | "sign" | "close" | "export";
  status: "active" | "blocked" | "done";
  blockers: string[];
  nextAction: { label: string; kind: "primary" | "blocked" | "done"; hint: string };
}
```

这个 `FlowState` 由纯函数 `flowFor(task)` 计算一次，**Composer 建议、右栏按钮、命令可用性、阶段条**都读同一份结果，避免四处各算一套。

### 12.3 交互呈现

1. **下一动作条**：放在 Composer 上方固定一行，例如：
   ```text
   下一步 · 闭包检查   2 个未决项：citation.related / limitations   [运行闭包检查]
   ```
   这是整个任务唯一的主 CTA；其他动作收进“更多”或命令面板。
2. **流程条**：任务头下方一条紧凑的 7 步流程（检索/假设/协议/运行/签署/闭包/导出），当前步蓝色，阻塞步 amber，完成步 teal；移动端横向滚动。
3. **状态反馈**：每次动作后，除了卡片，还在对话里追加一条 system line：
   ```text
   S5b → 签署完成 · G5 仍未闭合 · 下一步：闭包检查
   ```
   用户不需要去右栏猜状态。
4. **闭包卡**：显示 11 项检查、未决项、每项需要的动作；只有 closure pass 后，才出现“导出证据包”。
5. **两种导出分开**：
   - 顶部“导出工作区 JSON”= 本地快照，随时可用；
   - 闭包后的“导出证据包（SIM/真实）”= 受治理导出，只由 closure 解锁。
6. **全自动遇阻即停**：S13 如果 closure 不可能通过，应停在 S13 并显示“缺 citation.related / 作者声明”，不要继续到 META 并宣告完成。

### 12.4 最小落地顺序

1. 先加 `domain/flow.ts` 的 `flowFor(task)`，替换 `suggestionsFor` 的模式判断；
2. 加 `closure.check` 前端动作与 `closure` 卡；即使当前只能返回 blocked，也要让阻塞可见、可解释；
3. 给 `S12.related` / `S12.limitations` 两个槽位提供“作者补齐（SIM）”或明确 disabled 的说明，避免永远 9/11；
4. closure pass 后开放“导出证据包”，并把顶部 JSON 导出改名为“导出工作区 JSON”；
5. 自动运行在 S13 blocked 时暂停，而不是继续到 META；
6. 最后再把流程条接到命令/右栏，保证四处读同一状态。

### 12.5 验收标准

- 任意状态都有下一步或明确 blocker，不存在“签完 claim 只能再检索”；
- 签署后的主建议一定是“闭包检查”，不是“再跑一次”；
- 闭包未通过时导出按钮明确 disabled，并说明缺什么；
- 闭包通过后存在一条可点的证据包导出路径；
- 全自动不会越过一个已知无法闭合的 S13；
- Skill/Agent 的调用只作为 receipt，不插入主流程步骤；
- 移动端下一动作条不超过两行，流程条可横向滚动。

### 12.6 一句话

> 当前流程不是“按钮不够”，而是**状态机没有闭环**：签署后没有闭包，闭包永远缺两个槽位，导出又没有区分工作区与证据包。先把 `flowFor(task)` 做成唯一事实源，再谈视觉。

### 12.7 线上实测（2026-10-25）：不是“不够清晰”，而是存在状态回退

在线上按 `/research → /experiment → /freeze → /run → /sign → /writing → /run` 实跑：

| 时点 | claim | G5 | Composer 主建议 |
| --- | --- | --- | --- |
| 签署后 | `signed` | `blocked`（closure 未运行） | **运行 3 seeds / 查看 EA / 查看证据链** |
| 生成写作槽位后 | `signed` | `blocked` | **生成写作槽位 / 检查证据边界 / 查看证据链** |
| 再次 `/run` 后 | **`unsigned`** | `blocked` | 生成写作槽位 / 去补证据 / 查看证据链 |

三个严重问题：

1. **签署后的 claim 会被重跑静默回退**。`runExperiment` 用固定 ID `CLAIM-014` 写入 `status="unsigned"`（`workspaceStore.ts:1901`），`withEvidence` 会替换同 ID 的已签 claim；界面只提示“EA 已封存”，没有告诉用户签名已失效。建议后的“运行 3 seeds”正好把用户引向这个回退。
2. **进度有三套来源**。`stage`、`completedStages`、`autoStages`、`mode` 由不同动作分别更新：生成写作槽位后 `stage=6`，但 `completedStages` 仍是 5 个；冻结协议后 `stage=2`；关闭全自动后 `completedStages` 与 `autoStages` 也可能不一致。任务头的 `x/9 stages` 因此只是一个近似值。
3. **建议不看真实状态**。`suggestionsFor` 只看 `task.mode`（`Composer.tsx:27`），所以签署后仍建议重跑；写作阶段仍建议再生成槽位，而不是闭包/导出。

另外：

- 全自动在 S13 写死 `closure 9/11`，仍继续到 META 并提示“全自动完成”（`workspaceStore.ts:715,738`）；
- `startAutoTask` 会过滤掉所有 claim（`workspaceStore.ts:913`），在已有签名 claim 的任务上启动全自动，等于静默删除签名；
- 顶部“导出当前状态”永远可用（`workspaceStore.ts:2557`），与“导出锁定”文案冲突。

结论：**不能称“整体逻辑清晰”。** 这不是视觉层的卡片问题，而是多个状态字段各自更新、动作之间没有不变量保护。

### 12.8 先修的状态不变量

在继续设计之前，先把这五条写成代码约束：

1. **已签 claim 不可被同 ID 覆盖**：重跑只能创建新的 claim draft，并显式 `supersedes` 旧 claim；旧签名保留，需重新签署。
2. **phase 与 mode 分离**：`mode` 是视图/入口（调研/实验/写作/全自动），`phase` 是流程状态（retrieve/converge/design/freeze/run/sign/close/export）；切换 mode 不改变 phase。
3. **进度单一事实源**：`stage/completedStages/autoStages` 由同一个 reducer 从 phase 派生，不允许四个动作各写一套。
4. **nextAction 由 flowFor(task) 计算**：Composer、右栏、命令、流程条读同一结果；禁止用 mode 猜下一步。
5. **closure/export 是显式状态**：没有 closure pass 就没有证据包导出；工作区 JSON 导出必须改名为“导出工作区 JSON”，不能冒充治理导出。

如果这五条不先落地，继续做视觉和流程条只会把矛盾藏得更深。
