## 0. 一页结论

**“把每个 claim 绑到证据”正在从差异化变成入场券。**

2026 年上半年，这句话还能撑起一个系统；到 2026 年 10 月，ScientistOne / CoE 已经在生成时强制 claim 追溯，Anti-Autoresearch / ARIS 已经能对第三方论文做证据审计，EditPropBench 已经在测“局部事实修改的非局部传播”，中文写作产品普遍宣称“证据链写作、零幻觉引用”。如果我们的产品仍然只卖“写的时候绑证据”，它会在第一时间被归入同一类工具。

真正稀缺的不是绑定，而是三件事：

1. **证据变化之后，稿件仍然站得住**：数据、代码、协议、引用、审稿意见变了，系统知道哪些 claim、句子、图失去支持，并给出“重跑 / 重写 / 复核”的处置。
2. **修复不是改一句话，而是重新闭合**：修复后重新跑门禁、重新生成图表、重新导出，并保留旧版本与变更理由。
3. **有人能签署**：作者/PI 知道哪些结论是条件化的、哪些证据是重跑得到的、AI 参与了什么；导出包能支持这个签署，而不是替人做决定。

因此，本文建议把产品从“证据链写作器”改定义为**证据运营工作台（Evidence Operations Workbench）**：

> 不是帮用户更快地写出一篇论文；而是让一篇论文在证据变化后，仍能被人负责地交付。

对应的新任务定义是 **RWMT（Reproduction–Writing Maintenance Task，复现—写作维护任务）**：给定一份已闭合稿件、一个变更集与预算，找出受影响的 claim/句/图，判定处置，执行或排队，重新过导出硬门，并产出一份可签署的变更报告。

**产品与研究的分工**：

- **产品旗舰**：存量稿件体检 + 变更影响 + 修复 + 重新导出（RWMT）。这是当前竞争密度较低、用户痛点更硬的一侧。
- **研究底座**：RWJT/ECM 的创建侧任务、R/W/J 与 C1/C2/C4，仍是论文 A 的内容；C3 从“支撑实验”升级为产品旗舰的核心证据。
- **实验顺序不变**：C2 仍是最便宜、最应先跑的实验；C3 是产品化投入最大的实验。**研究顺序 C2→C3，产品顺序 C3→C2**，两者不矛盾。
- **自进化层**：继续作为下游扩展，放在 Library/Governance，不作为首屏叙事。

**本文相对 [13-](13-创新点评审与主张收敛-需求对齐、开源对照与验证顺序.md) 的三个修正**：

1. 撤回“完整交集尚未见到”的强表述。ScientistOne/CoE 已经覆盖“写作时 claim 绑定 + 分数复现 + 引用核验 + 方法—代码对齐”的大部分；Anti-Autoresearch 已覆盖第三方论文的证据审计。剩余交集必须收窄为：**跨版本证据失效传播 + 三类处置 + 中文核刊/申报书体裁 + R/W 分开 + 人工签署导出包**。
2. “证据闭合”从主卖点降为**基础能力**；产品卖点改为“证据变化后的修复与签署”。
3. Demo 的问题不是“不够炫”，而是**演示的是概念片，不是工作台**：它没有稿件、运行胶囊、变更集、闭包报告与签署，用户无法完成一次真实的“体检—变更—修复—导出”。

## 1. 追补调研：证据链正在商品化

### 1.1 四个新邻近工作

| 工作 | 它做了什么 | 它覆盖了什么 | 它没有覆盖什么 | 证据等级 |
| --- | --- | --- | --- | --- |
| **ScientistOne / Chain-of-Evidence（CoE）**（arXiv 2605.26340v1） | 把科学 claim 分为引用、数值、方法、结论四类；生成 LaTeX 前强制 claim 验证；配套 CoE Integrity Audit 检查分数复现、规范违规、引用真实性、方法—代码对齐 | 生成时的证据绑定；数值/引用/方法/代码的一致性；对 75 篇论文、5 个系统、5 类任务的审计 | 已有稿件的跨版本维护；中文核刊/申报书体裁；R/W 分开的联合判定；作者侧修复工作流；资产/过程准入 | `[部分核验]`：arXiv 题名与摘要已核对；未读全文、未复现；其“零幻觉引用 0/337”等数字为作者口径 |
| **Anti-Autoresearch / ARIS integrity-forensics** | 输入 PDF / PDF+LaTeX / PDF+repo+results，构建 evidence ledger，跑一致性、引用取证、基线比较、实验取证、证明推导、评测设计等多维审计；确定性规则裁决；typed gate 可阻断投稿 | 第三方论文的事后审计；证据账本；可定位发现；投稿前自检 | 不跑 L3 复现；不负责修复；不把发现变成版本化稿件；不覆盖中文核刊体裁 | `[工程参考]`：读 GitHub README 与技能说明，未运行 |
| **EditPropBench**（arXiv 2605.02083） | 构造“局部事实编辑 → 非局部修订义务”的合成稿件与事实图，测 LLM 编辑是否把依赖句一起改掉；审计发现 37.2% 的近期 cs.CL benchmark/dataset 论文存在事实依赖的定性 claim | 编辑传播的测量；句级标签；非局部依赖 | 不是证据重跑；不判处置；不接导出；不覆盖中文长文 | `[部分核验]`：题名、摘要与 37.2% 来自 arXiv 摘要页检索结果，未读全文 |
| **中文“证据链写作”产品**（沁言学术、Writing Guard 等） | 宣称分级溯源、引用核验、证据漂移提示、目标期刊风格、格式适配 | 中文写作体验；引用与格式；部分证据漂移提示 | 多数停在“引用/文献”层，未接独立重跑、代码/数据快照、导出硬门；效果多为厂商口径 | `[厂商/项目口径]`：未实测，不引用其“零幻觉/100% 准确”数字 |

补充邻近工作：

- **When May an Agent Stop? Evidence-Carrying Termination**（arXiv 2608.23623）：把“停止”写成带证据的契约、账本与证书。它提醒我们：**导出不是排版动作，而是一次终止判定**；但它的对象是 agent 终止，不是中文稿件。
- **AI for Auto-Research: Roadmap & User Guide**（arXiv 2605.18661）：把 validation（peer review、rebuttal & revision）列为自主科研流程的一环，并讨论自动化系统在判断新颖性与评审上的局限。它支持本文的维护任务：**返修与修订不应停在文本层，而应回连到证据与稿件版本**；本文没有从该文取得“承诺—履行差距”的量化证据。
- **大规模复现审计报道**（2226 篇 ICML 论文，23% 主张送上复核台）：二手报道，只作市场信号，不作效果证据。它说明“AI 做审计员”已经从概念走向批量实践。

### 1.2 对这些工作的公平读法

- ScientistOne 不是“只会写”，它已经把“证据链”做成生成时的硬约束，并给出后验审计。**不能再把“写作时绑 claim”当首创。**
- Anti-Autoresearch 不是“只会查引用”，它有 evidence ledger 与多维审计，而且明确拒绝把审计做成“学术裁决”。**不能再把“事后审计”当空白。**
- EditPropBench 不是“只会改句子”，它把“局部修改的非局部传播”做成了可测任务。**不能再把“失效传播”当无人区。**
- 中文产品不是“只会润色”，它们已经在卖“证据链写作”。**不能再把“中文 + 引用溯源”当主创新。**

### 1.3 对 [13-](13-创新点评审与主张收敛-需求对齐、开源对照与验证顺序.md) §3 的修正

原文的判断是：“独立重跑 × 稿件写作 × 句/数字/图绑定 × 跨版本失效传播 × R/W/J 联合判定 × 中文核刊 × 导出硬门”的完整交集尚未见到。

按本轮检索，应改为：

> 在本轮公开材料与本地快照范围内，**“独立重跑 × 稿件写作 × 句/数字/图绑定 × 导出”** 已由 ScientistOne/CoE 接近覆盖；**“第三方审计 × 证据账本 × 可定位发现”** 已由 Anti-Autoresearch/ARIS 覆盖；**“局部编辑的非局部传播”** 已由 EditPropBench 测量。仍然较少见的是：**“跨版本证据失效传播 + 重跑/重写/复核三类处置 + 中文核刊/申报书体裁 + R/W 分开 + 人工签署导出包”** 的组合。

这不是文字游戏，而是研究策略的变化：

- 如果继续把主贡献写成“证据绑定 + 硬门”，审稿人只需指出 ScientistOne 已经做过。
- 如果把主贡献写成“证据变化后的维护任务与处置”，并给出与 EditPropBench/手工 diff/STALE 的对照，差异仍然成立，而且更贴近真实科研。
- 中文核刊/申报书是验证场，不是护城河；它能增加迁移难度，但不能单独支撑 novelty。

### 1.4 已经商品化 vs 仍然稀缺

| 能力 | 状态（2026-10） | 对我们的含义 |
| --- | --- | --- |
| 写作时 claim → 证据绑定 | 商品化：CoE、ARIS、中文产品都在做 | 只能作为基础能力，不能作为主卖点 |
| 引用存在性/元数据核验 | 商品化：ARIS citation-audit、中文工具、通用检索 | 不投入自研，接现成能力 |
| 数值与日志一致 | 接近商品化：CoE score verification、ARIS paper-claim-audit | 保留为硬门，但不宣称首创 |
| 独立干净重跑 | 稀缺：OpenRSI、PaperBenchX、RWVH 有机制，但未接稿件 | 保留，作为“证据强度”的来源 |
| 变更后的影响传播 | 学术上已被测量（EditPropBench），产品上未闭合 | 我们的机会：把测量变成处置与修复 |
| 修复后的重新闭合与签署 | 稀缺：审计工具多停在报告 | **产品核心** |
| 中文核刊/申报书体裁 + 版面锚点 | 叙事拥挤、执行稀缺 | 作为验证场与交付能力，不作为主创新 |
| 资产/过程准入与撤销传播 | 设计多、实测少（E7/E8 未跑） | 放扩展，不抢主线 |

**一句话**：绑定是入场券，重跑是证据强度，**传播—处置—修复—签署才是产品**。

## 2. 重读 01：五个判断、三个方向对产品的要求

### 2.1 五个判断 → 当前回应 → 产品含义 → 缺口

| 01 判断 | 当前工作回应 | 产品含义 | 现在缺什么 |
| --- | --- | --- | --- |
| 判断 1：程序自主 → 过程自主 | `11-` 的 EV1–EV4、租约、PF；demo 的候选账本、资产租约、过程反馈 | 产品要能回答“这次学到的跑法，下次凭什么加载” | 只有 SIM；没有跨轮真实对照；PF 与用户日常流程没有接上 |
| 判断 2：产出像论文 → 过程经得起复现 | `07-` 的 RWVH、三层可验证；demo 的 P4/P5/P7 | 产品的基本单位不是 PDF，而是“可重跑的运行 + 可追溯的句子” | 没有运行胶囊；没有真正的环境/seed/日志/产物浏览；三层复现只在侧栏文字里 |
| 判断 3：因果模型、干预、反事实脆弱 | demo 的“反事实探针”只是一段文字；P1 有信念概率变化 | 产品要能表达“在什么条件下成立、换一个条件会怎样” | 没有反事实运行、没有干预记录、没有信念状态机；这是 01 三个方向中覆盖最弱的一条 |
| 判断 4：多智能体功能分化，而非数量堆叠 | `09-` 的 13 个 Agent 角色、三权分离 | 产品要能看见“谁提议、谁执行、谁判定、谁签署” | demo 没有角色视图、没有签核、没有权限；三权分离只存在于架构文档 |
| 判断 5：科研记忆丰富，但类型间协调不清 | demo 的四类记忆、`04-` 的 claim/证据图 | 产品要能让四类记忆互相引用，而不是四个计数 | 记忆只是侧栏数字；没有检索、没有冲突边浏览、没有“这条记忆从哪来” |

**结论**：五个判断里，判断 2 与我们的证据闭合最同向；判断 1 是扩展；判断 3 是最大缺口；判断 4/5 是架构与交互问题，不是新研究点。

### 2.2 三个方向：B 是产品核心，A 是治理，C 是缺口

| 01 方向 | 我们的对应 | 产品角色 | 研究状态 |
| --- | --- | --- | --- |
| A 技能迁移的适用域判定 | `11-` 的护照、租约、pilot/拒绝复用；demo 的资产租约控制台 | 治理能力，放在 Library；不是首屏 | E7/E8 未跑；目前只能作扩展 |
| B 从实验运行到论文陈述的证据溯源 | RWJT/ECM、claim–run–artifact、G5、C3 | **产品核心**；但要从“溯源”升级为“维护” | C2/C3 未跑；C1/C4 未跑 |
| C 证据冲突下的信念修订与假设再激活 | demo P1 的三条信念概率变化，但没有后续动作 | **研究缺口**；可作为产品差异化：contested / underdetermined / reopened | 没有实验、没有状态机、没有评测 |

方向 C 值得单独强调。当前框架的 claim 状态基本是“confirmed / stale / blocked”，但真实科研里更常见的是：

- **contested**：两篇文献或两次运行给出相反方向；
- **underdetermined**：置信区间跨过门槛，不能支持也不能否定；
- **retired**：旧解释被新证据降权，但不删除；
- **reopened**：新证据让过去被否决的假设重新值得测试。

demo 已经在 P1 场景显示“信念 0.62 → 0.54、0.21 → 0.33、旧解释保留冲突”，这是正确的方向；但它只是**展示**，没有让用户执行“降权 / 保留 / 重开 / 退休”，也没有把这些状态传到 claim、稿件句与导出。补上这个状态机，既能回应 01 判断 3，也能形成与 ScientistOne/CoE 不同的产品体验：**不是把冲突平均掉，而是把冲突保留下来并管理。**

### 2.3 01 的主线二（多样性）为什么还没进入产品

01 的主线二关注“同质化监测 + 探索奖励 + 反事实证伪”。当前框架只有 Idea 发散/收敛与 Elo，没有：

- 机制簇覆盖度、主流相似度、群体趋同指标；
- 探索配额与组合选择；
- 多轮构思的分布漂移；
- 反事实/证伪实验规划。

这不是首发产品的必需项，但它是 01 两条主线中目前最空的一条。建议把它放在 P2：**先做“Idea 组合视图 + 机制簇/相似度两个指标”**，不做完整 DiversityBench；等 C2/C3 有结果后再决定是否独立成实验。

### 2.4 产品应押“过程可信 + 证据运营”，不是“更多 Agent”

01 的判断 4 已经说明：多智能体的价值在功能分化，不在数量。当前 demo 的 9 阶段、18 阶段、13 个角色已经足够多；继续加 Agent 不会产生差异化。真正缺的是：

- 一个用户能看懂、能操作、能签署的**工作台**；
- 一个能在变更后自动收缩的**证据图**；
- 一个能把“发现”变成“修复任务”的**处置队列**。

这也是本文把产品从“生成流水线”改为“证据运营”的原因。

## 3. 仓库与 Demo 的事实审计

### 3.1 仓库事实：文档多、可执行物少

截至 2026-10-20，仓库的实际构成是：

| 类别 | 数量/事实 | 含义 |
| --- | --- | --- |
| 设计文档 | 14 份 Markdown（含 README） | 需求、流水线、架构、验证、自进化、评审 |
| 可执行前端 | 1 个单文件 `demo/index.html`（约 4,832 行 / 284 KB） | 概念演示，不是产品 |
| 后端/运行时 | 无 | 没有 API、数据库、任务队列、Judge、评测代码 |
| 评测代码 | 无 | C1–C4 只有目标卡片，没有 harness |
| 开源快照 | 11 个项目 / 8,870 文件 / 361.3 MB | 只读参考，不是依赖 |
| 真实数据/任务 | 无 | demo 的 3 个领域均为手写 SIM 数据 |

这不是指责文档太多，而是要说清**主张与产物之间的距离**：

| 文档里的主张 | 仓库里的对应物 | 证据等级 |
| --- | --- | --- |
| Work/Judge、干净重跑、EA | 只有 `07-` 设计与 demo 的 P4/P5 文案 | `[设计]` |
| claim–run–artifact 契约 | 只有 `04-`/`09-` schema 与 demo 的 claim 图 | `[设计]` + `[SIM]` |
| 跨版本失效传播 | demo 只有一次数字篡改动画 | `[SIM]` |
| 中文核刊体裁/GB/T 7714 | demo 只有一条门禁文字 | `[设计]` |
| 自进化四问/租约/PF | demo 有交互，但全部是 SIM | `[SIM]` |
| R/W/J、C1–C4 | demo 有目标卡片，没有运行 | `[设计]` |
| 9 阶段/18 阶段/可调工作流 | demo 固定 9 阶段；18 阶段是另一张图 | `[SIM]` / 未实现 |

**结论**：当前最稀缺的不是第 15 份设计文档，而是**一个能跑通的最小产品纵切**。这份文档因此不再扩写流水线，而是定义“先做哪一刀”。

### 3.2 Demo 做对了什么

必须公平地承认，demo 不是空壳。它在几个关键点上是正确的：

1. **负结果与未判定不是失败**：`DOMAINS` 里明确有 `refuted` 与 `inconclusive`，并给出“不建结果 claim / 登记 open question”的处置（[demo/index.html:2518](demo/index.html#L2518)、[demo/index.html:2564](demo/index.html#L2564)、[demo/index.html:2578](demo/index.html#L2578)）。这比很多“只演示成功”的系统更接近科研。
2. **证据冲突不被平均**：P1 场景显示三条信念的概率变化与“保留冲突”（[demo/index.html:2532](demo/index.html#L2532)、[demo/index.html:2854](demo/index.html#L2854)）。这是 01 方向 C 的种子。
3. **换假设要回滚**：P3 之后切换主假设会回到 P2，并提示协议与判决需要重跑（[demo/index.html:3337](demo/index.html#L3337)）。这是“选择即承诺”的正确交互。
4. **篡改会传播并阻断导出**：数字从 3.2% 改到 5.1%，claim/句进入 stale，G5 阻断（[demo/index.html:1876](demo/index.html#L1876)）。这是全 demo 最接近产品的一刻。
5. **探索/确证分车道**：E 车道不进 Judge、不建 claim；C 车道只认 scored verdict 与 rerun EA（[demo/index.html:1893](demo/index.html#L1893)）。这是对“只认重跑”的清晰表达。
6. **过程协议与 claim 资产分开**：PF 面板回答“同一阶段下一次怎么跑”，并明确不改 claim（[demo/index.html:1607](demo/index.html#L1607)、[demo/index.html:4328](demo/index.html#L4328)）。
7. **SIM 标注诚实**：首屏、控制台、演化区、评估区都标注了模拟/未实测（[demo/index.html:1295](demo/index.html#L1295)、[demo/index.html:1354](demo/index.html#L1354)、[demo/index.html:1404](demo/index.html#L1404)、[demo/index.html:1934](demo/index.html#L1934)）。

这些优点应该保留，尤其是负结果、冲突、回滚与 fail-closed。

### 3.3 Demo 的结构性问题

#### 问题 1：它是概念片，不是工作台

demo 的“运行”是预写场景的切换：`PHASES` 固定 9 项（[demo/index.html:2727](demo/index.html#L2727)），`SCENES` 是 10 个固定 HTML 生成函数（[demo/index.html:3073](demo/index.html#L3073)），单步前进只是 `phase++`（[demo/index.html:3353](demo/index.html#L3353)）。用户不能：

- 输入自己的研究问题、上传稿件、接入代码/数据；
- 查看一条 claim 的完整上游（run → artifact → EA）；
- 编辑一句话并看到槽位变化；
- 导出任何东西；
- 邀请合作者、分配角色、签署。

`grep` 的事实很直接：`upload` 0 次、`docx` 0 次、`editor` 0 次、`textarea` 0 次、`contenteditable` 0 次、`协作` 0 次、`reviewer` 0 次。它没有“稿件编辑”这个产品最核心的表面。

#### 问题 2：三种阶段模型同时存在

- 首屏与控制台：9 阶段（P0–P8，[demo/index.html:1295](demo/index.html#L1295)、[demo/index.html:2727](demo/index.html#L2727)）；
- 全流程区：18 阶段 S0–S16（[demo/index.html:1709](demo/index.html#L1709)）；
- 过程反馈：另一套 9 阶段 PF（[demo/index.html:4328](demo/index.html#L4328)）。

三个模型各有道理，但放在同一个页面里，用户不知道“我现在在哪、下一步该点哪个”。产品需要一个**唯一的主对象模型**，其他都是视图。

#### 问题 3：没有“稿件”这个第一对象

demo 有 claim 图、有“写作与图表”场景、有“2 条 manuscript_claim”的文字（[demo/index.html:3066](demo/index.html#L3066)），但没有稿件正文、没有句子列表、没有段落/章节、没有版面锚点、没有 Word/LaTeX/PDF 预览。用户无法体验“这句话为什么不能导出”。

#### 问题 4：没有“运行胶囊”

P4 场景有柱状图、Run 1/Run 2、反事实探针（[demo/index.html:2936](demo/index.html#L2936)），但没有：

- 环境镜像 digest、依赖 lockfile、seed、硬件；
- 命令、日志、失败栈；
- 产物列表与 hash；
- verdict 的 rubric 细节；
- EA 的路径与来源；
- 成本与耗时。

没有这些，“可复现”仍然是一句文案。

#### 问题 5：没有“变更集”，只有一次篡改

demo 的唯一变更路径是“把 3.2% 改成 5.1%”（[demo/index.html:1876](demo/index.html#L1876)）。真实场景包括：

- 新数据替换旧数据；
- 代码修复导致指标变化；
- 协议/阈值变更；
- 审稿人要求补实验；
- 文献被撤稿或出现相反证据；
- 图表数据源变更。

不同变更的传播规则、处置选项与人工签核点不同。只演示“改数字”会把问题简化成“数字比对”。

#### 问题 6：没有闭包报告与签署

G5 是一张 8 项清单（[demo/index.html:1866](demo/index.html#L1866)），但没有生成一份可交付的“闭包报告”：结构闭合率、语义支持抽样、未解析项、stale 清单、人工签核、AI 使用记录、成本。产品交付物不是“通过/不通过”两个状态，而是**一份能解释为什么可以通过的报告**。

#### 问题 7：自进化抢了主线

`#evolution` 是页面最大的区块之一（[demo/index.html:1396](demo/index.html#L1396)），包含循环图、候选账本、周期继承、PF、资产租约、增益曲线。它设计得很好，但与 [13-](13-创新点评审与主张收敛-需求对齐、开源对照与验证顺序.md) 的结论冲突：主贡献是证据闭合，自进化是扩展。首屏用户看到的是“自进化”，不是“证据运营”。

#### 问题 8：可调工作流仍未实现

控制台固定 9 阶段（[demo/index.html:2727](demo/index.html#L2727)），没有模板选择、没有跳过阶段的证据权限变化、没有运行中改模板的签核。`13-` §8 已经给出设计，但 demo 没有体现。

#### 问题 9：评估区是静态卡片

C1–C4 的目标阈值、B0–B5/A1–A5 对照都写在页面上（[demo/index.html:1926](demo/index.html#L1926)），但没有任务集、没有运行、没有结果、没有 κ 工作流。它是“评测计划”，不是“评测工作台”。

#### 问题 10：缺少协作与责任

没有角色、权限、评论、签核、CRediT、AI 使用披露。A3 边界说“人保留最终责任”，但产品里没有承载责任的界面。

### 3.4 结论：demo 证明叙事，不证明能力

demo 证明了三件事：

1. 这个故事讲得通；
2. 证据闭合的关键交互可以被可视化；
3. 团队对 SIM 标注是诚实的。

它没有证明：

1. 系统能处理真实稿件与真实运行；
2. 变更传播在真实场景中召回足够高；
3. 用户愿意用、看得懂、签得下；
4. C1–C4 的任何一条。

下一步不应继续加动画，而应做**一个真实纵切**：一份稿件、一次变更、一条 claim、一个 run、一次修复、一次导出。

## 4. 产品定义：证据运营工作台

### 4.1 一句话与产品类别

**一句话**：

> Research Agent是一个证据运营工作台：它让每一句经验陈述都能追溯到一次独立重跑；当数据、代码、协议或引用发生变化时，它告诉你哪些句子、图和结论不再成立，并把修复、复核与签署串成一条可审计的流程。

**产品类别**：不是“AI 论文生成器”，不是“文献管理器的 AI 版”，也不是“通用写作工具”；而是 **Evidence Operations / Research Integrity Workbench**（证据运营 / 科研诚信工作台）。

**对外 tagline（候选）**：

- “数据变了，论文哪一句还成立？”
- “不是写得更快，而是交得更稳。”
- “每一句，都有一次重跑；每一次变更，都有一次处置。”

### 4.2 三个 jobs-to-be-done

| 用户任务 | 典型触发 | 现在怎么做 | 产品应该做什么 |
| --- | --- | --- | --- |
| **J1 新项目：从问题到可导出稿件** | 有了问题、代码、初步结果 | 手写 + 工具拼接 + 事后核对 | 冻结 TaskSpec、跑确证、建 claim、写稿、过 G5、导出 |
| **J2 存量稿件：体检与修复** | 已有 draft，准备投稿/返修 | 人工逐句核对、Excel、焦虑 | 导入稿件与材料，重建 claim 图，标出无证据/过期/冲突句，给修复队列 |
| **J3 变更：数据/代码/协议/引用变了** | 新数据、代码修复、审稿意见、撤稿 | 手工 diff、凭记忆改、容易漏 | 计算影响闭包，分派重跑/重写/复核，修复后重新闭合与导出 |

J1 是“创建”，J2/J3 是“维护”。**产品差异化在 J2/J3，不在 J1**；J1 是必要的入口与 testbed。

### 4.3 两种入口

| 入口 | 输入 | 输出 | 价值 | 优先级 |
| --- | --- | --- | --- | --- |
| **新建项目** | 研究问题、代码/数据快照、协议、目标体裁 | 可导出稿件 + 证据包 | 展示完整能力；RWJT 任务 | P0（可用简化版） |
| **存量稿件体检** | PDF/DOCX/LaTeX + 代码/数据 + 目标期刊模板 | 证据地图 + 问题清单 + 修复计划 | 更贴近真实用户；与审计类工具差异化在“修复” | **P0（产品楔子）** |
| **变更维护** | 已闭合稿件 + 变更集 | 影响清单 + 处置 + 新版本 + 闭包报告 | 最高频、最痛；C3 的产品化 | **P0（核心）** |

### 4.4 核心循环

```
捕获证据 → 判定 → 建 claim → 写作绑定 → 闭合检查 → 签署导出
                ↑                                      │
                └──── 变更集 ← 影响分析 ← 修复/重跑 ←──┘
```

展开为六步：

1. **Detect**：接收变更（新 run、新数据、代码 diff、协议修订、审稿意见、引用撤稿）。
2. **Impact**：沿 `depends_on / derived_from / supports / cites` 计算受影响 claim、句、图、表。
3. **Triage**：为每个受影响项给出处置：`rerun` / `rewrite` / `recheck`；不能自动判定的进入人工队列。
4. **Repair**：执行重跑或改写；改写只能降低/限定 claim 强度，不能新增结论；重跑必须走确证车道。
5. **Re-close**：重新检查槽位、数字、引用、图表、结构、证据包；更新闭包报告。
6. **Sign**：作者/PI 签署；记录 AI 使用、未解决项、限制与版本；导出新版本，旧版本保留。

这个循环的产品对象是 **ChangeSet**，不是文档。文档只是循环的终点。

### 4.5 与邻近系统的差异

| 维度 | ScientistOne / CoE | Anti-Autoresearch / ARIS | EditPropBench | 中文写作工具 | Research Agent（目标态） |
| --- | --- | --- | --- | --- | --- |
| 介入时点 | 生成时 | 投稿前/事后审计 | 编辑后传播评测 | 写作时 | 生成时 + 变更后 + 导出前 |
| 证据来源 | 检索、实验日志、代码 | 论文自身 + 外部文献 + 可选 repo | 合成事实图 | 文献引用 | 独立重跑 EA + 文献 span + 代码/数据快照 |
| 发现后的动作 | 删除/重写 claim | 报告/flag | 度量传播 | 改写/润色 | **重跑/重写/复核处置队列 + 版本化修复** |
| 输出 | 论文 + 审计 | 审计报告 | benchmark | 稿件 | **可签署导出包 + 闭包报告 + 变更记录** |
| 人类角色 | 系统自动 | 审计者 | 研究者 | 作者 | **PI/作者签核，AI 使用披露** |
| 体裁 | 英文 ML | 英文论文 | 英文 ML/NLP | 中文通用 | 中文核刊/申报书 + 英文对照 |
| 复用治理 | 无 | 无 | 无 | 无 | 资产/过程租约（扩展，未验证） |

**读法**：ScientistOne 是最接近的正面竞争者；我们不在“生成时绑定”上竞争，而在“变更后维护 + 签署”上竞争。Anti-Autoresearch 是最接近的审计者；我们不在“发现问题”上竞争，而在“修复到可导出”上竞争。

### 4.6 不做什么

- 不做通用聊天/写作助手；
- 不做“一键生成整篇论文并自动投稿”；
- 不做假同行评审、代写、代投；
- 不做 AIGC 检测规避；
- 不做湿实验执行（P2 另议）；
- 不在 v1 做多租户 RBAC、图数据库、微服务；
- 不把“引用数量/字数/生成速度”当核心指标。

### 4.7 护城河在哪里

不是模型，也不是流程数量。护城河是四样东西的复利：

1. **契约**：claim–run–artifact–sentence–export 的稳定 schema；
2. **证据图**：用户每次项目积累的 claim/run/变更/处置，越用越厚；
3. **体裁与模板**：中文核刊/申报书的章节义务、版面锚点、GB/T 7714、期刊/基金模板；
4. **审计轨迹与人的签署**：谁在什么时候、基于什么证据、批准了什么。

模型会商品化，流程会被复制；**历史证据图与签署记录**不会一夜之间被复制。

## 5. 当前框架缺少的六个对象与六个回路

这是本文对“补充现在缺少的”最直接的回答。当前框架有 claim、证据图、租约、门禁，但缺少让这些机制变成产品的**对象**和**回路**。

### 5.1 六个缺失对象

| 对象 | 为什么必须有 | 最小字段 | 产品表面 | 验收 |
| --- | --- | --- | --- | --- |
| **Manuscript / SentenceSlot** | 用户交付的是稿件，不是 claim 图；没有句子就没有“哪一句不成立” | `manuscript_id / version / section / sentence_id / text / claim_id / slots[] / status` | 稿件工作台；句级 provenance；未解析槽位高亮 | 任一句可点开到 claim → run → EA；未解析槽位阻止导出 |
| **RunCapsule** | “可复现”必须能被人打开看，而不是一句口号 | `run_id / task_spec / env_digest / seed / code_snapshot / data_snapshot / command / logs / artifacts[] / verdict / EA / cost / operator` | 运行详情页；重跑按钮；失败栈 | 任一计分数字能在 3 次点击内追溯到 run + EA |
| **ChangeSet** | 没有变更对象，传播就只是一次性动画 | `change_id / type / before / after / source / affected_claims[] / affected_sentences[] / affected_figures[] / dispositions[]` | 变更 cockpit；影响图；处置队列 | 每类变更都有影响清单与处置；不能空着导出 |
| **ClosureReport** | 导出不是“通过/不通过”，而是可解释的交付物 | `closure_id / structural_rate / semantic_audit / unresolved[] / stale[] / human_signoff / ai_usage / cost / version` | 导出前报告；随包导出 | 报告能解释每个阻断项与放行项 |
| **Actor / Signature** | A3 边界要求人负责；没有签署就没有责任链 | `actor_id / role / scope / decision / timestamp / evidence_refs / ai_disclosure` | 角色切换；签核；审计事件 | 导出必须有作者/PI 签署；AI 使用可披露 |
| **CostLedger** | 闭合有成本；不记成本就无法证明“值得” | `project_id / run_cost / model_cost / human_minutes / storage / total_per_claim` | 项目成本条；单 claim 成本 | 每个 run 与每次修复都有成本；能算“每 claim 成本” |

**为什么是这六个**：它们分别对应“交付物、证据、变化、解释、责任、代价”。缺任何一个，产品都退化成一个演示或一个审计报告。

### 5.2 六个缺失回路

| 回路 | 对应 01/13 | 最小实现 | 研究价值 | 优先级 |
| --- | --- | --- | --- | --- |
| **L1 导入—重建—体检** | 01 方向 B；产品 J2 | 导入 PDF/LaTeX + 代码/数据；抽 claim；对齐证据；标出无证据/过期/冲突 | 形成“存量稿件”任务集；可做用户研究 | **P0** |
| **L2 变更—影响—处置—修复—重闭合** | C3；产品 J3 | ChangeSet + 影响闭包 + 三类处置 + 修复 + G5 重跑 | C3 的核心 testbed；与 EditPropBench/手工 diff 对照 | **P0** |
| **L3 语义支持审计** | 13 §5.4 | 结构闭合之外，抽样专家判“claim 是否真的支持该句”；报告一致性与分歧 | 防止“槽位对了、意思错了”；C1/C4 的一部分 | **P1** |
| **L4 冲突—信念—重开/退休** | 01 方向 C；判断 3 | claim 状态机：contested / underdetermined / retired / reopened；冲突边；修订日志 | 新实验 E9；产品差异化 | **P1** |
| **L5 反馈质量—行动变化—协议准入** | 01 问题二；判断 1 | 反馈来源/质量标记；扰动反馈测试；行动变化日志；PF 准入 | E7/E8 的前置；避免“反思文本不等于行动改变” | **P2** |
| **L6 组合—多样性—探索配额** | 01 主线二 | 机制簇、主流相似度、组合覆盖；Idea 组合视图 | E10；防止趋同 | **P2** |

| Actor/Signature | ● | ● | ● | ● | ○ | — |

● 直接依赖；○ 间接相关；— 不相关。读法：**L2 是产品主干，L1 是入口，L3/L4 是差异化，L5/L6 是研究扩展。**

## 6. 新任务定义：RWMT

### 6.1 定义

> **RWMT（Reproduction–Writing Maintenance Task）**：给定一份已闭合稿件 \(M_t\)、一个变更集 \(\Delta\) 与预算 \(B\)，产出 \(M_{t+1}\)，使得：
> 1. 所有受 \(\Delta\) 影响的 claim、句、图被识别；
> 2. 每个受影响项被赋予处置 `rerun` / `rewrite` / `recheck`，并说明理由；
> 3. 处置被执行或进入人工队列；
> 4. 导出硬门被重新评估；
> 5. 产出一份可签署的变更报告，记录旧版本、证据、AI 使用与未解决项。

### 6.2 任务契约（压缩版）

```json
{
  "task_id": "T-RWMT-001",
  "task_type": "repro_and_maintain",
  "input": {
    "manuscript": {"id": "MS-001", "version": "v3", "format": "latex"},
    "change_set": {
      "type": "data_replacement",
      "before": "sha256:...",
      "after": "sha256:...",
      "scope": ["dataset", "analysis_script"]
    },
    "evidence_bundle": ["runs", "artifacts", "verdicts", "figures", "ai_usage"],
    "budget": {"wall_clock_min": 60, "submissions": 3, "cost_cny": 30}
  },
  "output": {
    "affected": ["claims", "sentences", "figures"],
    "dispositions": [{"item": "CL-0044", "action": "rerun", "reason": "..."}],
    "manuscript_next": "v4",
    "closure_report": "signed",
    "unresolved": []
  },
  "constraints": {
    "rerun_only_for_numbers": true,
    "rewrite_cannot_add_claims": true,
    "unresolved_blocks_export": true,
    "human_signoff_required": true
  }
}
```

### 6.3 与 RWJT、EditPropBench、CoE 的区别

| 维度 | RWJT | RWMT | EditPropBench | ScientistOne / CoE |
| --- | --- | --- | --- | --- |
| 起点 | 问题 + 代码/数据 + 协议 | 已闭合稿件 + 变更集 | 合成稿件 + 事实编辑 | 问题 + 检索 + 实验 |
| 核心动作 | 复现 + 写作 | 影响分析 + 处置 + 修复 + 重闭合 | 测编辑传播 | 生成时绑证据 + 审计 |
| 证据来源 | 独立重跑 | 既有 run + 新 run + 文献 span | 合成事实图 | 实验日志 + 代码 + 文献 |
| 输出 | 可导出稿件 | 新版本 + 闭包报告 | benchmark 分数 | 论文 + 审计 |
| 人的角色 | 终审 | 签核处置与版本 | 研究者 | 系统自动 |
| 我们的差异 | 已有设计 | **本文新增，产品旗舰** | 可作 C3 基线 | 最近的正面竞争者 |

### 6.4 指标

RWMT 的主指标不是“写得好不好”，而是“维护得对不对、快不快、可不可签”：

| 指标 | 定义 | 目标（待预注册） |
| --- | --- | --- |
| 影响召回 | 真正受影响的 claim/句/图被找出的比例 | ≥ 85% |
| 误报率 | 被标受影响但实际未受影响的比例 | ≤ 20% |
| 处置准确率 | 处置类型（重跑/重写/复核）与专家判断一致 | ≥ 80% |
| 修复完成率 | 受影响项在预算内被修复或明确挂起的比例 | ≥ 80% |
| 重新闭合率 | 修复后通过 G5 的比例 | 100%（未通过必须阻断） |
| 人工干预次数 | 每个变更集需要人处理的次数 | 越低越好，但不得以少做规避 |
| 时间到影响清单 | 从变更到给出影响清单的墙钟时间 | 目标 ≤ 10 min（未实测） |
| 每变更成本 | 模型 + 计算 + 人工 | 记录，不先设目标 |
| 签署可解释性 | 作者能否在 5 分钟内解释每个放行/阻断项 | 用户研究 |

### 6.5 C3 的实验设计（升级版）

| 项 | 设计 |
| --- | --- |
| 任务 | 15–20 个变更场景，覆盖数据替换、代码修复、协议变更、引用撤稿、审稿意见、图表数据源变更 |
| 材料 | 3–5 篇真实论文（有代码/数据）+ 10–15 个合成变更；合成变更必须有事实图与句级标签 |
| 基线 | B1 手工 diff + 关键词搜索；B2 事后审计（ARIS/Anti-Autoresearch 式）；B3 STALE/哈希失效；B4 EditPropBench 式 LLM 编辑传播；B5 我们的影响闭包 + 处置 |
| 指标 | 召回、误报、处置准确、修复完成、重新闭合、人工干预、时间、成本 |
| 评审 | 2 位领域专家抽样判“影响判断 + 处置”是否正确；报告分歧 |
| Kill | 召回 < 70%，或比手工 diff 只高 < 10pp，或处置准确 < 60%，或成本调整后无优势 |
| 产出 | C3 论文；产品 K3 的验收；`13-` §9 的 C3 门槛（≥85%/≤20%/≥80%）需要按真实材料重估 |

### 6.6 对论文轨道的影响

[13-](13-创新点评审与主张收敛-需求对齐、开源对照与验证顺序.md) §6.4 的默认结构是 Paper A（RWJT）旗舰、Paper B（传播）第二。按本轮竞争态势，有两个选项：

| 选项 | 旗舰 | 优点 | 风险 | 适用 |
| --- | --- | --- | --- | --- |
| **A（维持 13-）** | Paper A：RWJT/ECM + C1/C2/C4 | 任务定义完整；创建侧故事清楚 | “证据绑定”已被 ScientistOne 覆盖；审稿人会问差异 | 团队大、能跑 κ、想做 benchmark |
| **B（本文建议的产品侧）** | Paper B：RWMT + C3 | 差异更窄、更硬；与产品楔子一致；真实用户痛点 | 需要真实稿件与变更材料；C3 实验更贵；RWJT 变成 testbed | 单人/小队、产品优先、想避开正面竞争 |

**建议**：

- **Paper C（自进化）** 继续后置，E7/E8 未跑前不立项。

### 7.3 三幕交互

#### 第一幕：体检

- 预载一份中文核刊稿件（不是上传，避免 demo 依赖后端），标注“样例”。
- 系统抽取 12–20 条 claim，映射到 3–5 个 run、2 个图、1 个文献集。
- 仪表显示：结构闭合 78%、语义抽样待做、2 条无证据句、1 条 stale、1 条 contested。
- 用户点击一条无证据句 → 抽屉显示“缺 R 槽；可用 run-0342 补，或降级为限制句”。
- 目的：让用户第一次看到“稿件可以被这样读”。

#### 第二幕：变更

- 用户选择一个 ChangeSet：`数据集 v2 替换 v1`（或“代码修复：seed 对齐”）。
- 影响图动画：数据集 → 3 个 run → 2 条 result claim → 4 句 → 1 图。
- 处置队列：2 条重跑、1 条重写、1 条复核；每条有理由与预算。
- 用户点击“执行重跑” → 模拟 run 完成 → 数字变化 → claim 更新 → 句子变 stale → G5 阻断。
- 用户选择“把结论降级为条件化表述” → 句子修复 → 重新检查 → G5 放行。
- 目的：让用户看到“变更不是改一句话，而是一条链”。

#### 第三幕：签署

- 导出前报告：结构闭合 100%、语义抽样 2/20 待专家、0 个未解析槽、1 个已挂起限制。
- 角色切换：作者 → PI；PI 看到“哪些结论是条件化的、哪些证据是重跑的、AI 使用了什么”。
- 签署 → 生成导出包：稿件、claim 图、run 胶囊、图包、闭包报告、AI 使用记录、变更记录。
- 目的：让用户看到“交付物不是 PDF，而是一个可审计包”。

3. **做一个句级 provenance 抽屉**：点一句话，看到 claim → run → EA → artifact；看不到就说明数据模型不对。

### 8.4 里程碑与 kill criteria

| 里程碑 | 通过条件 | 不通过怎么办 |
| --- | --- | --- |
| M0 对象模型 | 一份稿件、3 个 run、12 条 claim、10 个句、1 个变更可串起来 | 缩到 1 个 run、3 条 claim，先把链路跑通 |
| M1 体检 | 3 份真实稿件能抽出可定位 claim；问题清单有人认可 | 缩到 1 份；先做“结果句”不做全文 |
| M2 变更 | 10 个变更场景召回 ≥70%、处置准确 ≥60% | 收窄到“结果数字→摘要句/图” |
| M3 签署 | 导出包能解释每个阻断/放行；作者愿签 | 先做“闭包报告”，不做完整导出 |
| M4 C2 | 无证据句相对下降 ≥30%；伪造通过 0 | 硬门降为工程贡献；转 C3 |
| M5 C3 | 召回 ≥70%、误报 ≤30%、优于手工 diff | 收窄场景；不宣称通用传播 |

## 9. 风险与止损

### 9.1 产品风险

| 风险 | 信号 | 缓解 |
| --- | --- | --- |
| **正面竞争**：ScientistOne/CoE 继续扩展到维护侧 | 对方发布“revision/repair”功能 | 把差异锁在中文体裁 + 处置 + 签署；加快真实用户案例 |
| **审计商品化**：ARIS/Anti-Autoresearch 免费且够用 | 用户说“审计用现成的就行” | 不比“发现问题”，比“修复到可导出” |
| **中文写作工具下沉** | 厂商把“证据链”做成标配 | 用独立重跑与代码/数据证据建立不可替代性；不靠引用数量 |
| **导入解析太难** | PDF/LaTeX 抽取 claim 的准确率低 | 先支持 LaTeX + 结构化稿件；PDF 只做辅助 |
| **语义审计太贵** | 专家抽样成本高 | 先做规则 + 小样本；把语义审计作为增值服务 |
| **用户不愿签** | 作者觉得“签了要负责” | 把签署设计成“确认已知限制”，不是“替系统背书” |
| **演示很炫但没人用** | 用户看完说“然后呢” | 用三幕任务验收，不用视觉验收 |
| **范围蔓延** | 同时做生成、审计、修复、协作、自进化 | 只做 J2/J3；J1 用简化版；自进化后置 |

### 9.2 研究会证伪什么

- C2 不成立：硬门只挡语法，不降无证据句 → 硬门降为工程贡献，论文转 C3。
- C3 不成立：影响闭包不如手工 diff/STALE，或处置准确低 → 收窄到“结果变更→摘要句/图”。
- C1 不成立：κ < 0.60 或 R–W 高度相关 → 拆报 R/W；J 降为参考。
- C4 零结果：benchmark 仍可发表；删除“验证瓶颈”强叙事。
- RWMT 不成立：维护任务不比“重新生成一篇”便宜/准 → 放弃产品旗舰，回到 RWJT。
- 用户研究不成立：作者不愿为“影响清单”付费/使用 → 产品转为“投稿前自检”，不做日常维护。

### 9.3 不可以宣称（增补版）

| 不可以写 | 原因 | 可以改成 |
| --- | --- | --- |
| “首个证据链写作 / 首个 claim 绑定 / 首个导出硬门” | ScientistOne/CoE、ARIS、Anti-Autoresearch 已覆盖大部分 | “我们定义并测量证据变化后的维护任务；在本轮核验范围内未见完整的中文核刊维护闭环” |
| “证据链是我们的核心创新” | 正在商品化 | “证据链是基础能力；我们的差异是传播、处置、修复与签署” |
| “中文 + 证据链 = 差异化” | 中文产品已在宣传 | “中文核刊/申报书是验证场；差异化在重跑证据与维护流程” |
| “自动审计 = 科学裁决” | 审计只提供异常与证据，不判造假 | “我们提供可复核的异常证据与修复建议；最终判断由人负责” |
| “Demo 2.0 证明产品可用” | 仍是 SIM/前端 | “Demo 2.0 演示交互；可用性需用户研究” |

| “影响召回 ≥85%” | 目标，不是结果 | “预注册目标 ≥85%；待 C3 实测” |
| “ScientistOne 的数字证明我们落后/领先” | 外部数字未复现，任务不同 | “ScientistOne 报告了其任务上的结果；我们不继承其数字” |
| “我们的系统会自进化” | E7/E8 未跑 | “我们设计并待验证过程协议与租约” |

## 10. 结论

**当前框架最需要的不是第 15 份设计文档，而是一次产品方向的收缩。**

过去几个月的工作已经把“证据闭合”讲清楚：claim–run–artifact、六类槽、只认重跑、导出硬门、失效传播、租约与过程协议。这些设计是扎实的。但 2026 年下半年的竞争态势说明：**“绑定证据”正在成为所有系统的标配**；如果我们继续把它当主卖点，就会陷入与 ScientistOne/CoE、ARIS、中文写作工具的正面比较。

真正属于我们的位置是：

> **证据变化之后，稿件仍然站得住，并且有人能签署。**

这要求产品从“生成流水线”变成“证据运营工作台”，从“写一篇论文”变成“维护一份可交付的证据闭合稿件”。它要求补上六个对象（稿件、运行胶囊、变更集、闭包报告、签署、成本）与六个回路（导入体检、变更修复、语义审计、信念修订、反馈质量、多样性）。它也要求 Demo 从概念片变成三幕工作台：**体检 → 变更 → 签署**。

研究上，这不推翻 [13-](13-创新点评审与主张收敛-需求对齐、开源对照与验证顺序.md) 的 C1–C4，而是把 C3 从“支撑实验”提升为“产品旗舰的核心证据”，并新增 RWMT 作为可测任务。**C2 仍是第一个实验，C3 是产品化的主战场。** 如果 C3 不成立，产品应退回“投稿前自检”；如果 RWMT 不比重新生成更便宜/更准，产品应退回 RWJT。这些止损条件必须提前写死。

最后一句话：

> 我们不是再做一个会写论文的系统；我们让一篇论文在证据变化后，仍然知道哪一句还成立、哪一句必须改、以及谁可以为它签字。
