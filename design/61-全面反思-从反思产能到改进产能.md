> 状态基线：2026-11-05。性质：**只读全量审计 + 一轮已落地的代码改进**。

## 0. 结论先说

1. **工作成果的真实定位**：这是一套工程质量相当高、证据治理纪律相当硬的**受治理科研证据运行时原型**，不是能产出学术结论的科研智能体。最硬的部分（人工门、span-only、负结果保留、构建指纹）经逐条核验成立；最软的部分（真检索、真实验、真签核、生成质量）在 `58-交付验收清单.md` §4 里被作者自己列为 8 项「明确未达成」。
2. **本次审计最重要的新发现不是某个 bug，而是一个循环**：仓库有 62 篇编号文档、约 159 万字符，其中至少 20 篇是「反思 / 自查 / 对账 / 缺陷与改正」；但 `39-系统级反思` §2 的 P0（10-25）到 `58-` §4（10-30 之后）仍是未达成。**反思产能远高于改进产能**。根因不是没想到，而是「想到了但无人裁决」：`60-科研智能体设计缺陷与改正.md` §优先级把 9 条缺陷中的 5 条标为「必须你先定」，`58-` §239 把「整体反思并设计到足够强」判为未达成、阻塞于三个人定决定。Agent 有反思权、无决策权，人这边没有结构化的裁决通道，于是每轮都以「需要你定」收尾。
3. **四个维度里，架构与协作方式的失效是结构性的，任务分工与工作流程的失效是可修的**：架构上「规格说 A、代码做 B、架构文档说 A」三层脱节；协作上文档是事实上的接口却不可执行。任务分工（29 个 SPEC 全是 draft/pilot 却按已交付宣传）与工作流程（证据堆积、签核恒为 0）都有明确的最小修法。
4. **本轮没有再写一篇「建议」，而是做完了一条**：按 `60-` D6 的授权（明确写着「可直接实现、不需要你先决定任何政策」）落地了文档路径守卫，19 例可失败用例、规格升版、导出与发布树同步。落地过程中守卫把自己判负过一次，如实保留。
5. **一句话改进方向**：不要再增加阶段、面板、概念或反思文档；把已有规则变成机器可执行的守卫，把「需要人定」压缩成三道带默认值的二选一决策题，然后让证据走完最后一公里。

## 4. 科研智能体设计的四维审计

### 4.1 架构：稳定内核硬、适配层脱节

**有效性**：Kernel 层（证据、门禁、哈希、越界校验）确实稳定且不可绕过；Capabilities 的注册表化方向正确（`executable.py` 的 `supports`/`cannot_test`、`search_lab.py` 的 `SEARCH_FACTORS`）。

**问题 A1（最严重）：唯一 dispatch 的说法与依赖方向相反。**
`ARCHITECTURE.md:237` 写「`framework_api.py` 是唯一 dispatch 层」，`AGENTS.md:51` 写「MCP/HTTP/Python 必须共用 `framework_api` 的 dispatch」，`mcp_tools.py:1-6` 也这么写；实际 `framework_api.py:11-19` 是 `from .mcp_server import dispatch_tool ...`，真正 46 分支的调度中心在 `mcp_server.py:3738-3843`。HTTP 面确实复用它（`runtime/app.py:533` → `framework_api.call_tool` → `dispatch_tool`），但 `cli.py` **完全没有 import** `framework_api`/`dispatch_tool`，自带 127 个 `_cmd_*` 与约 2063 行 argparse。同一业务在两处各写一遍：`mcp_server.py:1363-1401` 与 `cli.py:1354-1376` 的 `writing_pack` 各自校验参数、各自写文件。
→ **建议 A1-a（低成本、可先做）**：在文档里如实改为「`mcp_server.dispatch_tool` 是唯一 dispatch，`framework_api` 是它的薄适配；CLI 是第二套独立执行面」，并补一条 `tests/test_cli_mcp_equivalence.py`：对 top-N 只读命令（如 `writing pack`、`rsi story`、`closure status`）断言 CLI 与 MCP 产物逐字节或按规范化 JSON 等价。验收判据：故意让 CLI 少写一个字段，测试红。
→ **建议 A1-b（长期）**：把 CLI 的 `_cmd_*` 逐个迁到共享 dispatch，但这是跨模块重构，必须另立计划、一次一个命令族，不要顺手做。

**问题 A2：门禁实现参差不齐。** G1/G2 是真校验，`Q0` 由 `flow.py:63` 计算；但 `pipeline.py:1080-1081` 的 G3/G5 只是硬编码 `status:"blocked"` 字符串，没有独立判定函数，只在 `write_pipeline_artifacts():1604-1620` 就地改写。
→ **建议 A2**：给每个 gate 一个纯函数 `gate_decision(gate, artifacts) -> {status, reason, evidence_refs}`，并把 `pipeline.py` 里那些字符串常量换成调用。验收判据：删掉某个 closure 产物，G5 的 reason 必须列出缺哪个 `evidence_ref`，而不是仍返回同一句固定文案。

**问题 A3：可数据化的东西仍硬编码。** `pipeline.py:232-246` 从 capsule 字符串猜数据集，`:527-545` 按 `run_dataset` 写死三套 hypothesis/baseline/metric/seeds，`:1408-1426` 按数据集名硬编码 `delta_r2`/`accuracy`；`revision_templates.py:9`、`figure_workflow.py:28` 的 profile 仍是代码（`modules/README.md:47-48` 自己标了「计划 JSON registry」）。而 `executable.py` 已经有现成注册表，`pipeline.py` 却绕过它。
→ **建议 A3**：让 `pipeline.py` 的 dataset profile 从 `executable.py` 的注册表读取；未知数据集直接拒绝而不是 fallback 到 iris。验收判据：往注册表加一个新 profile，不改 `pipeline.py` 就能跑；删掉某个 profile，引用它的命令在写入时失败。

### 4.2 任务分工：模块边界清楚，但「规格是唯一源」没有被执行

**有效性**：29 个模块按 S0–S16 与 META 分层，`SPEC.md` 的 frontmatter 齐备，`AGENTS.md` §8 有模块→代码映射；「子智能体不得直接写 Claim/EA/Verdict」在人签链上基本成立（`modules/run.py:380-393` 强制 `human_reason`，`study_claims.py:1061-1075` 同）。

**问题 B1：规格校验器不校验规格。** `AGENTS.md:42` 要求正文至少六节（Purpose / Contract / Current Implementation / Boundaries / Minimal Change Workflow / Changelog），但 `specs.py:146-158` 的 `validate_spec()` 只查 id/version/status/stage/outputs/路径名；`tests/test_specs.py:74-84` 扫的是临时目录里的合成 `demo` 规格，不是真实模块。后果已经落地：
- `modules/guideline-memory/SPEC.md:23,29,37,42,47,54` 用 `#`（H1）而非 `##`，且有两个 Changelog 标题 —— `specs.py:227-239` 的 `_patch_section()` 只认 `"## " + section`，对它执行 `spec patch --section "Current Implementation"` 会**追加重复节而不是替换**；
- `modules/bibliography/SPEC.md` 缺 `## Minimal Change Workflow`。

→ **建议 B1（P0，无需人定，与本轮改进同族）**：在 `validate_spec()` 增加 `REQUIRED_SECTIONS` 校验，并新增 `tests/test_real_module_specs.py` 枚举真实 `modules/*/SPEC.md` 断言六节齐全、标题级别为 `##`、Changelog 唯一。修掉上述两处规格（只改结构，不动契约，各升 patch）。验收判据：把任一 SPEC 的 `## Contract` 改成 `# Contract`，测试红；`spec patch` 对所有模块都只替换不追加。**本轮未做**，因为 `AGENTS.md` §3 要求一次只改一个模块，而它跨 `specs.py`（共享层）与两个模块 SPEC。

**问题 B2：两处越界。** `benchmark.py:104-111` 用硬编码 `human_reason="benchmark reviewed EA"` 直接调用 `RunAgent.claim()` 生成 `status=supported` 的 claim，且能通过 `pipeline.py:224` 的 `claim_signed` 判定；`mcp_server.py:2424` 的 `research_support_verdicts` 把 agent 提供的 verdict 写进 `support-ledger.json`，只校验 `rationale`、无 `human_reason`。前者违反 `AGENTS.md:251`「不自动创建 Claim」，后者在语义上是 support verdict 但确为 Verdict 落盘。
→ **建议 B2**：`benchmark.py` 的假签核改为显式 `benchmark_only=true` 且不计入任何 `claim_signed` 判定；support verdict 落盘时强制带来源面与 reason。**这两条涉及 claim 不变量，按 `AGENTS.md:60` 必须停下来要人工确认，本轮不动。**

**问题 B3：状态与宣传脱节（见 G1）。** 一个全库 0 个 `active` 的系统，`README.md` 却在用「已支持」语气写核心能力。
→ **建议 B3**：给 `status` 定义可验收的晋级条件（例如 `active` 需要：契约测试 + 至少一次非 fixture 的端到端跑通 + 边界文档齐备），并在 `workspace export` 的 agent-registry 里把 status 透出给前端；前端对 `draft` 能力显示「试验」而不是「可用」。

### 4.3 工作流程：闭环形状完整，最后一公里断开

**有效性**：S1→S16 的纵切、三套 closure profile、RunCapsule→EA→Claim→Closure→Lineage 的对象链、`next_actions` 自推进（`54-`）、复现计数（`55-`）都是真设计；strict 模式走过 G1/G2 撞出过 4 个真缺陷（`57-` §3.18）。

**问题 C1：证据生产远快于主张消费。** 190+ 研究包、4 环境、预注册与基线俱全，但已签确证 claim = 0（`60-` D4）。`59-自改进度量设计.md` §1 的口径更冷：431 个比较里 0 条已签确证结论、235/431 做过功效检查。唯一越过事先声明阈值的结论落在次度量 `best_score` 上，因 `search_lab.py:735,1255` 硬编码主度量而签不了（D2）。签核者要读简报、断言、复现计数、功效层级、基线绑定，信息分散在多份产物，成本从未被设计。
→ **建议 C1**：实现「可签包」（brief + assertions + replication + power tiers + baseline binding + environment，单文件带哈希清单，每项带自己的 base），签核命令只接受该包；配一次人工授权的重绑策略（见 §5 决策 3）。验收判据：一个不含 base 的包被拒；重绑后 `lineage verify` 通过且不改任何数值。
