## 3. 仍然存在的结构性问题（未修，含理由）

1. **两个巨型入口文件**（见 §1）。修法是把 handler/schema 分域拆分（`cli/` 包按 `study/memory/run/writing` 分模块；`mcp_server` 的 tools 表用注册表生成），但这是大范围移动代码、且 `tests/test_workspace` 的 catalog 快照会整体重写，**不适合在半成品状态下做**。这是下一轮最该专门做一次的事。
2. ~~**N× 重复扫描**~~ —— **本条被我夸大，实测后撤回**。在 `runtime_data/idea-replication` 上插计数器实测：
   一次 `pending_study_actions` 触发 `build_replication_report` **2 次**（idea 数上限 3，且已有 claim 草稿的
   想法直接静默），单次成本 **0.03 秒**（同级 11 根 / 25 包，都是小 JSON）。这远够不上"明显的重复 IO"，
   我在写这条时是按"每个调用点各算一次"的结构推断的，没有先测。结构上仍是可优化点（把 report 作为参数
   注入比现在更干净），但**不是性能问题**，因此从下一轮优先级里移除。
   自我修正的理由：这份文档的全部价值就在于它是测量而不是印象——同一套纪律如果只用来量别人，就不成立。
3. **宿主服务没有版本探针** —— **本轮已修**。此前三次无法判断 Qoder 里跑的 MCP 进程是否新码：工具描述仍写
   `Requires a configured DeepSeek key`（源码已 grep 不到 DeepSeek）、调用 `research_innovation_review` 真的发出
   HTTP 请求并失败、`research_model_respond` 又不在其工具表里——而同一个 `research_status` 却已经返回了
   `replication/overturned/power_ladders` 这些新字段。证据互相矛盾，只能猜。
   现在 `paths.build_fingerprint()` 对包内全部 `.py`（本机 184 个文件）取哈希，经
   `capabilities()["build"]` 与 `research_status` 的**结果载荷**一起暴露（第一版我误挂在传输信封上，被
   `structuredContent` 丢弃，测试抓出后改到载荷内）。实测对照：本进程指纹 `7c100540fda2c4fa`，
   而 Qoder 活动服务的 `research_status` **不含 `build` 字段** → 一次比较即可判定"服务是旧的，需要 reload"，
   不再需要猜测。副作用也记录在案：reload 前，活动服务的复现报告仍只看本项目目录（不含同级根）。
4. **记忆归属的不对称**：我用 CLI 回答宿主轮次时，回执里 `host_label = unspecified-host`；从 MCP 回答才可能带宿主标识。独立评审的供给判定依赖这个字段，因此"谁来答"会影响可核验的独立性——需要在 CLI 侧也允许显式标注（或拒绝冒充宿主）。
5. **过期轮次无人清理**：`host-model status` 显示 `expired: 7, pending: 1`。过期不是错误，但账本只增不删会让真正的 pending 被淹没，需要一条只读巡检或归档动作。
6. **`code_fingerprint` 仍是整文件哈希**：任何注释改动都会把旧包判成 stale。今天试过用 canary 相同来**解除**阻断，被既有守卫测试正确拒绝（canary 只覆盖一个 2×2，用它解除不安全），最终只加了正向证据（`code.canary_stable`、`--verify-repro` → `code.reproduced`，实测同一报告里 `unchanged=fail` 与 `reproduced=pass` 并存）。这条保守性还留着，属于设计取舍而非 bug。

## 3.5 一条测量学教训（由我自己的错误度量暴露）

给记忆做 A/B 时，第一版我拿三条**运行时已在执行的门**当指标（引用落到 ≥2 来源、否证句非空、计划过
`validate_plan`）。两臂实测全部 1.0、delta 0.0、`no_difference` —— 看起来像"记忆没用"，实际是
**度量在天花板上**：能进产物的想法必然已经过了这些门，所以任何干预都测不出来。补上三条有动态范围的
检查（来源广度、停止规则是否写明 seeds/配对/预算、是否点名风险）后，同一批真实两臂立刻给出
`power_aware_stopping_rate` 1.0 vs 0.8 的差，且只出现在预期维度的那一项上。

这条适用于整条链：我们后面任何"改进有没有用"的问题，都必须先问**指标是否离饱和点足够远**。
`55-` 的功效阶梯与 `56-` 的对照臂都是同一个原则的不同侧面。

## 3.6 护栏开火率：第一次有可复算的反事实数字

`closure guard-audit --project P`（`study_claims.guard_audit`）算的是：**如果护栏不在，会有多少断言
摆到人面前**。对当前 6 个项目、21 个研究包的实测：

```
offered (无反事实护栏时会给人的断言)   37
blocked (被本项目/同级项目的更高功效或跨环境证据否定)  3
总体开火率                            8.1%
只看"存在可对照档口"的包（33 条）      9.1%
packages_fully_blocked                0
```

两点方法论上的自我约束，比数字本身更重要：

1. **分开分母**。`parent-policy` 的 4 条 offering 全在**没有高功效孪生**的设计上，`0/4` 不是"安全"，
   而是"无法审计"——所以报告同时给 `power_audited_packages / offered_in_auditable_packages /
   blocking_rate_where_auditable`，避免把缺证据当成阴性结果。这正是我批评 TTME 用沙箱分数当唯一裁判时
   需要的同一纪律。
2. **它测的是开火，不是质量**。边界写进产物：`a guard-firing measurement ... says nothing about whether
   accepted papers, reviewer scores or author time improved`。要把 N1 变成论文主张，仍然需要
   **有/无护栏的对照运行**（E1），这个数字只是让那件事变得可测量、并且给出预期效应量级——
   若一次评审平均产出 6–8 条可签署断言，护栏大约每 4 次评审挡掉 1 条虚假断言。

## 3.7 反转率 11.1%：`55-` §3d 的量已落进产物

`55-` §3d 的量已经落进产物（`power_audit`）：**27 条低功效判定里 3 条在更高功效上不再成立（11.1%），
全部是区间回到零、无符号翻转**。这就是"如果没有这套护栏会发生什么"的直接计量——那 3 条本来会作为
可签署断言进入人签环节。同一份阶梯也规定了防护的形状：剔除断言，而不是怀疑方向。
诚实的限制：分母小（27）、且只有 iris 被我刻意跑到 8/16/32/64 四档，其余数据集档口不足，
所以这是**这套数据上的代价**，不是普适反转率。

## 3.8 E1 试点：同一批真实包的两臂对照（护栏开 / 护栏关）

§3.6 给的是**平均开火率**，它回答不了"这条护栏到底拦下了什么"。本轮把反事实臂做成产物：
`study_claims.build_study_claim(..., use_replication_guard=)` + CLI `study claim --no-guard`，
两臂分别落 `claim-draft.json` 与 `claim-draft-unguarded.json`（不同文件，反事实臂不覆盖受保护那份），
`verification.replication.guard_enabled` 记录本用了哪条臂。

对 3 个**已存在的真实包**各跑两臂（证据池 28 包，含同级项目）：

| 包 | 带护栏可签署 | 不带护栏可签署 | 被拦下的 |
| --- | --- | --- | --- |
| `power-ladder/studies/STUDY-IRIS-16` | 1 | 2 | `memory_on_gate_off` |
| `idea-replication/studies/STUDY-IDEA-01-iris` | 1 | 2 | `memory_on_gate_off` |
| `from-idea-check/studies/STUDY-IDEA-01` | 1 | 2 | `memory_on_gate_off` |
| 合计 | **3** | **6** | **3** |

三点读法，前两点是这套系统真正想要的性质：

1. **在护栏适用的包上，它拦掉了恰好一半的待签断言**（3/6）。这与 §3.6 的 8.1% 不矛盾：后者是
   跨 21 个包的**平均每包**开火率，而这里刻意挑的是"存在高功效孪生且低功效包已判定"的包。
   两个数一起看才是护栏的真实形状：平时安静，在能判定 wrong 的地方很准。
2. **被拦的三条是同一个断言**（`memory_on_gate_off`，16 种子点估计 +0.12、CI [0.0500, 0.1916]，
   在 64 种子的同设计同数据集包上重新跨零）。也就是说 3 不是三个独立错误，而是 `55-` 里那句
   "只用归档就更好"的 anecdote 在三个包里的三次复现——护栏把它们**当成同一件事**拦了三次。
   这是跨项目/跨功效分组（同一 `design_key` + 同一数据集）生效的直接证据，而不是三条各自运气好。
3. 反事实臂**不能签**：`--sign --no-guard` 直接 `ValueError`（"it cannot produce a signed claim"）。
   本轮所有产物仍是 `status=draft`、`signed=false`；我没有签署任何东西。

诚实边界（决定了这条还不能进论文的"效果"一节）：

- 3 个包不是任务集。这条测的是**拦截行为**，不是评审质量；要把 N1 写成主张，需要 N 条想法两臂各跑一遍，
  指标是"进入人签的假阳比例"与返工次数（§5 第 4 条）。
- 三条被拦断言同源，因此 3/6 的有效样本量近似 1；写成"50% 的过度声明被拦下"是错的措辞。
- 两臂共享同一份证据池（28 包 / 11 根），差别只在是否按该池剔除，不存在"臂间信息泄漏"这种混淆。
- 早于 `guard_enabled` 字段的旧草稿（`declarative-study` 两份、`STUDY-IRIS-64` 一份）该字段为空，
  含义是**臂未知**，不是"臂关闭"；做统计时要排除，不能算进反事实臂。

写测试时我自己犯过一次 §3.5 同类的错：先按"全被拦时返回 0 条可签署断言"的直觉写断言，读码才看到
那条路径是**抛错而不是产出空草稿**（空草稿会让人以为审过了）。改断言而不是改行为——这是本轮唯一
一处"我以为系统会怎么做"与"系统实际怎么做"的分歧，且分歧方向是系统更保守。

留出检验之后（§3.10，证据池从 28 包变 30 包）两臂重跑：逐包仍是 1 vs 2、合计 3 vs 6，但被拦断言的
`superseded_by` 现在指向 `STUDY-IRIS-128`（含 64 个从未参与该判定的新种子），
`comparisons.memory_on_gate_off` 变成 `undecided / decided_in=[]`。也就是说这句话现在由产物自己说出，
不再是我人工比对两个目录：护栏这次拦下的，是一个用留出数据也救不回来的断言。原 6 个项目的
`closure guard-audit` 聚合保持不变（46−9=37 条 offering、3 条阻断、8.1%；可审计口径 3/33=9.1%），
因为两个留出包都没有在低功效下判定任何新东西——这符合预期：留出是用来验证的，不该改变开火率基线。
护栏的不变量也由测试固定为**包含关系**而不是"越严越好"：同一证据池下 `guarded ⊆ unguarded`
（`test_guarded_assertions_are_never_more_than_the_unguarded_ones`）。

## 3.9 把 §3.5 的饱和审查推广到写作面板：量出来的不是"好不好"，是"有没有信息"

§3.5 的教训（指标离饱和点太近就测不出任何干预）当时只用在了记忆 A/B 上。本轮把同一条纪律对准
**我自己展示给用户的面板**：对磁盘上全部 133 份 `writing-audit.json` 逐检查项统计状态分布
（产物 `runtime_data/metric-saturation-writing-audit.json`）：

```
审计份数                     133（其中 fixture 模式 127 / 真实语料 6）
检查项总数                    21
从未出现过非默认值的项         15 / 21
```

三个层次必须分开写，否则这条就变成自我表扬：

1. **样本构成先于任何结论**。127/133 是离线演示产物，`fixture` 检查在它们里恒为 blocker 级 `fail`
   ——这是正确的（fixture 不可投稿），但也意味着"面板全绿"这句话的分母里 96% 不是真实稿件。
   README 里凡是用审计面板支撑"写作有闭合检查"的地方，都应当改成"结构/数值检查在 6 份真实语料稿上
   全部通过，其余为离线演示"。这是削弱自己的表述，不是加强。
2. **饱和里挖出一个真实缺陷**。9 个 `structure.*` 检查项在全样本上恒 `pass`，且失败分支在 `tests/`
   里**零引用**。做实验确认原因：`REQUIRED_SECTIONS` 是标题子串匹配，一个标题可同时满足多个必需章节。
   实测一份只有 6 个标题的稿（"引言与相关工作 / 实验与结果 / 讨论与结论"）报
   **`structure.* 9/9 pass`、`status=ready_for_human_review`、`blockers=[]`**——一篇没有独立引言、
   独立结果、独立结论的稿子拿到满屏绿。这是过度记分，正是这套系统对外宣称要防止的那类"看起来完整"。
3. **修法选择暴露价值排序**。合并章节是期刊/会议常见写法，**阻断它是错的**；问题只在面板把合并
   读成"9 个章节都存在"。所以新增 `structure.merged_headings`（`severity=warning`，永不进 blockers），
   detail 逐个列出被同一标题满足的章节组；标题一一对应时为 `pass`。同时补上此前没有测试的失败分支
   （删除摘要 → `structure.abstract=fail` 且进 blockers），并把一条**名字承诺了它没断言的覆盖**的测试
   （`test_review_draft_needs_no_claim_but_still_needs_sections_and_citations` 实际只断言了
   `claim.signed`）改名为它真正断言的东西。

方法论上最重要的一句：**饱和不等于错误**。恒 `pass` 的检查项可能是上游强制的回归护栏（那它有防漂移
价值），但它**不是信息通道**，因此不能出现在任何"改进有没有用"的效果表里。正确用法是把这 15 项分成
两类——上游强制（保留，但必须有失败分支测试）与无动态范围（从效果指标里剔除）。`57-` §3.5 的记忆
指标、`55-` 的功效阶梯与这条是同一原则的三个侧面。

复现：`python -m research_agent manuscript audit --project P --run-id R --draft <稿>` 产出面板；
分布统计脚本是一次性只读聚合，产物已落 `runtime_data/metric-saturation-writing-audit.json`。

## 3.10 注册表加一个因子 = 旧证据全部退役（本轮最重要的工程性发现）

§3.8 的留出检验本身暴露了一个更基础的问题：我为验证护栏新跑了两个 iris 包，跑完 `study replicate`
把它们放进了 **`unreplicated`**。原因不在数据而在键：0.20.0 加 `parent_selection` 因子后，新包的
`design` 多了一项 `parent_selection=['uniform']`，`comparability_key` 从 `93acf117bb219741` 变成
`6e1a00e0c5dd6bb8`，而旧包从未声明这个因子（当时它还不存在）。于是：

- 复现分组把同一个实验的两次执行判成两个实验；
- **签署护栏同时失明**：它按 `design_key` 找"同设计同数据集的更高功效包"，键一分家，新旧包互相看不见；
- 每加一个因子就开一个"证据纪元"，纪元之间不复现、不累积。这一条会随着因子数量**单调恶化**。

最危险的地方是它**不报错**：所有测试全绿、所有数字都对、报告也照样产出，只有分组悄悄变了。
我是靠"自己新跑的包出现在错误的组里"才发现的——如果没有这次留出实验，这条会一直藏着。

修法把可比性写成一条规则，而不是打补丁：停在**在任水平**（`search_lab.INCUMBENT_LEVEL`，即注册表每个
因子的首水平）的单水平因子不进入比较键——旧包没声明 = 该因子当时不存在，新包声明为首水平 = 行为与
不存在时相同，两者是同一个实验。三条边界都写明并测了：

- 离开在任水平的固定控制（`operators=feature_only`）**仍在键里**，那是另一个实验，不许合并；
- 注册表里没有的未知因子**一律保留**（无在任水平可比，保守处理）；
- "首水平 = 旧行为"这个约定不能只靠注释维持：新测试用 `inspect.signature(run_condition)` 把每个因子的
  在任水平与 runner 自己的默认值对起来（`operators` 特殊处理：注册表存集合名、runner 收元组），
  两处一旦漂移测试立刻红。

留出后实测（30 包、同级项目计入）：iris 阶梯从 6 包变 8 包 `[8,16,32,64,64,64,64,128]`；
`power_audit` 分母 27→31、`overturned` 仍是 3、反转率 11.1%→**9.68%**，`by_power_step` 改为
16→128 / 32→128 / 8→64；§3.8 的两臂重跑逐包仍是 1 vs 2（合计 3 vs 6），但被拦断言的
`superseded_by` 现在指向 `STUDY-IRIS-128`——即**运行时自己**（不再只是我人工读数）确认那次拦截由
未参与该判定的新种子支撑。

必须说清的一条：合并证据**不是单调收紧**。池子变大既可能新增拦截，也可能让原先的拦截被更新的
高功效证据推翻（这次恰好是后者没发生）。这是证据驱动的门应有的行为方向；如果只把"只增加拒绝"
当成不变量，就等于要求护栏永远越来越严，那本身是错的假设。护栏的真实不变量是：
**同一条证据池下，护栏给出的断言集合是不带护栏集合的子集**。

## 3.12 全流程实跑 + 护栏当分类器打分：0.75 精确率，和一次很有价值的误拦

### A. 今天真的用 CLI 跑通了一次完整回路（不是单元测试）

`pipeline run --real-corpus --study-dataset iris`，宿主（Qoder）连答三轮：S2 想法候选 → S4 实验设计
→ S8 非结果章节。每答一轮重跑同一命令，已答的轮次按哈希重放。最终 `modules` 状态：

```
literature ok · q0 pass · synthesis synthesized · idea candidates_need_human
experiment needs_human · study executed · figure schematic_ready · paper needs_evidence
```

三个细节决定了"闭环"这两个字是否名副其实：

1. 那次 8 种子研究的三条比较**全部跨零**，系统报的是"无方向性结论"，而不是拿 +0.104 的点估计当结果；
2. `manuscript-audit` 是 `blocked`、`submission_ready=false`、claim 注册表 0 条，
   阻断理由直接写着 `results.signed_claim: result.primary is pending_evidence`；
3. 研究包带 `study-origin.json` 且 `idea_id=IDEA-01` ——想法真的被执行了，不是被描述了。

也就是说这条流水线能一路走到写作，但在没有签核的地方**拒绝把散文当结果**。这才是它和"会自动写论文的
agent"的差别，也是 §2 那三个判定（资格/完成/失效）第一次在同一次实跑里同时可见。

### B. 护栏第一次被当成分类器打分，而且分数不是满分

`scripts/e1_guard_experiment.py`：3 个互相独立的设计（memory×gate、memory×parent_selection、
gate×operators）× 2 个数据集 × 3 段**互不相交**的种子——提出档 1..12、裁决档 13..48、
留出档 49..96。留出包写在 `eval/` 而不是 `studies/`，同级扫描看不见它，所以护栏在判定时
**结构上无法接触真值**（这是 §3.8 那条"循环风险"的正面解法）。

```
可提出断言 6 · 护栏拦下 4 · 放行 2
true_positive 3 · true_negative 2 · false_positive 1 · false_negative 0
拦截精确率 0.75 · 放行中的漏放率 0.00
```

漏放率 0 是好消息；**唯一那次误拦比数字更有价值**：

| 阶段 | `memory_off_gate_on_operators_feature_only` |
| --- | --- |
| 提出档 1..12 | +0.3083 CI [0.1168, 0.4999] 判为正 |
| 裁决档 13..48 | +0.0773 CI [−0.0326, 0.1872] 跨零 → 护栏据此推翻 |
| 留出档 49..96 | +0.0778 CI [0.0020, 0.1536] **仍判为正** |

效应是真的，但只有低功效估计的**四分之一**。现行规则把"裁决档未判定"一律算作推翻，
等于把"没有证据"与"证据表明没有"合并处理——而小样本在现实里的主要失败模式恰恰是
**效应量被高估**（winner's curse），不是符号翻转（本轮 31 条低功效判定里 0 例符号翻转，§3.7）。

这条不能顺手改：把某些"未判定"降级成警告会让断言重新可签，那是**放宽 claim 门**，
按 AGENTS.md §3 必须人工确认。本轮只加可见性（`shared_seeds` / `arbiter_independent`，
v0.24.0），把建议留给人裁决：overturn 分两级——只有裁决档**反号判定**或其区间**排除提出的点估计**
才 block；单纯跨零给 warn 并要求更高功效重跑。

#### 补测之后：上面那段结论被我自己新加的分类否证了

为了给"未判定"一个可区分的说法，本轮新增 `overturn_kind`（`sign_reversal` / `effect_bounded` /
`arbiter_uninformative`，判据是裁决档区间是否排除提出的点估计），并用
`scripts/e1_rescore_claim.py` 重算同一批数据：

```
4 条拦截的分类                effect_bounded 4 · arbiter_uninformative 0 · sign_reversal 0
按"方向"计分                  精确率 0.75（3/4）
按"断言原样（含幅度）"计分     精确率 1.00（4/4）
放行 2 条里幅度被留出档排除的   1 条（提出 −0.1444，留出 [−0.2912, −0.2011]）
```

三件事必须写清楚：

1. **我上一轮提的修法是错的**。"把仅跨零的拦截降级为警告"的前提是这些拦截可能只是没测出来；
   实测 4 条里 0 条属于那种情况——裁决档都明确排除了提出的幅度。降级会放走四条有价值的拦截，
   该建议已从 §5 撤回。
2. **我上一轮报的"唯一误拦"不是误拦**。按断言原样（幅度 +0.3083）计分，留出档
   [+0.0020, +0.1536] 同样排除该幅度，护栏拦得对；我当时只比符号，把度量的粗糙当成了系统的错。
3. **真正的漏洞在另一边，而且更糟**：放行的两条里有一条幅度错了 2 倍。根因不是规则松，而是
   **已签断言只存点估计、`tolerance=0.0`、不存区间**（`ClaimAssertion` 没有区间字段），
   所以幅度错误事后无法被任何机械规则作废——系统能拒绝"方向不成立"，却记不住"我说的是多大"。

下一轮该提的不是"放宽拦截"，而是"**让断言可被幅度否证**"：签核时把 95% 区间随断言一起存下
（或令 `tolerance` 等于区间半宽），使后续证据能用"区间不相交"作废旧断言。这会改变 claim 的
不变量语义，按 AGENTS.md §3 需要人工确认，本轮不自行落地。

### C. 实跑照出的四个流程缺口（本轮全部修掉，除溯源外都有回归测试）

1. **溯源（v0.24.1，上一轮已修）**：pipeline 研究臂把 `falsification` 硬编码成空串。被执行的研究带着想法编号
   却没带"什么结果会推翻它"——只有走 `study from-idea` 才带。改后同一命令重跑，最新包
   falsification 从 0 字符变 287 字符，改前的两个包仍留在 `runtime_data/e2e-full/studies/` 作前后对照。
2. **引用白名单过宽（paper v0.5.0）**：payload 的 `allowed_refs` 与校验集都用**全部** `request.spans`
   （实测 1329 条），而提示词只展示前 40 条 evidence——模型可以引用它从未见过的文本，
   而"文献主张指向 span"正是这套系统的立身之本。新增 `citable_refs()` 作为唯一来源：
   可引用集 = 展示给模型的切片 ∪ 展示的来源卡。方向是收紧，人工门与导出门未动。
3. **宿主轮次没有阶段标识（host-model v0.2.1）**：idea/experiment 走 `_port_for` 时带标识，
   而写手直接调 `gateway.complete`，挂起消息打印 `module=? purpose=?`，宿主必须 dump 整段提示词
   才知道是哪一阶段在等。现在 `host_module` / `host_purpose` 透传，实测新轮次记录
   `module=paper purpose=S8 non-result sections`。
4. **数字守卫误杀（paper v0.5.0，四个里最严重）**：`_validate_writer_sections` 在**含引用的原文**上扫
   `NUMBER_RE`，而 span id 自带数字（`ARXIV-2609.19526-S01-03`），于是宿主写的 5 个章节里 **4 个被判
   `ungrounded_number` 拒绝**，只有那条没引用的一节通过——规则把"引用得越多"变成"越像编造结果"。
   修法是先剥掉方括号引用再扫数字；真实编造的数字仍被拒（新测试用 `35 percent` 钉住两个方向）。

第 4 条值得单独记一句方法论：这条守卫**此前没有任何行为测试**（`tests/` 里只有一条静态源码断言），
所以它能存活到一次真实端到端跑。§3.9 说的是"恒 `pass` 的指标不是信息通道"，这里是它的镜像——
**没有失败分支测试的守卫，等于没有守卫**。新增 `tests/test_paper_writer_guard.py` 四项覆盖：
带引用被接受、编造数字被拒、未展示 span 被拒、可引用集等于展示集。

修完之后同一条命令的实测：`section writer produced 5 section(s); results/method remained
deterministic`，章节状态从 1×`model_draft` 变成 5×`model_draft`，而 `results` 仍是
`pending_evidence`、`method` 仍等 G2 ——**放宽的是文笔，不是证据**。

### D. 对"整体设计是否合理"的判断

- **站得住的**：三态判定单一来源、声明式设计 + 可执行注册表、人工门只在 CLI、宿主即模型、
  以及"反事实臂 / 留出档 / 构建指纹"这类能拒绝自己的机制。今天 A、B 两块之所以**能被这样审计**，
  全靠最后一类；没有它们，我只能像上一轮那样把"看起来对"写成结论。
- **还欠的**：判定语义混淆"无证据"与"证据为无"（B）；恒 `pass` 的面板仍被当效果证据引用（§3.9）；
  两个巨型入口文件；记忆两臂仍由同一宿主作答；留出与种子不相交性只是可见字段，还没成为判定维度。
- 一句话总评：这套系统现在的价值不在于能自动产出多少文字，而在于**它的错误开始可测量**——
  本轮新增的三条数字（0.75、0.00、以及一次 4× 的效应量高估）都是它自己产出的。

## 3.13 面向"平台 + 即插即用插件"的两块落地，以及第三次撞到的同一类毛病

用户把目标形态说清了：**一个平台 + 一个插件，效果一样，插件即插即用**。这暴露出我们过去没当
一回事的一件事——**可发现性也是契约的一部分**。本轮做了两块：

**一、file-drop 传输（`research_agent/handoff.py` + CLI `handoff export|import|status`）**
宿主只要能读写文件就能供模型能力：pending 轮次写成 `inbox/MT-xxx.json`（请求原文 + 期望形状 +
`messages_sha256` + 过期时间 + 答案格式），答案写回 `outbox/MT-xxx.answer.json`，导入走**同一个**
`ModelTurnLedger.respond`。所以形状校验、哈希绑定、一次性消费、`reject_count`、过期全部沿用，
没有第二套规则。为什么这条对"插件"是关键：它**没有长驻进程**，因此 §3.11 那类"连接器缓存旧模块"
的陈旧问题在这条路上结构上不存在；而 Codex/Zcode/Qoder 的宿主差异主要在权限与会话形态，不在协议。

**二、能力清单从手抄改为派生（integration v0.24.0）**
实测漂移规模很难看：真实 CLI 有 **170 条命令路径 / 37 个命令组**，而导出的
`command-catalog.json` 是手抄的 **48 条**，`study` / `memory` / `handoff` / `host-model` /
`benchmark` / `empirical` / `project` / `bibliography` / `signer` / `action` / `research` / `web`
**共 12 个组对宿主完全不可见**——包括本轮刚交付的复现护栏、留出验证和 file-drop 本身。
也就是说"插件即插即用"在事实层面不成立：宿主读到的清单里没有这些能力。
修法是 `workspace.cli_command_surface()` 遍历 `build_parser()` 的子命令树产出叶子，
快照 = 人工条目（`curated=true`，保留人写的描述与安全分级）+ 派生条目
（`curated=false`、`safety=catalog_only` 明确声明"未经人工分类、不携带安全承诺"）。
前端 `CommandRecord.safety` 加该取值、`SAFETY_LABEL` 加"未分类"，`tsc --noEmit` 通过。

**必须点名的模式**：这是本仓库**第三次**撞到同一类毛病——
§3.5 记忆指标全在天花板、§3.9 写作面板 15/21 恒 `pass`、这次是能力清单恒绿却漏掉 12 个组。
三次的共同结构都是**"绿色来自与自身比对的产物"**：`test_workspace` 比的就是那份手抄清单，
所以它永远绿。区别只在于前两次我用的是效果指标，这次用的是宿主可见的接口面，
因而后果直接落在交付形态上。修法也统一：让断言对着**不可伪造的外部事实**（argparse 树、
留出种子、真实产物哈希），而不是对着自己抄的清单。新增的四项漂移测试即为此设。

**还欠的三件**（决定"效果一样"是否可证）：① 能力协商（`doctor --host` 输出宿主声明的能力与缺失项，
内核按声明降级，而不是假定 MCP 可用）；② **双适配器一致性测试**——同一任务分别经 MCP stdio 与
file-drop 跑，断言产物内容哈希相同，这才是"平台与插件等价"的可执行定义；③ `plugin/` 打包目录
（三家配置片段 + `SKILL.md` + handoff 用法 + 一条自检命令）。

### 补：一致性测试第一次跑就抓到三处"差异"，而它们都不是分歧

`tests/test_adapter_equivalence.py` 三项（integration v0.24.1）：

1. 同一串 `project_init → plan → run` 分别走**进程内 API**（平台）与**真实 stdio MCP 服务**（插件），
   逐文件比较项目内全部 JSON 产物，只剥离实例身份；

## 3.15 模型供给到底带来什么：一次对照（同主题、两份真实产物）

| | deterministic（`loop-check/run`） | host-model（`e2e-full`） |
| --- | --- | --- |
| 章节数 | 8 | 8 |

## 3.17 不可判定不再是死胡同：给出下一步需要多少证据

闭环跑到 S5 时最尴尬的状态是「三条比较全跨零」——报告如实说不可判定，但读者拿不到下一步。
新增 `seeds_for_80pct`（每个比较一项）与 pipeline 警告里的一句话，把它变成可执行的量：

```
8 种子 iris，3 条比较全跨零
memory_on_gate_off  diff +0.1042  → 约 25 种子
memory_off_gate_on  diff +0.0708  → 约 119 种子
memory_on_gate_on   diff −0.0417  → 约 225 种子
警告：at the observed effect sizes the cheapest comparison would need about 25 seeds
```

三点意义：

1. **与既有复现工作互相印证**：`55-` 里 16 种子的 +0.12 在 64 种子上没站住——按本公式它需要约 25 种子
   才有机会判定，即「它本来就该被更大样本证伪或确认」，而不是「再跑几次就好」。
2. **边界写在字段里**：`power_note` 明说这是以观测效应量为基准的规划估算、不是对效应的承诺、
   不参与任何门禁；种子不足（<2）或无效应时返回 null 而不是编一个数。
3. **它改变的是报告的语气，不是判定**：仍然不可判定，但「不可判定」后面跟着「要多少才有机会」。

## 3.19 想法阶段的结构性缺陷：候选永远只能引用一篇论文

实测发现：宿主写的 3 个候选在词法预审里**全部被判 revise**，理由都是 relies on a single source。
一开始我以为是宿主偷懒，核对后是系统自己的问题——`_proposer_payload` 取的是 `request.spans[:24]`，
而 span 按来源成组排列，**前 24 条几乎全来自同一篇论文**。忠于证据的候选在这种情况下不可能满足
「至少两个来源」，所以 revise 是**提示词构造出来的必然结论**，不是质量判断。

修法是按 `source_id` 轮转取样（`_spread_spans`，各来源各取一条循环到上限）。实测：

```
修复前：证据 24 条 / 1 个来源  → 预审 0 advance / 3 revise
修复后：证据 24 条 / 4 个来源  → 预审 3 advance / 0 revise
```

也就是说「推进」这个结论第一次真的可达——此前 G1 面前的三个候选没有一个被系统认为可推进。

**顺带修掉一个宿主路径的硬伤**：`--idea-file` 原先只接受系统自己的 `idea.json`，宿主直接交的
原始答案（`candidates` 里没有 `idea_id`）会以 `TypeError: missing 1 required positional argument`
失败。现在按顺序补 `IDEA-01…`，缺 title/hypothesis 的候选给出明确错误而不是猜。

这两条合起来的意义：**「模型能给想法」和「这些想法能被系统接住」是两件事**，此前只通了前一件。

**补：确定性路径仍然推不动，这次我选择不修**。同一处取样改动搬到确定性聚类器上（轮转输入）
实测仍是 0 advance / 3 revise——因为该聚类器按 section 分组、且同来源相似度被强制为 1.0，
单来源簇是它的**构造结果**，换输入顺序无用。继续「修」只有两条路：放松同来源偏置，或给每个簇
硬拼一条弱相关的跨来源 span——后者是为翻转判定而造证据，属于我一直在批评的那种做法。
所以这处改动已回退，只保留对模型提示词生效的轮转取样（那里是实测有效且诚实：候选确实引用了
4 个来源中的 2 个），并把预审理由改成可执行指引：*ground it in a second source, or let a model
propose cross-source candidates*。

结论写清楚：**无模型的确定性路径能生成候选、但生成不了"可推进"的候选**；这是供给差异，
不是可以靠调参绕过的缺陷。

## 4. 设计上我认为是**对**的部分（有证据支撑）

- **单一来源的三态判定**：`study_claims.comparison_verdicts` 被闭包、复现计数、claim 剔除共用，因此"能签不能闭"这类不一致被结构性排除（历史上真出现过，修完后没再复发）。
- **只收紧、不放宽的改动纪律**：复现/功效进入签署路径时，新增的全部是**拒绝能力**（剔除被推翻的断言、全被推翻则拒签），没有任何一条让结论更容易成立。
- **确定性重放**：同一控制集重跑逐位相同（64 种子三数据集改码前后数值一致），这让 §3(6) 那种"代码变了但数字不变"的判断成为可能。
- **规格先行 + 漂移测试**：`test_workspace` 两次抓到我，说明这道门是有效的，不是仪式。
- **人工门未被移动**：MCP/runtime 依旧没有 approve/sign/freeze/export；今天所有验证只产出 `status=draft, signed=false` 的草稿。
